# テスト駆動開発 (TDD: RED-GREEN-REFACTOR)

## 原則

テストされていないコードは動く保証がない。**実装の前に、失敗するテストを書く。** これにより「本当に要求どおりに動く」ことと「テストが正しく要求を検証している」ことの両方が保証される。

## サイクル

### RED: 失敗するテストを書く

- 次に実装する小さな振る舞い 1 つを検証するテストを書く
- **まず実行して、期待どおりに失敗することを確認する**。失敗しないテスト(常に PASS するテスト)は何も検証していない
- 失敗メッセージが理解しやすいかも確認する。このメッセージが将来のデバッグの助けになる

### GREEN: 最小限の実装

- テストを通すための**最小限**のコードを書く
- 「後で必要になりそう」のコードは書かない(YAGNI)
- テストが通ったら次へ。美しさはまだ求めない

### REFACTOR: 重複の除去

- GREEN のままでリファクタリングする(テストが通った状態が安全網)
- 重複、ネーミング、構造を改善する
- 各ステップ後にテストを再実行し、壊れたら即戻す

## 実践上のコツ

- **1 サイクル = 1 振る舞い**: 大きく進めない。ステップが大きすぎると感じたら、さらに小さく分割する
- **バグ修正の場合**: まずバグを再現する失敗テストを書く → テストが通るように修正する。これで二度と再発しない回帰テストが残る
- **三角測量**: 1 例だけのテストはハードコードでも通る。2 例目を追加して一般化を強制する
- **テストファーストが難しい場合**(UI 調整、探索的コード): 理由を明示した上で後書きテストでもよいが、最終的に主要な振る舞いはテストでカバーする

## やってはいけないこと

- 実装を先に書いてからテストを書く(後書きテストは実装の都合に引きずられる)
- 失敗確認を省略してテストを書きっぱなしにする
- 内部実装を検証するテスト(プライベートメソッドの直接テスト等)を書く。観測可能な振る舞いを検証する
- テストを通すためにテストを書き換える(要件が変わった場合を除く)
