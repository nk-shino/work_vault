# 提案キュー画面の整理に向けた調査まとめ(デザインシステムの部分採用判断)

- 作成日: 2026-10-22
- 対象: `C:\work\用語集アプリ\src\glossary\web\templates\proposals.html`(読み取り専用で参照。この文書の作成にあたり変更は加えていない)
- 範囲: 公開デザインシステムの指針調査と、本画面への部分採用の判断まで。実装・コード変更は本調査の範囲外であり、行っていない
- 補足: `base.html` も併せて確認した(共通ヘッダ、skip link、`role="status"` の処理中表示、`/static/style.css` と `/static/app.js` の読み込み)

## 0. 結論の要点

1. 主根拠は **GitHub Primer**(GitHub 自身のデザインシステム)。フィルタ、ラベル、状態表示、行リスト、ページャ、空状態について、プルリクエスト一覧そのものの作り方に近い指針が公開されている。指針の「考え方と構造」を部分採用する。
2. **GOV.UK Design System** からは、ステータス付き行リスト(Task list)の利用者調査結果を借りる。要点は「未処理だけを彩色で目立たせ、処理済みは無彩色のテキストに格下げする」「ステータスをボタンに見せない」「補助文は短文1つ」。
3. **Atlassian Design System** からは、空状態の文言基準(理由と次の操作を1〜2文で)を借りる。
4. 表形式への全面変更、JS 製コンポーネントの導入、無限スクロール、相対時間表示は**見送る**。理由は第4.11節に記す。
5. 変更の中心は、1行を「左:状態 / 中央:本文 / 右:検証と操作」の3領域へ再配置し、情報に強弱をつけること。データの表示項目は減らさない(監査性のため全情報を維持する)。

### 1.2 視認性を下げている要因(今回の調査で特定した点)

1. **行内の強調要素が多すぎる。** 1行に最大4種の小要素(種別バッジ、状態バッジ、独立検証バッジ、AI チップ)が並び、どれも同程度の視覚的重みを持つ。一行見て「この提案は今どういう状態で、何をすべきか」が一言で読み取れない。
2. **状態系の情報が行内の複数の高さに散在している。** 見出し行のバッジ、メタ行、独立検証、操作行と、縦方向に別れる。視線の起点が定まらず、行同士の比較がしづらい。
3. **メタ情報が本文と同じ字面で並んでいる。** 「スコア 0.87 ／ 生成元 …」が本文段落と同サイズで表示され、主文(定義文や引用)と補助情報の区別がつかない。
4. **操作部が常時フル表示である。** 未処理行のボタン2つ+リンク1つが本文と同格の塊として存在し、行の輪郭をぼかしている。
5. **件数行とページャの情報量が弱い。** 件数行は本文行と区別がなく、ページャは前後のみでページ数が増えた場合の移動が遠回りになる。

### 1.3 GitHub プルリクエスト一覧の構成(目標像として整理)

Primer の Filter シナリオパターンは「リポジトリの issue 一覧を絞り込む」を実例として挙げており、GitHub の一覧画面の作り方は公開指針から追跡できる。実物の観察も合わせると、構成は次の通りである。

- 上部にタブ(状態)+件数カウンタ、その下にフィルタバー。状態の切替はページ遷移ではなく一覧の絞り込みとして動く。
- 行は「左端に状態アイコン / 中央にタイトル・ラベルチップ・日時などの補助情報 / 右端にレビュー判定などの補足アイコン」の一定配置。
- 補助情報は小さめ・低彩度のテキストで、タイトルが唯一の強調点。
- 操作(コメント、approve など)は一覧の行には置かず、詳細ページに置く。
- ページャは番号付き(前後リンク+ページ番号+省略記号)。

本画面は「一覧で直接処理するキュー」という性質が異なるため、この構成をそのまま真似るのではなく、次章以降の指針に基づいて取捨する。

## 3. 参照した指針の要点

### 3.1 GitHub Primer

**Filter(シナリオパターン)** — 絞り込みの設計指針。本画面のフィルタ改革の主根拠。

- 「フィルタ部品を課題の複雑さに合わせる。複数条件を組み合わせる開放的な絞り込みには Filter、少ない選択肢から1つ選ぶだけなら dropdown、リストから選ぶ形式なら SelectPanel」(本画面の状態は選択肢の少ない単一条件なので、dropdown で足りると判断できる)。
- 「選択肢が既知で選択が明確な dropdown フィルタには即時適用を使う」(「表示」ボタンの押下を必須にしない)。
- 「フィルタ状態は URL パラメータに保持し、共有可能にして再読込でも維持する」。
- 「フィルタ適用済みで開いた場合、元の状態に戻る導線(revert)を用意する」。
- 「結果が絞られているときは適用中フィルタの表示を出す。スクリーンリーダーにも伝わり、色だけに頼らない」。
- 「絞り込みで結果ゼロになったときは、適用中のフィルタ名を示し、リセットを明確にした空状態を出す」。
- 「絞り込み完了後の件数や状態変化は、恒久的な `role="status"` 領域で通知する。視覚だけの変化に頼らない」。

**Label** — 「ラベルは文脈的なメタデータとして視覚的に区別したテキストであり、状態・分類・その他のメタデータを加えるために使う」。色のバリエーション(success/attention/danger/done など)を持つ。分類系の情報はチップで表現する根拠。

**StateLabel** — 「issue やプルリクエストの状態を表示するために使う」。状態ごとに対応するアイコンが紐づき、色+アイコン+短いテキストで状態を表す。状態表示を一定の位置・形式に寄せる根拠。

**ActionList** — 「一貫した単一カラムの形式で項目を提示し、アイコン、説明、側面情報などのリッチな要素の置き場所を確保する」。行に leading visual(先頭)/本文/説明(block 型)/trailing visual(末尾)を置ける構造。破壊的操作には danger バリアントを用意する。**行の内部構造の設計根拠**。

**Pagination** — 「前後リンクのみ」は公式に用意された形態で、「ページの飛び越しを防ぎ順次移動させたい場合はページ番号を隠して前後リンクのみにしてよい」。逆にページ番号を表示する場合は、先頭・末尾を常に残し、現在ページ前後の表示数を調整し、間を省略記号でつなぐ。現行の前後のみページャの評価と拡張判断の根拠。

**ProgressBar** — 「ProgressBar には値を明示するテキストを並べるのが既定。テキストは省略してよく、省略してよいのは意図的に値を曖昧にする場合だけ」。`aria-label` の例も示されている。メーターの表現の根拠。

**Empty states(UI パターン/Blankslate)** — 空状態は「主テキスト(タイトル)/補助テキスト(簡潔で重複しない)/主操作(1つを推奨)/副操作(テキストリンク)」で構成する。手順やコマンドで始めさせる空状態には `code` ブロックの変形がある。枠線は必要なときに付けられる。現行空状態の評価の根拠。

### 3.2 GOV.UK Design System

**Task list** — 名前とステータス(と必要なら hint)からなる行リスト。ステータスは「色と短い語で、全体のうち何が終わり何が残っているかを一目で示す」。

改良の経緯が公開されており、本画面に直接使える知見が含まれる。

- 「一部の利用者がステータスをボタンやリンクだと誤解して選択しようとしたため、ステータスはボタンらしく見えない形に設計し直された」。
- 「大文字表記は読みにくく、処理済みが増えると未処理を見つけにくくなるという調査結果から、ステータスは文頭のみ大文字の普通の文で書き、『完了』は背景色なしの黒テキストにした。これにより要対応の項目が目立つ」。
- hint は「短文1つ、句点なし」で、「hint 内にリンクを含めない」(行全体がリンクになる構造では hint 内リンクが機能しないため)。
- タイトルのリンクとステータスを `aria-describedby` で結び、タイトルを読み上げた後にステータスが続く例が示されている。

**Complete multiple tasks パターン** — グループ分けの指針など。本画面はトランザクションのタスクリストではないため、構造は借りず上記のステータス扱いの部分だけを参考にする。

### 3.3 Atlassian Design System

**Empty state(コンテンツ指針)** — 「空状態の理由と、次にどこへ行けるかを含める」「タイトルの内容の繰り返しを避ける」「メッセージは1〜2文に保つ」。CTA(実行への導線)を本文に含める考え方。現行空状態の文言の点検に使う。

## 4. 部分採用の判断

### 4.1 判断一覧

判断ラベルの定義:

- **部分採用** — 指針の考え方・構造だけを借りて本画面に合わせて使う
- **新規採用** — 現状に存在しない構造を、指針に基づいて導入する
- **現状維持** — 現状がすでに指針に合致しており、変更しない
- **見送り** — 今回は適用しない(理由つき)

| 対象要素(現テンプレートの箇所) | 判断 | 借りる指針 | 主な出典 |
|--------------------------------|------|-----------|----------|
| 状態フィルタ(select+「表示」ボタン) | 部分採用 | 少ない選択肢の絞り込みは dropdown で足りる/選択が明確なら即時適用/URL 保持は現状どおり | Primer Filter |
| 適用中フィルタの表示とリセット導線 | 新規採用 | 適用中フィルタを色以外で示し、戻り道を用意する | Primer Filter |
| 件数行の絞り込み後の通知 | 部分採用 | 絞り込み後の件数を `role="status"` で通知する | Primer Filter |
| 行の内部構造 | 新規採用 | leading visual/本文/説明/末尾要素の一定配置、区切り線リスト | Primer ActionList |
| `h2` 内のバッジ併記 | 部分採用(改変) | タイトルは強調点を1つに。種別はタイトル直後のチップ(Primer Label 相当)へ | Primer Label / GOV.UK |
| 状態バッジ(st-pending 等) | 部分採用 | 状態は色+短い語。要対応のみ彩色、処理済みは無彩色テキストに格下げ。ボタンに見せない | GOV.UK Task list / Primer StateLabel |
| 独立検証バッジ(3状態+理由) | 部分採用 | 行右端の定位置に集約し、色+テキストで伝える。理由は短文 hint | Primer StateLabel・ActionList / GOV.UK hint |
| メタ行(スコア/生成元/プロンプト版) | 部分採用 | 情報は削らず、説明ブロック(muted 小字)へ格下げ。数値は等幅数字 | Primer ActionList(説明ブロック) |
| 確からしさメーター | 部分採用 | バー+値のテキストを併記。`aria-label` は現状維持 | Primer ProgressBar |
| 判定メモ | 部分採用 | 左罫線付きの注記(GOV.UK Inset text 的な扱い)で視覚区別 | GOV.UK の注記扱い |
| モック警告文 | 現状維持(文言のみ点検) | 短文1つ、リンクを含まない hint | GOV.UK hint |
| 行内操作(採用/却下/修正して採用) | 部分採用 | 操作は行に置かないのが PR 一覧の作り方だが、本画面はキュー処理が主業務のため残す。重みを下げ、右領域に集約、1行に主操作1つ、却下は danger 相当 | Primer ActionList(danger)/GitHub 一覧の観察 |
| 処理記録(氏名・日時) | 部分採用 | メタ行に統合。相対時間にはしない | Primer RelativeTime 不採用の判断(4.11) |
| ページャ(前後のみ) | 部分採用 | 前後のみは公式形態。ページ数増加時に番号+省略記号へ拡張 | Primer Pagination |
| 空状態 | 現状維持(文言のみ点検) | 主テキスト/補助/主操作の構成が合致。フィルタでゼロ件のときは適用中フィルタ名を明示 | Primer Blankslate・Filter / Atlassian |
| 画面レイアウトのサイドバー化(PageLayout 相当) | 見送り | フィルタが1項目のため過剰 | Primer Filter(部品を課題に合わせる) |
| 表形式(DataTable)への全面変更 | 見送り | 行の中身が種別ごとに異なり列へ正規化できない | 4.11 |
| JS 製コンポーネント(SelectPanel 等)の導入 | 見送り | 外部接続なし・サーバーレンダリングの構成を維持 | 2.1 |

### 4.2 各判断の詳細

#### D1. 状態フィルタ — 部分採用

- 状態は選択肢の少ない単一条件なので、Primer Filter の「dropdown で足りる」判断に従い、フィルタ部品の置換はしない。
- 採用するのは動作面。「選択が明確な dropdown は即時適用」に従い、`select` 変更時に絞り込みを実行する形へ改める方向性とする。「表示」ボタンは JavaScript 無効環境向けに残す(noscript で提供する)。実装の可否含め、実装時に `app.js` と一体で検討する。
- フィルタ状態の URL 反映は現状の GET フォームで既に満たしており、この点は変更しない。
- 適用済みのとき(「すべて」以外が選ばれているとき)は、選択中の状態名をテキストで明示し、解除導線を近くに置く。これは Primer Filter の「適用中フィルタの表示(色以外でも伝わる形)」と「revert の用意」による。現状は空状態の中にしか戻り導線がなく、結果が1件以上ある絞り込み済み画面に戻り導線がないため、ここを埋める。

#### D2. 行の内部構造 — 新規採用(行の3領域化)

Primer ActionList の「一貫した単一カラム+先頭/本文/末尾の置き場所」という行構造を借り、1行を次の3領域に再配置する。

```
行(article)
├─ 左領域 : 状態アイコン(未処理のみ彩色。処理済みは低彩度)
├─ 中央領域
│    ├─ h2 見出し語(または A ⇔ B)
│    ├─ 種別チップ(h2 の外に移動)
│    ├─ 本文(種別に応じた定義文・引用・関係)
│    └─ メタ行(muted 小字): スコア・生成元・プロンプト版
└─ 右領域 : 独立検証の状態 / 未処理なら操作
```

- 隣接行はカード枠ではなく区切り線で分ける(ActionList の dividers 相当)。現在は行の枠組みが見えにくく、行頭の揃いも定まらないため、この変更だけで掃除された印象が大きく変わる。
- 左領域の状態アイコンは、Primer StateLabel の「状態に対応するアイコン+色+短い語」の考え方による。色覚に依存しないよう、アイコンの形も状態ごとに変える(円/丸印/斜線など)。
- なお GOV.UK Task list の「行全体をリンクにする」考え方は、本画面では採用しない。行内に複数のフォームボタンとリンクがあり、行全体をリンクにすると入れ子の操作要素が発生するためである。行の操作は現行どおり個別要素とする。

#### D3. 見出し語とバッジの分離 — 部分採用(改変)

- 現状は `h2` の中に見出し語と2種のバッジが入っており、見出しの強調が効かない上、`aria-labelledby` 経由で記事名として「見出し語+種別名+状態名」が読み上げられる。
- `h2` は見出し語(または A ⇔ B)のみにし、種別はタイトル直後の小さなチップへ移す(Primer Label の「文脈的なメタデータ」としてのチップ)。
- 状態は中央領域から右領域へ移す(D4)。これにより見出し行は「何の提案か」だけを伝え、「どうなっているか」は一定位置で伝わる。

#### D4. 状態表示の強弱 — 部分採用

GOV.UK Task list の調査結果をそのまま借りる。

- 「完了」に相当する処理済み(採用済・却下済)は背景色のない無彩色テキストへ格下げする。「完了を無彩色にすると要対応項目が目立つ」という改良の知見による。
- 未処理(pending)のみ彩色のタグとし、これが画面で最も目立つ状態表現になるよう揃える。
- ステータスは大文字化や過剰な装飾をしない(読みにくさの調査結果より)。現在の `label()` 出力の文言はそのまま使える。
- 「ステータスがボタンに見えると誤操作される」という調査結果から、処理済みの状態タグは塗りの強い形にしない。

#### D5. 独立検証の表示 — 部分採用

- 現状は本文の途中の段落にバッジが現れるため、行ごとの比較位置が定まらない。GitHub の一覧がレビュー判定を右端に置くのと同じ発想で、右領域に定位置化する(ActionList の trailing 要素の考え方)。
- 表示は「検証:あり / 検証:なし / 検証:未実施」のように短くする。色はあり=緑系、なし=注意系、未実施=無彩色とし、必ずテキストと併記する(色だけに頼らない、Primer Filter の指針)。
- 理由文(`v.reason`)は行の次段に短文の hint として出す。GOV.UK の hint 基準(短文1つ)に合わせ、長くなる場合は省略形にするか、詳細は実装時に定める。

#### D6. メタ行とメーター — 部分採用

- スコア・生成元・プロンプト版は削らない。採用判断の根拠として監査に必要な情報であるため。ただし ActionList の「説明ブロック」相当へ格下げし、小さめ・低彩度・等幅数字で表示する。これにより本文(定義文・引用)と補助情報の差がつく。
- 区切りは現行の「／」を維持してよい。字面の統一は実装時に `style.css` 側で行う。
- 確からしさメーターは現行の条件(pending かつ sense かつスコアあり)のまま残す。Primer ProgressBar の「バーに値のテキストを並べる」に合わせ、メーターとスコア数値を同じ行に置く現行の構成(`meter-wrap` 内のラベル+バー)は方向として正しい。`aria-label` 付きの現行実装も指針に合致する。
- メーターの色は状態色(緑・注意系)と混同しない配色にする。バーの色が状態を意味すると誤読させないためである。

#### D7. 判定メモ・モック警告 — 部分採用/現状維持

- 判定メモ(`decision_note`)は処理済み行のみ出る現行挙動を維持し、左罫線付きの注記として視覚的に他の本文と区別する。
- モック警告は「短文1つ・リンクなし」の GOV.UK hint 基準に現状適合しているため、位置(操作ボタンの直上)と内容は維持する。文言の語尾の統一のみ実装時に点検する。

#### D8. 行内操作 — 部分採用

GitHub の一覧は行に操作を置かないが、本画面はキューとして一覧上で処理を完結させるのが主業務である。指針を機械的に当てはめて操作を一覧から外すと、作業手数が増える。このため部分採用とし、次のように調整する。

- 操作を右領域に集約し、タイトル・本文と視覚的に分離する。
- 1行につき主操作は「採用」の1つのみとし、その他は低強度のスタイルにする。「却下」は ActionList の danger バリアント相当(目立つが主操作より弱い形)、「修正して採用…」はテキストリンクのまま。
- ホバー時のみ表示する形にはしない。タッチ環境で発見できない問題と、キーボード利用での煩雑さを避けるため、常時表示+低彩度とする。
- 処理済み行の「処理:氏名(日時)」はメタ行へ統合し、行の高さを種別・状態によらず揃える。

#### D9. ページャ — 部分採用

- 現行の「前のページ/次のページ」のみの形は、Primer Pagination で公式に認められた形態であり、撤去の必要はない。
- ただし提案の蓄積でページ数が増えると移動が遠回りになるため、ページ数が一定数を超えたら「先頭・末尾を常に表示+現在ページ前後の番号+省略記号」の形へ拡張する(Primer Pagination の番号付き形態)。切替の閾値(例:7 ページ超)は実装時に定める。
- 件数行「N 件(N / N ページ)」は D10 と合わせ、リスト直上の1行として残す。絞り込み結果の通知先として `role="status"`(aria-live)をこの行に設定する方向性とする(Primer Filter の絞り込み後通知)。

#### D10. 空状態 — 現状維持(文言のみ点検)

現行の空状態は Primer Blankslate の構成(主テキスト/補助テキスト/主操作)と一致しており、未処理ゼロの `code` コマンドは Blankslate の code ブロック変形に相当する。Atlassian の基準(1〜2文・タイトルの繰り返しを避ける)にも現状適合している。変更は2点のみ。

- 該当ゼロの空状態の文言に、適用中の状態名を明示する(Primer Filter の「結果ゼロでは適用中フィルタ名を示す」)。現状は「状態を『すべて』に変えると…」で概ね対応済みだが、絞り込み済みであることを一文目で明示すると確実である。
- 主操作(「すべてを表示」)の現行位置は正しい。追加の操作は置かない(Blankslate の主操作1つ)。

#### D11. 見送りリスト(理由つき)

| 見送り項目 | 理由 |
|-----------|------|
| 表形式(DataTable)への全面変更 | 行の中身が種別ごとに異なる(引用リスト/定義文+文脈タグ/関係)。列へ正規化できない。単一カラムの行リストを維持する |
| JS 製コンポーネントの導入(Primer React、SelectPanel 等) | 外部接続なし・サーバーレンダリング+単一 CSS+小規模 JS の現行構成を維持する。指針は考え方と構造だけ借りる |
| 無限スクロール | フィルタ状態の URL 反映(現行で有効)と矛盾する。キューの残量の見通しが落ちる。キーボード・スクリーンリーダー利用の負担が増える |
| 相対時間表示(「3日前」等) | 処理記録は監査用途のため絶対日時を維持する(Primer RelativeTime は参考に留める) |
| 状態タブ+件数カウンタ(Open/Closed 式タブ) | 件数表示のために追加の集計クエリが必要になり、今回の範囲を超える。現行の dropdown+件数行で目的は達成できる。将来の拡張候補として記録する |
| フィルタのサイドバー化(PageLayout 相当) | フィルタ項目が1つのため過剰。Primer Filter の「部品を課題に合わせる」により、単純な dropdown のままにする |
| ホバー開示の操作・画像のアイコン化のみの状態表現 | タッチ環境・色覚特性・キーボード操作での発見性と伝達性の問題 |

## 5. 現状のまま維持する点(変更不要と判断したもの)

指針と照合した結果、次の点は既に適合しており変更しない。

- GET によるフィルタ状態の URL 反映(Primer Filter の指針に合致)
- `label` と `select` の紐付け、可視ラベルの存在
- 空状態の構成と文言の長さ(第 D10 節の微修正を除く)
- メーターの `aria-label`、`article` の `aria-labelledby`、ページャ `nav` の `aria-label` と `rel="prev"`/`rel="next"`
- skip link、処理中の `role="status"` 表示(`base.html`)
- 提案1件=1 `article`+`h2` という見出し階層

## 6. 実装を始めるときの留意点(本調査では未実施)

1. **読み上げ順の確認。** D2〜D5 の再配置後、スクリーンリーダーでの読み上げ順(見出し語→種別→本文→メタ→状態→操作)が自然かを確認する。右領域を DOM の後方に置くか、CSS だけで視覚配置するかは読み上げ順の観点で決める。
2. **AI チップの伝え方。** 現行の `title` 属性は環境によって読み上げられない。チップに `aria-label` か視覚的に隠れたテキストを併用する方向で実装時に検討する。
3. **即時適用フィルタと no-JS 環境。** `onchange` での自動送信を入れる場合、「表示」ボタンは noscript で残す。`app.js` の既存の処理(busy-on-submit)との整合を実装時に確認する。
4. **レスポンシブ。** 右領域(検証・操作)は狭い画面で中央領域の下に折り返す規則を決める。ヘッダのナビゲーションが多く、行の実効幅が中程度の端末でさらに狭くなる点にも注意する。
5. **style.css との整合。** `.badge`、`.st-*`、`.meter`、`.actions` の既存クラスはページ分割せず、強弱の追加(無彩色の状態テキスト、muted メタ行)をクラス追加で行う。種別チップと状態タグは視覚的に別物にする。
6. **着手順の目安。** 影響の大きい順に、(1) 行の3領域化とバッジ分離 → (2) 状態・検証の強弱付けとメタ行の字面 → (3) 操作部の視覚重み調整 → (4) フィルタの即時適用と件数通知 → (5) ページャの番号拡張(ページ数増加後)。
