# 提案キュー画面の整理 — 調査まとめ

- 日付: 2026-10-22
- 対象: `C:\work\用語集アプリ\src\glossary\web\templates\proposals.html`（この文書では参照のみ。実装は別の機会に行う）
- 目的: 提案キューを、GitHub のプルリクエスト一覧のように一覧で見渡せる画面に整理する。公開されているデザインシステムの使用指針（usage ページ）を根拠に、何を部分採用するかをここで決める。

## 1. 現状把握

### 画面の構成要素

- フィルタ: 状態のセレクト（すべて・未処理・採用済み・却下）＋「表示」ボタン
- 件数表示（総件数と現在ページ / 全ページ数）
- 空状態（2種）
  - 未処理で空のとき: 見出し「未処理の提案はありません」＋取り込みコマンドの案内
  - それ以外: 見出し「該当する提案はありません」＋状態変更の案内＋「すべてを表示」リンク
- 提案カード（1件につき1つの `article.proposal`）
  - 見出し語（または置換語の対「A ⇔ B」）＋種別バッジ（語義・関係・用例の追加）＋状態バッジ（未処理・採用済み・却下）
  - 判定の注記（`decision_note` があれば）
  - メタ行: スコア ／ 生成元 ／ プロンプト版
  - 確からしさのバー（未処理かつ語義でスコアがあるとき。数値は aria-label でも読める）
  - 独立検証のバッジ（裏付けあり・裏付けなし・未実施）＋理由のテキスト
  - 種別ごとの本文（用例は引用のリスト、語義は AI チップ＋定義文＋文脈タグ＋引用、関係は関係種別と手法）
  - 未処理のとき: 「採用」「却下」ボタンと、語義なら「修正して採用…」リンク（モック生成の定義は採用ボタンの代わりに注意文）
  - 処理済みのとき: 処理者と処理日時
- ページ送り（前・次）

### 現状の課題

1. 情報の階層が弱い。1件のカードに見出し・バッジ2種・判定・メタ・確からしさ・独立検証・本文・操作が縦に並び、同じ重さで読まないと全体がつかめない。
2. メタ情報（生成元・プロンプト版・スコア）が本文と同列に置かれ、普段は確認しない情報が視線を止める。
3. 1件あたりの縦幅が大きく、1画面に入る件数が少ない。キューの滞留量を一覧で把握しにくい。
4. 状態での絞り込みはあるが、種別（語義・関係・用例の追加）での絞り込みがない。
5. 位置指定セレクタでボタンを塗り分けているため、モック生成の語義では「却下」ボタンが主操作と同じ青いグラデーションで塗られる。採用ボタンが存在しないため、`.actions form:first-of-type` が却下に当たる。

### テストが保護している文言と挙動

実装時にこれらを変えるとテストが壊れる。

- 「採用」（tests/test_e2e.py:79）
- 「未処理の提案はありません」（tests/test_e2e.py:160）
- 「独立検証：裏付けなし」「用例に定義の後半の根拠が無い」（tests/test_self_improvement.py:120-121。後者は DB 由来の reason 文を hint で表示したもの）
- モック生成の定義は通常の採用を 400 で拒否する（tests/test_e2e.py:81、tests/test_usable.py:122）。「採用」ボタンの出し分けと注意文を維持する
- `/proposals/{id}/edit` の画面に「【モック草案】」を含めない（tests/test_usable.py:123）
- `label()` が返す和名（未処理・採用済み・却下・語義・関係・用例の追加）は画面文言の源であり、文言変更はテストと app.py の LABELS 辞書の両方に影響する

### 既存トーンの維持条件

- 色は style.css の変数経由で扱い、新しい色定義を作らない。ダークモードは `prefers-color-scheme` の自動切替に従う
- 状態表示は色ドット＋テキスト併記（`.badge`）。AI 生成の出自は「AI」チップ＋ title 属性で示す。いずれも CSS のコメントに現行方針として明記してある
- 動きは控えめにし、`prefers-reduced-motion` で止める
- 絵文字は使わない。記号は SVG かテキスト
- 空状態は「見出し＋説明＋次の一手」の3段構成。ここまで出来上がっているため維持する

## 3. 採用する指針（出典付き）

Primer — ActionList Guidelines より:

- リスト項目は「主テキスト＋補助の視覚（leading / trailing）＋補助テキスト」の一貫した1列構成にする。trailing 側は状態や補助情報の置き場所とし、そこに操作の対象を置かない
- 項目の区切り線は、複数行の説明を含む複雑なリストで情報の読み取りを助ける。ただし「本当に読み取りやすくなるか」を確認し、視覚的なノイズを増やすだけにしない
- 破壊的な操作は注意を引く danger スタイルにし、リストの末尾に置く。取り消せない操作には確認を挟む
- 非活性な項目には、なぜ操作できないかの理由テキストを必ず添える

Carbon — Data table より:

- ツールバーは全体に関わる操作（検索・フィルタ・表示設定）の場所とし、操作は5個までに収める
- バッチ操作は、複数項目への同じ操作の反復を1回にまとめる。バッチモード中は行単位の操作を無効化する
- 補足的な情報は展開領域に置く。展開領域が窮屈になるなら、詳細ページへ誘導する
- 行のホバーは、行が対話対象でなくても列の走査に役立つため常に有効にする（現状の `.proposal:hover` と同じ考え方で、既存実装と一致している）
- ソートの矢印はソート中の列だけに表示し、他の列はホバー時のみ出す（terms 一覧の既存実装と同じ考え方）
- AI が生成したデータには、該当するセルにだけインラインの AI ラベルを付ける（現状の ai-chip の出し方と一致している）

Atlassian — Lozenge Usage より:

- lozenge（色付きの強調ラベル）は「対応・判断・理解に影響する重要な属性」＝状態や優先度に使う。分類のための説明的メタデータは tag（無色）に寄せる
- 色だけで重要な属性を示さない。明確なラベルを併記する
- lozenge に長いラベルを使わない。幅の上限で省略され、フォーカスもできないため、省略部分が読めなくなる

## 4. 採用しない指針（部分採用の線引き）

- Carbon の data table をそのまま移植しない。列ヘッダーとチェックボックスによる本格的な表は列に揃ったデータ向きで、提案1件の情報量（定義文・引用・検証結果）に合わない。代わりに、展開領域つきの「行リスト」に寄せる
- Carbon のバッチ展開（全行を一括で開く操作）を採用しない。Carbon 自身が「一括展開は、必要になるまでの取得を遅らせるという展開行の利点を失わせる」と述べており、未処理を順に確認するこの画面の運用でも利点が薄い
- Primer の tooltip による非活性理由の提示を採用しない。キーボードやタッチでは読めないため、理由は既存どおり画面上のテキストで示す
- Atlassian の trailingMetric（lozenge 内への数値の添付）を採用しない。確からしさは既存のバー＋数値のほうが読み取れる
- Atlassian の塗りアイコンによる強調（filled icon）を採用しない。アイコンライブラリを導入しない方針のため
- Carbon の AI label（popover で説明を開く仕組み）を採用しない。外部接続なし・軽量方針のこのアプリでは、既存の「AI」チップ＋ title 属性で足りる。考え方（AI が生成した箇所にだけラベルを付ける）はすでに一致している
- GitHub プルリクエスト一覧の見た目の全面的な移植（サイドバーナビ、アバタースタック、多数のラベル色）をしない。既存のヘッダーと配色変数を壊す根拠がない

|---|---|---|---|
| バッジの役割を2種に分ける。状態（未処理・採用済み・却下）は色付きの lozenge 相当、種別（語義・関係・用例の追加）は無色の tag 相当に格下げする | h2 内の2つの `.badge` | Atlassian（lozenge と tag の使い分け） | 判断に効くのは状態。種別の色ドットを外して視線を状態に集める。文言は `label()` のまま触らない |

## 6. 見送りとその理由

- **テーブル（table 要素）化**: 提案は1件あたりの情報量が多く、1行に収まらない。Carbon の「data table は列に揃ったデータを整理するためのもの」という位置づけに照らすと不適合。行リスト＋展開領域で目的を満たす
- **全行の一括展開**: Carbon が利点を失わせると明記している操作。未処理を順に確認する運用でも必要がない
- **行ホバーの追加対応**: 既に実装済み（`.proposal:hover`）。追加の変更なし
- **ページャーの番号化**: GitHub 風の見た目には近づくが、前・次だけで運用上の不満は出ていない。変更の根拠が薄いので見送る
- **Polaris の badge 指針の採用**: 使用指針ページを取得できず、根拠を示せないため。方針として「根拠を示せない採用はしない」に従う

## 7. 判断が必要な点（実装前の決定事項）

1. **展開領域の既定状態**: 未処理だけ既定で展開するか、すべて閉じておくか。採用の判断には定義文が必要なので、未処理は展開を推奨する（Carbon の「展開領域は補足情報」という位置づけに対し、この画面では定義文が判断の主材料であるため）
2. **プロンプト版の扱い**: 画面から消して title 属性に退避してよいか。監査のために常に見える形で残す運用なら、メタ行に1行残す
3. **種別バッジの無色化の可否**: 視覚的な変化が大きい。色付きのままサイズを下げる折衷案もある
4. **バッチ操作を入れるか**: 未処理の滞留量と運用の実態次第。入れない場合は P3 の該当行を取り下げる
