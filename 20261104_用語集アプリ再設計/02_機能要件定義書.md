# 機能要件定義書 — 社内用語集アプリ再設計

作成: 2026-11-04／作成者: 設計（UI/UX）担当
基準線: `_docs/用語集アプリ_全体改修設計案_20261030.md`（以下「改修案 20261030」）
区分の約束: 「維持」= 現行のまま。「変更」= 現行を改める。「新規」= 追加。「廃止」= 取り去る。
優先度: Must（この設計の成立に必須）／Should（効果が高く、次に作る）／Could（条件が整ったら）／Won't（作らない）。
フェーズ: P1（テンプレート＋CSS＋JS 中心。DB・クエリの変更が最小）／P2（小さなクエリ・表示用集計の追加を含む）／P3（DB 変更または仕様確定を要する）。

---

## 1. 要件の全体像

| 分類 | 件数 | 要件 ID |
|---|---|---|
| 機能要件（維持・変更・新規） | 22 | FR-001〜FR-022 |
| 非機能要件 | 10 | NFR-001〜NFR-010 |

設計の柱（根拠: `01_現状分析.md` §5.2 と `_docs/用語集アプリ_進捗_1002.md` 末尾の UI 改善要請）:
1. **引く速さ** — コマンドパレット・`/` フォーカス・一覧→詳細の共有要素遷移。語を引く操作を最短にする
2. **人の手が見える** — 評価・採用・訂正を朱色で示す視覚言語（詳細は `03_デザイン設計書.md`）。自動と人を区別する既存方針（README「運用の決定事項」）を画面で強化する
3. **手入れの負荷を下げる** — 見直しからの直接評価・健全性ストリップ・ゼロ件検索の登録導線。評価の未実施をためるのではなく、流れの中で処理する

### 2.3 新規の要件

#### FR-004 ゼロ件検索からの登録導線
| 項目 | 内容 |
|---|---|
| 要件 | 検索結果が 0 件のとき、「この語を登録する」のカードを出す。見出しに検索語を事前入力し、用例欄には入力規則の案内を出す。カードは空状態の構造（見出し＋説明＋次の一手）に従う |
| 背景・根拠 | P-02。探したが無かった語は、取り込み候補として最も価値が高い需要の記録。登録の入口を検索の終点に置くことで、用語集が使われる語から育つ |
| 現行との関係 | 新規 |
| 優先度／フェーズ | Must／P1 |
| 受け入れ条件 | ①`/terms?q=存在しない語` でカードが出る ②カードのリンク先 `/new?headword=…` で見出しが事前入力される（現行 `term_new_form` の headword 引数を再利用）③絞り込み 0 件（条件が複数）のときは解除リンクのまま、語としての登録カードは出さない（混同しない） |
| 依存 | FR-001 |

## 4. 優先度別の要約

- **Must（P1 の中心）**: FR-003（一覧の列設計）・FR-004（ゼロ件→登録）・FR-006（キュー裁定。種別絞り込みは P2）・FR-008（見直しの改良＋直接評価）・FR-016（成功帯）・FR-020（健全性ストリップ）・FR-022（採用の来歴）。既存基盤（FR-001/002/007/009/011/014）の維持。
- **Should**: P1 は FR-018（キーボード操作体系とヘルプ）・FR-021（共有要素遷移）。P2 は FR-010（履歴タイムライン）・FR-012（プレビュー）・FR-015（条件付き CSV）・FR-017（パレット）・FR-019（読み一致）。P3 は FR-005（ゼロ件語の累積）。
- **Could（P3）**: FR-013（つながり図）・FR-019 の統合補助・FR-023（改稿案）。
- **Won't**: §2.4 のとおり。
