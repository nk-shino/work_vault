## 1. 運用上限と撤退条件の骨子

起案物: `運用上限と撤退条件_骨子_20261028.md`（§1〜§8＋未確定事項のまとめ）

| 観点 | 内容 |
|---|---|
| What | 指摘の受付運用（検証1-B〜検証3）に上限と終わり方を定める運用文書の起案。節の構成は、受付範囲・重大性基準・滞留時の対応・縮小停止条件・停止後の残件とデータ扱い・相談先の解釈・受付時の安全規定・外部サービスの選定基準の8節 |
| Why | 受付を続けるか止めるかの判断基準を、運用の開始前に文書として残すため。基準がなければ、指摘の量次第で運営者の負担が計画の枠を超えて広がる恐れがある |
| Who | 運営者（ユーザー）が運用する。文書の維持は進行側 |
| When | 採否後、受付の稼働前に「試運転前の確定事項」（相談先の解釈・データ退避先と保存期間・7割閾値の実測値）を確定する。運用中は週あたり処理時間を実測し、閾値を差し替える |
| Where | 保管庫 `00_site-devlops/03_共通と運用/` 配下の運用文書として管理する（対象A・対象Bで共通の骨子。対象Bへの適用は検証3の開始条件とセット） |
| How | 現行の骨子に確定事項を記入して確定版とする。7割閾値は試行の実測値から設定する（Q2回答「内容次第。費用対効果」により、枠の実時間は固定しない） |
| How much | 確定作業は0.5時間程度の推定。運用中の追加負担は週あたり処理時間の記録のみ |

採否で変わること: 採用した場合、検証3などの受付運用の停止条件はこの文書に従う。不採用の場合、受付運用の縮小・停止の基準が文書として存在しない状態になるため、検証3の開始条件④（観測項目と判断条件の対応表の作成）を満たす時点で、別の基準を用意する必要がある。

## 2. 提案キュー役割整理（接続方式を含む）

起案物: `提案キュー役割整理_提案_20261028.md`（役割分担表＋接続方式5項目）

| 観点 | 内容 |
|---|---|
| What | 既存の提案キュー（出所は llm・statistics・manual の3種。実測済み）と、新設する閲覧者指摘経路の役割分担。接続方式の5項目は、①受付は別経路とする ②起因タグ `reader` を追加する ③起因が `reader` の提案は自動受理しない（運営者の確認を必須とする） ④集計は起因別に分ける ⑤重複・却下の規則は既存キューに従う |
| Why | 台帳Q3の回答「検討中。提案待ち」に対する提案である。閲覧者経路を既存キューに混ぜると二重管理の恐れがあり、この回避は接続方式の定義の後に行える主張である（評価: 運営者・計画§1） |
| Who | 対象A（用語集・社内）はアプリ内の報告経路から起因 `reader` で直接記録する。対象B（資料サイト・公開）は運営者が確認のうえ手動で記録する |
| When | 実装は形式段階（経路の実現方式の比較検討）以降であり、本提案の採否と台帳A-06（機能的提案・A-04採否後）が確定してから着手する。現時点でコードは変更しない |
| Where | 受付の経路は1本、キューへの記録も1本。対象Aはアプリ内、対象Bは報告経路（検証3の開始条件の充足後） |
| How | 起因タグで処理規則の差を明示する。閲覧者由来の扱い（自動受理しない・確認必須）だけを新たに明文化し、他の規則は既存キューのものに従う |
| How much | 実装コストは形式段階の設計が終わるまで見積もれない（未確定）。運用の追加負担は、起因別集計の分類だけである（推定・小さい） |
