## 2. 各候補の実装要点

### P2#5 キューの一括採用/却下
- 選択: 未処理の提案カードの左端にチェックボックス。HTML の `form` 属性で画面下端の選択バーに属させるので、JS が無くても送信できる
- 選択バー: 件数表示（aria-live）・「このページをすべて選択」（JS のみ）・採用と却下の2ボタン。チェック0件では JS がバーを隠す。JS が無い場合は常に見えていて、0件のまま押すとサーバーが理由の帯を出して一覧へ戻す
- API: `POST /proposals/bulk`。引数は `action`（accept/reject）・`ids`（複数）・`status`・`page`。処理後は元の絞り込みとページへ戻る（隠し項目で引き継ぐ）
- 扱いは全部か無しか: 1件でも失敗したらコミットせず全件を無効にして戻す。部分的に採用されて「どれが通ったか分からない」状態を作らない
- モック草案を含む選択では、JS がバーに警告を出す（サーバー側の強制は下記 §4）

### P2#6 一覧行の展開で語義プレビュー
- 見出しセルのリンクの右に details/summary の開閉部品。展開すると最初の語義の冒頭（100字で打ち切り）を明朝体で表示する。詳細画面の定義と同じ組版を小さめにした
- 対象は却下済みを除く語義。語義が無い語には開閉部品を出さない。語義が複数ある語は「ほかの語義 N 件」も出す
- `list_terms` がページ内の語について1回の追加問い合わせで集める（N+1 にはしない）

### P3#7 表の密度切替
- 一覧の件数行の右に「行を狭く」ボタン（`aria-pressed` の切替ボタン）。`table.compact` でセルの余白を詰める。文字の大きさは変えない
- 状態は localStorage（`glossary-density`）に保存する。表示だけの好みなので URL には載せない（全リンクへの密度引数の付替えを避けた）
- JS が無いときはボタン自体が出ない（`.js-only`）。既定は普段の行高

### P3#8 キーボードトリアージ
- `j`/`k` で提案カードの間を移動する（端で止まる。ループはしない）。`a` で採用、`r` で却下、`x` で一括処理のチェック切替
- 移動はカード（`tabindex="-1"`）へフォーカスを移す方式。Tab の順序は変わらない
- `a`/`r` は各カードが既に持つ採用・却下フォームを `requestSubmit()` で送るだけ。フォームが存在しない提案（モック草案・処理済み）では送らず、ライブリージョンで理由を読み上げる
- 入力欄・ボタン・リンクにフォーカスがあるときは全キーを無視する
- 操作案内（kbd 付きの1行）は JS があるときだけ表示する

### 実証済みパターン（vba-glossary-tool 2026-10-29 実証分）
- 数値入りバッジ: ナビの提案キューに未処理の件数を表示。`render()` が全ページで1問い合わせ件数を渡す。0件では非表示
- `:focus-visible` の統一フォーカスリング: 既存実装（`2px solid var(--accent)` + offset 2px）で充足していた。新規のチェックボックス・summary・ボタンも同じ規則に乗る。追加コードは不要だった
- 空状態の「タイトル＋次の操作」統一: 一覧とキューは既存実装で構造化済み。残っていた見直し画面と詳細の関連語を「見出し＋説明」に揃えた。空状態ブロックは中央揃えから左揃えに変更（Carbon の指針。vba と同じ形）
- 絞り込み0件時の空状態ブロック: 一覧・キューとも既存実装で充足（解除リンク付き）。変更なし
- 保留チップ赤→黄: 本アプリでの該当要素は提案の `st-pending` バッジ（現状は中性のグレー）。vba と同じ注意黄（warn 系）に変更した。「保留＝対応待ち」の意味づけで、赤は破壊的な操作（却下ボタンのホバー等）専用に保つ

## 3. proposal_accept 保護検査との両立方式（設計判断・必須項目）

現行の保護: 単独採用の入口（`web/app.py` の `proposal_accept`）が「語義の提案で生成元がモック」を検査し、`ValidationFailed`（400）にする。「修正して採用」（`/proposals/{pid}/edit`）は人が定義を書く経路なので対象外（モックの文は編集フォームに空で出す）。

今回の判断:

1. 保護検査を web 層の `_is_protected_mock()` に共通化し、単独採用と一括採用の両方が同じ関数を通る
2. 一括採用では事前検査で保護対象を数え、1件でも含まれていれば採用を開始しない。エラー種別 `mock` と件数を付けた URL で一覧へ戻し、帯で「修正して採用を使う」ことを案内する
3. 層の根拠: モック定義の扱いは「画面から確定させない」という画面側の決め（app.py 冒頭の注記）なので、ドメインの `accept()` には入れなかった。ドメインに入れると `test_e2e` がドメイン経由でモック提案を直接採用している箇所（前処理〜採用の通し確認）と衝突し、テスト変更が必要になる
4. 強制はサーバー側だけが担う。画面の `data-protected` 属性と JS の警告は補助にすぎない。キーボードの `a` も、モック草案のカードには採用フォームが存在しないため送れない
5. ドメインの `accept_many` は各提案を `accept()` の未処理検査に通すので、誰が呼んでも処理済み提案の再採用は起きない。失敗時は例外で抜け、呼び出し側がコミットしないため全体が無効になる

未確定のまま残る点: 将来 CLI や自動判定から `accept_many` を直接呼ぶ実装者が、モック保護を知らない可能性がある。ドメイン層への移動は上記3のテスト変更を伴うため今回はしない。この節を次の実装者の参照先とする。

## 4. a11y 確認内容

- キーボードトラップ: 無し。j/k/a/r/x は補助で、Tab と Shift+Tab の順序は不変。入力欄・ボタン・リンクではキーを無視する。Escape を要るモーダルは無い
- フォーカスの可視性: 全操作要素に既存の `:focus-visible` 輪郭。j/k で移動したカードはキーボード由来のフォーカスなので輪郭が出る（Safari はプログラム的フォーカスで輪郭を出さない heuristic があるため、`kcursor` で枠の色と影も変えている）。輪郭と cursor 表示の二重示唆
- ラベルと id: 追加のチェックボックスは行ごとに一意の id と label（`sr-only` で「この提案を選択」）。`test_all_inputs_have_labels` の条件（id 必須・id 重複禁止・label 対応・hidden 除外）を満たすように実装した
- ライブリージョン: 選択件数・モック警告・j/k の移動先（見出し語と位置）を `aria-live="polite"`＋`role="status"` で通知
- 開閉部品: 語義プレビューはネイティブの details/summary（開閉状態が支援技術へ伝わる）。summary 内の矢印は `aria-hidden`、名称は sr-only テキスト。密度切替は `aria-pressed`
- 色だけに頼らない表示: 保留チップは文字＋点。モック草案は hint 文と data-protected（読み上げ用）の両方。数値バッジはリンクの文字列に件数が続く
- reduced-motion: 追加した transition は既存の全停止規則で止まる。新規のアニメーションは無い
- 操作の代替経路: すべての操作はボタン・リンク・フォームで直接可能（キーボードショートカットが無くても成立する）

## 5. 懸念（テスト・確認時に見る場所）

1. `test_all_inputs_have_labels`（/terms と /proposals）: /proposals に行ごとのチェックボックス（id＋label）とバー関係の id を追加した。id 重複が無いことは確認したが、このテストが落ちたら最初にここを見ること
2. `/proposals/bulk` のフォーム解釈: `ids: list[str] | None` の `Form()` は python-multipart 依存。既存の実装も Form を使うため環境差は無いはずだが、422 が出たらフィールド名（`ids`・`action`・`status`・`page`）を確認すること
3. 既存文言の保持: 「未処理の提案はありません」「条件に合う用語がありません」「採用」等のテストが見る文字列は変更していない。空状態の左揃え化はスタイルのみ
4. プレビュー展開時の表の再配置: 展開すると1列目が広がり表全体が流れ直る。行を跨ぐ展開行はサーバーレンダリングでは details/summary しか手段が無く（調査まとめの案どおり）、JS を使う方法は今回は採らなかった。実画面で気になる場合は次段で検討する
5. `render()` の追加問い合わせ: 全ページで未処理件数を数える（1問い合わせ）。SQLite 手元では負担は無視できる範囲。DB を分離するときに見直す
6. density の保存先: localStorage のため別端末・シークレットウィンドウでは引き継がれない。仕様として許容
7. キー割付: j/k は慣習どおり。a/r/x は GitHub・Linear の慣習に寄せたが、この割付自体はユーザー確認の対象（変更は app.js の1箇所と案内1行）
8. 実画面での未確認事項: 実キーボードでの j/k 操作・スクリーンリーダーの読み上げ・ダークモードでの新規要素（黄チップ・バッジ・選択バー）の見え方は、オーケストレータの実画面検証で確認する
