## Part A: 本体への小改修（2件）

作業場所: `C:\work\用語集アプリ`（実行コピーのみ。正本は触っていない）

### A1. 一括処理のエラー帯 — ドメインの規則で拒まれた理由をそのまま出す

**経緯**: 検証で、関係提案の一括採用がドメインの規則（関係の採用には両端の語義の採用が要る）で拒まれたとき、帯が「処理済みのものが混ざっているか、先に他で処理された」（`error=stale` の文）になり、実際の原因と合っていないことが分かった。

**変更**:

- `web/app.py`（`POST /proposals/bulk`）: 途中の `except DomainError` を `error=stale` ではなく `error=rule&reason=<理由の文>` で戻す。reason は `str(e).strip()` を 200 字で打ち切り、`urlencode` で渡す（Jinja の自動エスケープで帯に出る）。文はドメイン層が生成したものをそのまま使う（例: 「関係の両端の語に、先に語義を採用しておく必要がある」）。docstring も実態どおりに更新
- `templates/proposals.html`: 帯に `rule` の分岐を追加。「選択した提案の処理を中止しました。1件も変更していません。理由: （reason）」。reason が無い場合（手で URL を作った場合など）の代替文も用意
- 役割の分担は変えていない。事前検査（選択と取得の不一致・処理済み混在）は従来どおり `error=stale`。`error=mock&n=`・`error=empty`・`error=invalid` もそのまま。途中失敗の原因が競合（処理済み）のときもドメインの文（「この提案は処理済み（accepted）」等）が帯に出るが、これは文自体が自己説明的なので許容とした

**テスト**: `tests/test_usable.py` に `test_bulk_rule_violation_reports_the_reason` を1件追加（154 → 155件）。関係提案を1件だけ一括採用し、リダイレクト先の query が `error=rule` で reason に「先に語義を採用」を含むこと・帯の文が画面に出ること・提案が未処理のまま（全部か無しか）を確認。**pytest は未実行**（オーケストレータが実行する段取りのため）。ファイルの構文コンパイルのみ確認済み

### A2. 選択バーの表示位置 — fixed を sticky に替えて一覧の上に置く

**経緯**: 検証のスクリーンショットで、チェックを付けても選択バーが視界に入らない（一覧の下・折り返し以降に落ちる）ことが分かった。

**原因**: `main` に登場アニメーション（`animation: rise .28s ease-out both`）があり、fill-mode `both` が最終キーフレームの `transform` を要素の寿命の間ずっと残す。transform が残る要素は `position: fixed` の子孫の基準位置（包含ブロック）になるため、バーの `fixed; bottom: 1rem` がビューポートでなく `main` の下端を基準に計算され、一覧の下に置かれていた。仕様どおりの挙動で、ブラウザの不具合ではない（CSS Transforms の仕様と実装の確認済み）。

**変更**:

- `templates/proposals.html`: 選択バーのフォームを一覧の後ろ（ページャーの後）から一覧の直前（空状態ブロックの後）へ移動。中身（hidden の status/page・件数・全選択・採用・却下・モック警告）は変えていない
- `static/style.css`: `.bulk-bar` を `position: fixed` から `position: sticky; top: 3.2rem; z-index: 4` へ。`left/bottom/transform/min-width` は削除し幅は流れに任せる。sticky は包含ブロックの影響を受けないので、今後 `main` のアニメーションを変えても壊れない
- `top: 3.2rem` の根拠: ヘッダー（sticky, z-index 5）の高さが約 3.2rem。バーをヘッダーの下端にぴたりと付けて張り付かせる。z-index はヘッダーの下（5 未満）にし、狭い画面でナビが折り返してヘッダーが伸びてもバーの上端がヘッダーの下に隠れるだけで、隙間は開かない
- `app.js` は無変更。チェック 0 件でバーを隠す挙動・aria-live の件数・全選択ボタンはそのまま。JS が無い環境ではバーが流れの中に常に見える（以前の fixed と同じ性質）

**確認ポイント（実画面検証で）**: 一覧の上部でチェックを付けたとき、バーがヘッダーの下端に張り付いて見えること。狭い幅（900px 未満）でヘッダーが2段になったとき、バーがヘッダーに少し食い込んで見えること（不具合ではなく、隙間を出さないための取り方）

## Part B: モックアップ 第2段（採否判断用）

成果物: `20261030_用語集アプリ全面改修\mock_第2段\モックアップ_第2段.html`（単一ファイル・CDN 無し・日本語 UI・明暗両対応）

**作り方の方針**: 20261021 モックアップのデザイン言語（配色・Yu Gothic UI + Yu Mincho・radius/shadow・帯と上部バーの構え）を踏襲し、**現在の本体（第1段反映後）の画面に提案要素を1つずつ重ねた**。旧モックアップは当時の統計や画面構成のままなので、そのまま見せると「変更の差分」と「画面の差分」が混ざって採否の邪魔になるため。上部のタブで案1〜案4を切り替え、右上で明るさを自動（OS 追従）／明／暗に切り替えられる。各案の画面の上に「意図・実装イメージ・注意」の短い説明を置き、判断の材料を画面の中に添えた。データは架空のもの（卵温計・竜舎・FLT点検等、これまでの資料と同じ世界の語）。

### 案1 トースト通知

- 意図: 1件ずつの採用・却下で「今の操作が今通った」を残す。キーボード（a/r）でも同じ文を出す想定
- 見せ方: 現行の提案キュー（チェックボックス・選択バー・メーター・AIチップ付き）を再現し、採用・却下ボタンを押すと右下に通知。カードは処理済みの見え方に変わる。「通知をもう一度見る」ボタン付き
- 設計判断: 位置は本体の「処理中…」表示と同じ右下。処理中 → 完了で同じ場所が入れ替わる連続性を狙う。形状は旧モックアップと同じ黒いピル型（1行・2.2秒）。採用と却下で色を変えない（色は状態表示に取ってあり、通知は文で伝える）
- 注意: 実装はサーバーレンダリングを前提にすると「戻り先の URL に結果を載せて通知を出す」方式になる（単独操作は既にエラー帯があるので、成功時の追加）

### 案2 カウントアップ統計カード

- 意図: 統計4枚の数値に目が行くようにする飾り
- 重要な前提: **本体には簡易版（0.5秒）が既に入っている**（第1段の実装時点で）。この案の採否の軸は「有無」ではなく「時間と減速を強めるか・現行のままでよいか」。そのため0.5秒（現行）と0.9秒（提案）を切り替えて比べられるようにした
- 実装の性質: 数値は HTML 直書きで JS が無くても正しい数が出る（本体と同じ）。OS の「動きを減らす」設定では上げずに即座に出す

### 案3 ミニグラフ

- 意図: 「増えている・減っている」をひと目で伝える。折れ線は直近7日、右端の丸は今日、「先週比」で正確な増減を添える
- 設計判断: 折れ線の色は1色（濃（濃紺）に絞った。旧モックアップは統計ごとに色を変えていたが、本体の色の使い方（色は状態の意味に使う）に合わせる。折れ線の高さはカード内比較のみ（軸の共有はしない）とし、誇張の議論を避ける
- 注意: **4案の中で実装の負担が最も大きい**。本体には日ごとの履歴がなく、日次の記録（取り込み時に1日1回数値を控える）が前提。採否では「履歴を取り始める価値があるか」も含めて見てほしい

### 案4 左サイドバー

- 意図: 項目の現在位置と未処理の件数が常に見えるナビ。使う項目は現行の5つから変えず、グループ名（さがす・処理する・ふやす）で意味ごとに束ねた
- 第1段で不採用だった経緯（横幅の圧迫）を踏まえ、幅を 204px に絞り、中身の最大幅は変えない構えで再提案。900px 未満では隠して現行の上部ナビに戻す（開閉操作の詳細は本体設計時に別途）。フッターの「外部接続なし・このPCの中だけ」は現行の安心表示を縦置きにしたもの
- 数値バッジ（提案キュー 23・見直し 13）は第1段で入れた本体の部品をそのまま縦置きにした
