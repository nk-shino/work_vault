# 共有フォルダ ファイル台帳クローラー 仕様書

作成日 2026-09-11  
版数 初版（全件版）

* 修正事項：業務統括部Cloud\_棚卸関連、VX\_棚卸関連、CDX統括部情報システム部\_在庫Sim など \[1]

などは、会社全体および事業部ごとのものと考えられる。今回は実装技術課、生産技術課など富岡工場に範囲を絞る。そのうえで棚卸に限定することはない。

## このツールが何をするか

社内共有フォルダを一日ごとに走査し、そこにあるファイルのメタデータをCSVに書き出す。どんなデータがどこにあるか、どれが生きていてどれが放置されているかを機械的に把握するのが狙い。用途は棚卸に限らず、データ整理の下地、単語集づくり、ファイルの所在調査、佐藤さんの業務引き継ぎの手がかりなど幅広く使う。手順や存在理由が不明なファイルが多いため、まず全体像を掴む。
棚卸の共有はあくまで走査対象の一部であって、このデータの目的そのものではない。集めた台帳は横断的に使い回す前提で設計する。

## 動作の大前提

読み取りしかしない。ファイルの列挙とプロパティ読み取りだけを行い、書き込み・移動・削除・コピー・属性変更のコマンドは一切使わない。対象フォルダには触れず、出力先はこのPCのローカルに固定する。
出力は上書きしない。実行のたびに実行時刻を付けた新しいCSVを作る。過去分を残すので、日ごとの差分やアクティブ状態の推移をあとから追える。

## 決定した運用条件

* 実行はこのPC。タスクスケジューラで一日ごとに回す。夜間か始業前を想定。
* 走査は全件。まずどれだけ使われているかを調べる調査フェーズなので、対象を絞らず全部を見る。
* 走査時間は20分程度まで許容する。これを超えそうなら対象の絞り込みを検討する。
* 作成者と最終更新者まで取る。ファイルシステムの所有者だけでなく、Officeファイル内部の作成者・前回保存者も読む。
* 初版は全件版を先に作る。アクティブや更新分の抽出は、全件データが揃ってから次版で足す。



## クロール対象

過去の件数調査で判明した共有構成を反映する。サーバー名だけの指定では共有を展開できず0件になるため、共有名までパスに含める \[1]。

* nksv1359 share / WWW
* nksv569 Share / WWW
* nksv523 Backup / LOG
* nksv250 共有が数百件あるため丸ごとは対象外。棚卸に関わる共有だけに絞る。業務統括部Cloud\_棚卸関連、VX\_棚卸関連、CDX統括部情報システム部\_在庫Sim など \[1]
* ローカルの C:\\Users\\ss80751\\NK \[1]



棚卸系の共有は対象の一部にすぎない。目的が棚卸に限らない以上、この全件走査でどこがどれだけ使われているかを見たうえで、必要な共有を足し引きして対象を確定する。今の版はまず全部を舐める。
569は旧式でDGS-SVまで絞って走査していたサーバーで、共有の中身が大きい可能性がある。丸ごと含めると走査対象が増えるため、時間が延びる点は見込んでおく \[1]。

## 取得する列

ファイルシステムから軽く取れる項目を基本列にする \[1]。

* SourceShare 走査起点の共有パス
* Name ファイル名
* Extension 拡張子
* LastWriteTime 更新日時
* DaysOld 現在との差分日数。アクティブ判定の材料
* DirectoryName 置かれているフォルダのパス
* Length サイズのバイト数
* SizeMB サイズのMB換算
* ScanTimestamp 走査した時刻。履歴管理用



出力は LastWriteTime の降順で並べ、Export-Csv で書き出す \[1]。

## 作成者・最終更新者の扱い

ファイルシステムからは、誰が更新したか誰が作ったかを確実には取れない。Get-ChildItem が返すのはファイル名・更新日時・パス・サイズで、人の情報は含まない。NTFSが持つのは日時の属性であって人ではない \[1]。
取れる範囲は次の通り。

* 所有者。Get-Acl でファイルのOwnerを読める。ただし所有者は作った人とは限らず、共有へコピーした時点で変わることもある。nksv1359やnksv569はSambaサーバーで、Windowsアカウントとの対応がずれてSID表記や意図しない値になることがある。さらにGet-Aclを一件ずつ呼ぶと走査が大幅に遅くなるため、全件で回すと20分に収まらないおそれがある \[1]。
* Officeファイル内部のプロパティ。xlsx・xlsm・docx などは中に作成者と最終更新者を持つ。ファイルのプロパティで見える作成者・前回保存者がこれにあたる。ただし中身の情報なので手で書き換えられる場合があり、正確とは限らない。読むには一件ずつ開くので件数が多いと時間がかかる \[1]。
* 監査ログ。誰がいつ変更したかを本当に追うにはサーバー側で事前に監査を有効にしておく必要があり、あとから走査しても取れない \[1]。



作成者・最終更新者まで必要という要望に対しては、次の設計にする。基本列の全件走査を先に完成させる。そのうえで作成者・更新者は、内部プロパティを持つOffice系拡張子に対象を絞って読む。全件へGet-Aclを掛けると時間が破綻するため、所有者列は必要なフォルダに絞るか二段階目に回す。20分の枠を守るため、重い処理は対象を限定する。

## 文字コード

CSVをUTF8で出すとExcelで文字化けする。Shift-JISで出す。Windows PowerShell 5.1なら Export-Csv の -Encoding Default がShift-JISになる。PowerShell 7系ではDefaultがUTF-8の意味に変わっているため化けが直らない。7系なら -Encoding oem を使うか、コードページ932を明示指定する \[1]。
自分の環境がどちらかは $PSVersionTable.PSVersion で確認する。先頭が5なら Default でよい \[1]。

## エラーの扱い

サーバー丸ごとを走査すると、アクセス拒否が出る共有がある。今の作りは -ErrorAction SilentlyContinue で握りつぶすため、どこで拒否されたかは記録に残らない。あとで拒否箇所を把握したいなら、-ErrorVariable でエラーを別途拾ってログに出す作りに変える \[1]。
nksv250と523は共有が多く、コンソールでは一覧が見切れる。net view の結果をテキストに書き出して落ち着いて確認する \[1]。

## 履歴の積み上げ

出力ファイル名は inventory\_YYYYMMDD\_HHmmss.csv のように実行時刻を付ける。上書きせず日ごとに積み上がる。放置すると増え続けるため、古い分の退避方針は運用しながら決める。

## 段階計画

1. 基本列の全件版を作り、まず全体を舐めて件数と所要時間を測る。ここで20分に収まるか、どこが活発かを見る。
2. 全件データをもとにクロール対象を確定する。棚卸に限らず必要な共有を足し引きする。
3. 作成者・最終更新者を、Office系拡張子に絞って読む処理を足す。
4. アクティブ判定と更新分の抽出を足す。しきい値の日数は全件の分布を見てから決める。



## 実行手順

スクリプトは `06_Tools\crawl_inventory.ps1`。**社内ネットワークからのみ実行できる。**

```
powershell -NoProfile -ExecutionPolicy Bypass -File "06_Tools\crawl_inventory.ps1"
```

初回は**タスクスケジューラに登録せず、手で1回**流す。走査時間と件数を測るのが目的で、
20分を超えるかどうかがクロール対象を絞るかどうかの判断材料になるため。

### 実行前に確認すること

- [ ] 共有名までパスに含まれているか。**サーバー名だけでは0件になる**
- [ ] 出力先のディスクに空きがあるか。全件走査のCSVは数十MBになりうる
- [ ] 夜間か始業前か。日中に流すと共有の応答が遅くなる可能性がある

### 実行中に止まったら

**件数が想定より少ない場合、まず走査方法を疑う。**
.NET の `EnumerateFiles` は途中のディレクトリでアクセス拒否が出ると
**残り全部を黙って捨てる。** `IgnoreInaccessible` でも防げない。
本スクリプトは Stack による自前再帰でディレクトリ単位に try/catch しているが、
それでも件数が落ちたときは、スキップされたディレクトリのログを先に見る。

## 出力の読み方

CSVが出たら、次の順で見る。**この4つを見れば未確定事項が全部決まる。**

| 見るもの | 出し方 | 何が決まるか |
| --- | --- | --- |
| 総件数と走査時間 | スクリプトの出力 | 20分以内か。超えたら対象を絞る |
| `DaysOld` の分布 | 30 / 90 / 180 / 365 日で区切って件数を数える | **アクティブの基準日数**。件数が急に落ちるところが境目 |
| `SourceShare` 別の件数とサイズ | SourceShare でグループ化 | **nksv250 で含める共有**。件数が極端に少ない共有は外す |
| 所有者列の取得にかかった時間 | 基本列のみの走査時間との差 | **所有者列を全件で取るか絞るか** |

### 基準日数の決め方

分布を見て決める、とだけ書くと決まらないので判定規則を置く。

**`DaysOld` を昇順に並べ、累積件数が全体の80%に達する日数を基準にする。**
その日数より新しいものをアクティブとする。
理由は、8割が収まる範囲を「現役」とみなすと、残り2割が見直し候補として
手に負える量になるため。80%で切った結果が極端（30日未満、または3年超）に
なった場合だけ、分布の形を見て手で調整する。

## 未確定事項

**すべて初回走査で決まる。** 実行前に決める必要はない。

| 項目 | 決め方 | 決まる時期 |
| --- | --- | --- |
| アクティブ／非アクティブの基準日数 | `DaysOld` の累積80%地点（上記） | 初回走査の直後 |
| nksv250 で対象に含める共有の最終リスト | SourceShare 別の件数とサイズを見て足し引き | 初回走査の直後 |
| 所有者列を全件で取るか絞るか | 走査時間が20分を超えるかで判断。超えるならOffice系拡張子に絞る | 初回走査の直後 |
| 古いCSVの保管と退避のルール | 1回のCSVサイズが分かってから。**世代数×サイズがディスクに収まる範囲**で決める | 初回走査の直後 |

**4件とも「測る前に決められない」ものであって、検討が止まっているわけではない。**
初回を1回流せば全部埋まる。
