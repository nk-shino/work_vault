# forced-logging（記録の確実化）

## 記録ルール

- **指示1件 = 実行ログ1エントリ**。
  置き場所: `YYYYMMDD_<topic>/実行ログ_YYYYMMDD.md`（ワークスペース配下）
  形式: `## エントリN: <題名>` → 指示 / 実施 / 成果物 / 状態（コミット番号を含む）
- 既存の日のログがあればそこに追記する。無ければ新規作成する
- 失敗（問題・バグ・エラー）は解決の成否にかかわらず
  `.learnings/ERRORS.md` に記録する
  （形式: `[ERR-YYYYMMDD-XXX] 概要` + 発生コマンド/状況 + 解決法 + Pattern-Key）
- Work_Vault 配下の成果物は保管庫側の運用（rules.md）にも従う
  （vault-change-and-report スキルが担当）

## 検証手順（完了宣言の前に実行）

1. **ログエントリの存在確認**:

```bash
grep -l "<今回の指示に対応する題名やキーワード>" YYYYMMDD_<topic>/実行ログ_YYYYMMDD.md
```

2. なければ**先にログを書く**。完了報告はその後に行う
3. エントリの不足（指示/実施/成果物/状態の欠落）があれば補完する
4. 失敗があったセッションなら `.learnings/ERRORS.md` のエントリも確認する
   （解決済みなら Status: resolved と解決法の追記まで済ませる）

## ゲート

- **ログ未記載のまま完了報告・コミットをしない**
- 報告には検証結果（確認したファイルと、その中の該当箇所）を含める
- コミット前に `git status` で、ログファイルがステージ対象に入っているかを確認する

## 失敗パターンキー

`logging.missing-entry`（ログ未記載のまま完了報告）。
発生時は `.learnings/ERRORS.md` に記録する。
