# vault-change-and-report

## 起動条件

- 00_inbox に新規ノートが追加された後の整理
- タスク完了後の記録・日報作成
- 仕様変更に伴う既存ノートの更新
- フォルダの新規作成・リネーム・再分類
- **業務保管庫内のフォルダ変更(作成・移動・改名・廃止)のとき**
- **成果物(報告書・計画書・スクリプト・検証記録など)を作成したとき。作ったまま保管庫に入れないと埋もれるため、成果物の作成時点でこのスキルを起動し保管庫への登録までを行う**

## 保管庫の構成(既定)

- 業務用: Work_vault / 日常用: Zettelkasten
- 受付領域: 00_inbox
- タスク管理: Todo.md
- 旧資料退避先: 99_archive
- 開発・運用・保守・整理はフォルダで区分
- **運用ルールの正本は `Work_Vault/_system/rules.md`。フォルダ変更・成果物登録の判断はこのルールに従う**

## 成果物の登録ルール(rules.md に沿う)

1. **分類判定**は rules.md §5 の順で行う:
   - 特定案件に属する成果物 → その案件のフォルダ(例: `10_業務全般/PanaCIM_LNB/LNB_Collector/`)
   - 業務の汎用ナレッジ → `10_業務全般/`
   - 複数ステップ・期限ありの案件タスク → `05_Tasks/`
   - 判定不能 → 移動せず `pending.md` に記録して質問する
2. **置きっぱなしを作らない**: 成果物は作成時に正しい置き場へ入れる。「あとで見る置き場」(inboxへの一時置きの常態化)を作らない
3. **命名**: rules.md §2「命名規約」(v1.3・2026-10-20 制定) に従う。最優先は同一フォルダの既存資料の様式。原典資料・自動生成ファイルは改名しない
4. **フロントマター**: rules.md §3 の様式(type/phase/status/project/updated)を付与する。Tier A なので承認不要
5. **削除は勝手にしない**: 旧版は 99_archive へ退避(Tier B、承認を得る)。削除も Tier B
6. **記録**: 成果物の追加・更新・削除は `decision-log.md` へ1行(Tier A)、フォルダ変更(Tier B/C)は `02-2_Weekly/changelog/YYYY-MM-DD_changelog.md` へ記録
7. **絵文字を使用しない**。生成ツールの痕跡を本文に残さない

## 手順

1. **範囲確認**: 対象Vaultと既存分類を確認する。操作範囲を先に決めてから動く。
2. **正本の整理**: 正本・重複・旧版・参照関係を確認する。内容と適用条件で判断し、ファイル名や日時だけに依存しない。
3. **影響確認**: 移動・改名前に、内部リンク・埋め込みへの影響を確認する。Obsidianのリンク解決を壊さない。
4. **削除と退避の区別**: 削除は勝手にしない。旧版は 99_archive へ退避する。仕様書の自動更新範囲が不明なら本人に確認する。
5. **記録の更新**:
   - 変更内容を一枚の変更記録ノートにまとめる(何を・なぜ・どこへ)
   - 日報を更新する

## 日報テンプレート

- 狙い
- 実施内容
- 結果
- 成果物
- 確定・保留事項
- 課題
- 次の行動

## 注意

- AIっぽい定型表現を避け、具体的な日本語で書く
- 確定事項と保留事項を混ぜない
