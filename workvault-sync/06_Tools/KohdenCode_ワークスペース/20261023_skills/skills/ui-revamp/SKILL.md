# リファレンスに基づくUI改修（部分採用）

既存の画面を、根拠のある指針に照らして改善する。重要な制約は「部分採用」である。参照先のデザインを丸ごと真似ると、その製品の文脈（情報量・利用者・運用）が違うため壊れる。取る部分と取らない部分を明示し、根拠を文書に残す。

## 原則

- **部分採用**: どの指針を採用し、何を採用しないかを必ず文書に残す。完全な模倣はしない（依頼で明示されることが多い）
- **根拠は一次資料**: 公式デザインシステムの usage／使用指針ページだけを根拠にする。ブログ記事、ランディングページ、APIリファレンス、ナビゲーションだけの取得結果は根拠にしない。使用指針が公開範囲に無いシステムは候補から外す。根拠を示せない採用は、後から検証できない
- **既存のトーンを維持**: 対象アプリに既にある配色変数・余白のリズム・文言のトーンを壊さない。色は既存のCSS変数経由で扱い、ダークモードがあるなら自動追従させる。絵文字は使わずSVGかテキストで示す
- **状態は色だけで示さない**: 状態表示はテキスト併記が前提。生成物の出自（AI生成／人手）を誤って表示しない

## 手順

### 1. 現状把握

対象画面の構成要素を列挙する（コンポーネント・文言・空状態・操作）。テストコードが検査している文字列を先に調べる。文言は画面の意味を保つ根拠であり、気づきで変えるとテストが壊れる。

### 2. 一次資料の収集

- Atlassian Design System、Carbon Design System など、usage ページが公開されているシステムから2〜4件選ぶ
- ページ取得には抽出プロンプトを添える。ナビやAPIリファレンスだけ返ってきたら1回だけ再試行し、それでも駄目ならそのシステムは打ち切る。無理に既知知識で補わない
- 各システムから「採用する指針」と「採用しない指針」を摘出する

### 3. 調査まとめの作成

`YYYYMMDD_<topic>/調査まとめ.md` に書く。項目:

- 参照した一次資料の表（システム・参照箇所・URL）
- 各資料から採用する指針（箇条書き、出典を添える）
- 適用候補の表: 候補／適用先／出典／備考。P1（小さな変更で効く）・P2（実装コスト中）・P3（大きい・後回し）に分ける
- 見送りとその理由。実装しない判断も根拠を残す
- 判断が必要な点。実装前にユーザーの決定が必要な設計上の分岐を明示する

### 4. 範囲の合意

調査まとめを提示し、question ツールで実装範囲を聞く（P1のみ／P1+P2／特定項目のみ／保留）。「判断が必要な点」の答えもここで得る。

### 5. 実装

- UI/UX の設計判断を含むなら @designer に委任する。機械的な後追いだけなら @fixer でよい。委任プロンプトには、変更対象ファイル、既存トーンの維持条件、テストが保護する文言、検証コマンドを明記する
- 完了条件は、既存のテスト・lint・型検査がすべて通ること

### 6. 検証

- 自動テスト全通過に加え、実画面で確認する。ブラウザツールでスクリーンショットを保存する。**ライトとダーク両方**、追加した機能の状態（ソート中の列、空状態、新ラベル等）を見る。HTMLテキストの確認では崩れや色の破綻は分からない
- 追加・改修した機能の主要な操作経路（クリック・キー操作）を実際に実行して確認する。同じ箇所に複数の操作経路があると、片方だけの実装漏れが起きる。スクリプトの目視点検では操作経路の欠落は分からない
- デモ用データやスクラッチ環境を使ったら後始末（サーバー停止、一時DB削除）まで行う

### 7. 記録と同期

- 実行ログ（`YYYYMMDD_<topic>/実行ログ_YYYYMMDD.md`）に指示1件＝エントリ1件で追記する
- コミットは自分のトピックフォルダだけ add する。並行セッションの変更を巻き込まない
- 正本が Vault にある運用なら、実行コピーから反映し、vault-sync スキルの手順で同期する。同期後は追跡に入ったことを検証する

## よくある失敗

- 公式サイトのページ取得がナビゲーションやAPIリファレンスだけを返す → 抽出プロンプトを添える。2回取れないなら打ち切り、そのシステムは「見送り」に記す
- 参照先の見た目をそのまま移植する（サイドバー、コマンドパレット等）→ 文脈が違うため失敗しやすい。採用／不採用の表で意図的に防ぐ
- 色だけで状態を示す、出自を誤って表示する → テキスト併記を確認する
- 実装後の文言変更でテストが壊れる → 手順1でテストが検査する文字列を先に調べる
