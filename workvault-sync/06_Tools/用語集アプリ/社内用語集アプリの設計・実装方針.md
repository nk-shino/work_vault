# 社内用語集アプリの設計・実装仕様

## 目的と方針

複数の情報源から、できるだけ多くの社内用語と用例を収集し、用語集に蓄積する。件数が多く、人がすべてを確認する運用は成り立たないため、採用判断とDBへの登録・更新を判断ロジックに組み込む。

人による全件の事前承認は必須としない。登録された用語に評価ボタンを設け、レビュアーが正確性や有用性を判断できるようにする。人の作業は、登録後の評価、自動判断できない項目の確認、誤りの訂正に集中させる。

本仕様では、既存資料の内容を「現行仕様」、今回の対話で定めた内容を「変更方針」、実装に向けた提案を「設計案」として区別する。コードと実行結果は未確認であり、変更方針や設計案を実装済みとは扱わない。

## 1. 前提条件

### 検証範囲

現行のPhase 0では外部に接続せず、架空メール50通とモックを使って一連の処理を検証する。メールの取得元と社内LiteLLMの利用可否は未確定である。[1]

多数の情報源から収集する変更方針は、Phase 0の外部接続禁止を解除するものではない。まず架空データで複数情報源の取り扱い、自動採用、登録後評価を検証し、実際の接続は利用条件が整ってから追加する。

架空データで動作しても、実メールの処理精度、実LLMの品質、業務上の効果を確認したことにはならない。

### 実行環境

社用PC上でPython 3.11以上を使用する。make、Docker、PowerShellスクリプトには依存せず、操作の入口を`tasks.py`にまとめる。[1]

| 用途 | 現行構成 |
|---|---|
| DB | SQLite |
| データ操作 | SQLAlchemy |
| スキーマ管理 | Alembic |
| Webアプリ | FastAPI |
| 画面 | Jinja2、JavaScript |
| 外部依存の分離 | SourcePort、LlmPort、RawDocument |
| アダプタの選択 | factory.py |

依存パッケージは`requirements-lock.txt`で固定し、社用PCから外部へ接続できない場合はwheelhouseを使って導入する。資料にはPython 3.11、3.12、3.13向けのwheel取得とオフライン導入後のテストを確認した旨が記載されているが、本仕様の作成時点ではその結果を再検証していない。[1]

### 入力と接続先

現行の入力アダプタは、EMLと、`body`、`thread_id`、`occurred_at`、`source_ref`を持つCSVまたはJSONLを扱う。CSVはBOM付きUTF-8とcp932に対応し、時差情報のない日時は日本時間として扱う。[1]

`export_file_adapter`は完成、`knowledge_api_adapter`はスタブ、`litellm_adapter`と`local_embedding_adapter`は骨格と記載されている。LLMの既定値はモックである。[1]

EML、CSV、JSONLは入力形式として定められたものであり、同じ形式での出力機能が決まっているわけではない。

### 利用と管理

単一PCで試すのか、複数人で共同利用するのかを定める。対象利用者、レビュー担当、運用責任者も決める。

収集対象は利用が認められた情報源に限る。情報源を広げる場合も、元の情報を閲覧できることと、その内容を用語集に掲載してよいことは分けて判断する。

依存パッケージの調達、社用PCへの導入、通常実行では、それぞれの通信条件を定める。資料にある通信遮断はテスト時の仕組みであり、通常実行時に強制できるかは別途確認する。

## 2. 必須要件

### 収集と候補の保持

変更方針として、複数の情報源から広く収集し、取りこぼしを減らす。収集時に対象を狭めすぎず、取得した候補を採用判断に渡す。

広く拾うことと、すべてを確定することは分ける。判断ロジックは、新規登録、既存項目への用例追加、定義の更新、保留を振り分ける。

情報源ごとの違いはアダプタで吸収する。共通の入力形式と安定した出典識別子を設け、同じ情報を繰り返し取り込んでも重複しないようにする。

原表記を残し、表記揺れと意味の違いを区別する。同じ略語が部署や業務によって異なる意味を持つ場合は、無理に統合せず、語義と適用範囲を分ける。

### 前処理と保存

現行仕様では、署名や引用などを除去してからマスキングし、その後に形態素解析、候補抽出、名寄せ、TF-IDF、共起、PMIを処理する。統計処理にはLLMを使わない。[1]

語義には用例を必須とする。保存する用例は400字以下のマスキング済み抜粋とし、出典キーを付ける。マスキング前の本文はメモリ上でのみ扱う。[1]

生本文、処理済み全文、抜粋について、入力ファイル、中間ファイル、DB、ログ、バックアップごとの保存可否を定める。マスキング済み全文を中間保存してよいかは未確定とする。

400字の制限は根拠を選ぶ段階から考慮する。保存直前に機械的に切り詰め、対象語や定義を支える文脈を失わないようにする。

保存前の検査で禁止情報の残存を検知した場合は保存を止める。同じ正規表現による再検査だけで安全性を保証せず、独立した期待値付きテストで検出漏れと過剰なマスキングを評価する。

### 自動採用とDB更新

変更方針として、判断ロジックが採用を決め、DBへの登録・更新まで実行する。人の操作を待たずに処理できるようにする。

DBを直接更新する方針でも、制約を迂回して各処理が個別に書き込む構成にはしない。現行の`sense_writer`への集約を維持し、判断ロジックから共通の書き込み処理を呼び出す設計とする。

現行仕様では、語義の書き込み経路を提案の受理とレビュー画面に限定している。[1] 変更後は、提案の受理を判断ロジックからも実行できるようにし、書き込みガードと検査を更新する。

採用時には、語義、用例、提案の状態、判断理由、履歴を同じトランザクションで保存する。途中で失敗した場合は全体を戻す。

再実行や二重採用による重複を防ぐ。用例の追加と定義の書き換えは別に判断し、人が編集した内容を無条件に上書きしない。

### 採用状態と品質の区別

現行仕様では、提案を採用した時点で確定となる。[1] この方針を自動採用にも適用する。

確定は用語集への掲載状態として扱い、人が確認済みであることや会社の公式定義であることとは区別する。自動採用か人による採用かを記録し、人の評価状況を別に保持する。

用例が存在するだけでは、定義が正しいとは限らない。採用判断では、用例が定義を支えているか、既存語義と矛盾していないか、保存条件を満たすかを扱う。具体的な判定方法と基準値は未確定とする。

### 登録後の評価ボタン

変更方針として、用語の表示部分に評価ボタンを設け、レビュアーが正確性や良し悪しを判断できるようにする。

設計案では、同じ用語に複数の語義がある場合、語義ごとに評価する。正確性と有用性を分け、正しいが利用機会の少ない用語と、役立つが定義に修正が必要な用語を混同しない。

| 評価する内容 | ボタンの設計案 |
|---|---|
| 定義の正確性 | 正しい、修正が必要、判断できない |
| 用語集としての有用性 | 役に立つ、役に立たない |

必要に応じて理由や修正案を記入できるようにする。ボタンの名称と理由欄の仕様は確定前の案とする。

評価がない項目は未評価として扱う。否定的な評価や意見が分かれた項目を、見直し対象として取り出せるようにする。

評価数だけで定義を書き換えたり、削除したりしない設計を基本案とする。評価結果は再確認の優先順位と判断ロジックの改善に使い、再判定を起動する条件は別途定める。

### 評価の記録

評価には、対象の語義、評価時点の版、評価内容、日時、任意の理由を紐付ける。定義が更新された後も評価履歴を残し、旧版への評価を新版の評価として扱わない。

評価の保存と語義の更新は分ける。評価ボタンを押しただけでは定義を変更せず、修正する場合に共通の書き込み処理を通す。

現行仕様ではログインがなく、`editor_name`と`reviewed_by`は空である。[1] そのままでは評価者の本人識別や、同一人物による重複評価の防止を保証できない。識別方法が整うまでは、評価件数を人数や合意の強さとして表示しない。

### 整合性と履歴

現行仕様の用例必須、更新理由、履歴、楽観ロック、論理削除を自動処理にも適用する。[1]

SQLiteの各接続で外部キーが有効か、必須列にNULLが入らないか、初回用例が同じ語義に属するかを実DBで検証する。用例をアーカイブして有効な根拠がなくなる場合の扱いも定める。

履歴の改変防止と、変更の記録漏れ防止は別に確認する。通常のORM更新だけでなく、一括更新や直接SQLが履歴生成と競合検出を迂回しないかを調べ、許可する書き込み経路を限定する。

### 安全対策と復旧

ローカルの画面にも待受先の制限、HTMLエスケープ、CSRF対策を施す。ログや例外に生本文を残さない。

実データ導入前に、利用許可、掲載範囲、アクセス制御、保持期間、消去方法、バックアップ、復元手順を定める。

現行仕様では全表の物理削除を禁止し、マイグレーションのdowngradeも用意していない。[1] 通常操作はアーカイブとしつつ、誤って保存した機密情報の消去と障害時の復旧は別の管理手順として設計する。

## 3. 推測と未確定事項

次の内容は未確定であり、実装前または各段階への移行前に決める。

| 項目 | 決める内容 |
|---|---|
| 情報源 | 接続先、取得方法、利用許可、掲載できる範囲 |
| 利用形態 | 単一PCか共同利用か、運用責任者とレビュー担当 |
| 自動採用 | 判定方法、基準値、保留条件、定義更新の条件 |
| 語義の適用範囲 | 部署、業務、公式性、最終確認日の扱い |
| 保存 | マスキング済み全文の中間保存、保持期間 |
| 出典 | 再参照方法、参照時の権限、元データ消失時の扱い |
| 用例 | 最後の有効用例をアーカイブする場合の扱い |
| 評価 | ボタン名称、理由欄、変更・取り消し、重複評価の扱い |
| 評価の反映 | 見直しの優先順位、再判定の条件、自動判断への反映方法 |
| 本人識別 | 匿名編集を維持する範囲と、共同利用時の操作記録 |
| LLM | LiteLLMの利用条件、入力範囲、ログやデータの取扱条件 |
| 埋め込み | local_embeddingの役割と、文章生成用Portとの分離 |

Phase 0の主目的は、処理全体が再現でき、保存や更新の制約を守れるかの検証と捉える。品質の数値目標と業務上の成功条件は別途合意する。

`masked`フラグは処理済みの印であり、それだけで本文の安全性を保証するものではない。評価件数も、定義の正しさを直接証明する値としては扱わない。

## 4. 必要タスク

### T1　仕様と状態を確定する

最優先で、対象情報源、保存範囲、採用状態、評価状態、責任者を整理する。全件の事前承認を前提とする記述を改め、自動採用と登録後評価を中心に据える。

現行仕様、変更方針、設計案、未決事項が分かれ、受入基準が定まった時点を完了とする。

### T2　データモデルと書き込み処理を整える

用語項目、表記、語義、適用範囲、出典、用例、提案、処理実行情報、履歴、評価の関係を整理する。

`sense_writer`を通した自動採用と更新を実装し、外部キー、必須列、遅延制約、履歴、競合、二重採用、ロールバックを実DBで検証する。失敗時に部分的な保存が残らないことを完了条件とする。

### T3　前処理と通信の安全性を検証する

保存経路と通信経路を確認し、通常実行でも禁止された接続先やバックエンドを使えないようにする。

マスキングに使うルールとは独立した期待値付きテストを用意する。生本文が中間ファイル、DB、ログ、例外に漏れず、禁止情報を検知した場合に保存を止められることを確認する。

### T4　広範な収集と自動判断を実装する

情報源ごとの入力を共通形式にそろえ、重複除去、引用除去、名寄せ、根拠選定を整える。

新規登録、用例追加、定義更新、保留を分けて判断し、根拠、適用ルールの版、判断理由を残す。再実行しても重複せず、人の編集内容を失わないことを確認する。

### T5　登録後の評価と見直し画面を実装する

語義と版に紐付く評価を保存し、評価状況、未評価、修正が必要な項目、意見が分かれた項目を表示する。

評価の変更・取り消しと重複の扱いを仕様化する。全件を順に承認する画面ではなく、閲覧時の評価と、問題のある項目の確認に使える構成にする。

### T6　大量処理と運用を検証する

途中からの再開、失敗項目の取り出し、再実行、配布、バックアップ、復元を試す。

調整用と評価用のデータを分け、次を測定する。

- 抽出の適合率と取りこぼし
- 誤採用と誤統合
- 定義を根拠が支えている割合
- マスキング漏れと過剰なマスキング
- 自動処理できた割合
- 人の確認に残った件数と所要時間
- 登録後に修正された内容
- 同じ入力と設定での再現性

取りこぼしの評価には、抽出されなかった用語も含む正解ラベルを用意する。担当者、期限、数値目標、検証環境、結果を各タスクに紐付けて記録する。

## 5. 前後関連性

### 実装の順序

目的と保存範囲を定めてから、データモデルと状態遷移を決める。そのうえでDB制約と書き込み処理を整え、自動採用を接続する。評価機能は語義の版管理と結び付けて実装する。

実データの接続は、利用承認、掲載範囲、安全性の評価を終えてから行う。

### 処理の流れ

情報源からデータを取り込み、形式と出典識別子を確認する。重複や不要部分を除去してマスキングし、保存前の検査を行う。

処理済みデータから候補語を抽出し、表記と既存語義を照合する。根拠となる抜粋を選び、必要に応じて定義案を生成する。

判断ロジックが根拠と既存項目を確認し、新規登録、用例追加、定義更新、保留を選ぶ。採用する場合は、関連データと履歴を一括保存する。

登録した内容を利用者が検索・閲覧し、レビュアーが評価する。問題のある項目は再確認や訂正につなげ、その結果を判断ロジックの改善に使う。

### 工程間で引き継ぐ情報

取り込み時には出典識別子と日時の解釈を、前処理後には処理ルールの版を保持する。抽出結果には原表記、正規化表記、出典との対応を残す。

定義案には根拠を紐付け、採用時には判断方法と理由を保存する。評価は対象の語義と版に結び付ける。

前処理や辞書を変更すると統計結果も変わるため、入力集合、ルール、辞書、実行IDを記録する。再計算できる候補やスコアと、人の編集・評価は分けて管理する。

## 6. 相互補完性

統計処理は候補の発見と選定理由の説明を担う。LLMは必要に応じて定義案の作成を補助し、判断ロジックが採用と更新を実行する。人は登録後の評価、判断が難しい項目の確認、訂正を担う。

LLMを利用する場合も、判断ロジックと共通の書き込み処理を介する。生成された文章を検証せずに保存しない。出典にない用例を、実際の引用として扱わない。

DB制約はデータの構造を守り、アプリは書き込み経路と一括更新を管理する。テストで両者が働くことを確かめる。DBだけで定義の意味の正しさを保証しようとしない。

用例と出典は判断材料になる。登録後評価で誤りや不足を見つけ、履歴を使って変更を追跡する。評価は自動採用を止めるためではなく、蓄積した内容を改善するために使う。

マスキングは情報の露出を減らし、アクセス制御は閲覧者を制限する。保持期間と消去手順は、情報が残り続けるリスクを減らす。いずれか一つで代替できるものではない。

モックでは処理の接続と異常時の動作を再現する。限定実データでは実務での品質を測る。両方を分けて検証する。

## 7. 相対解決性

ここでは、対立する要件の折り合いと、段階ごとの解決方針を扱う。

### 収集範囲と誤採用

収集段階では広く拾い、採用段階では根拠と既存語義を確認する。判断できない候補は保留として残し、収集時の絞り込みだけで失わないようにする。

候補数や採用数だけで成果を測らず、取りこぼし、誤採用、訂正作業まで評価する。

### 自動採用と品質確認

全件の事前承認をなくし、自動採用後に評価と訂正を行う。自動採用の状態と人による評価を分け、未評価の項目を確認済みとして見せない。

人の作業は矛盾や否定的評価のある項目に寄せる。登録数が増えても、修正作業が増え続けるなら判断ロジックを見直す。

### DB更新の自動化と整合性

判断ロジックから登録・更新まで実行する一方、書き込み経路は共通化する。用例、履歴、変更理由、競合検出を自動処理にも適用し、処理速度のために省略しない。

### 編集の自由度と追跡可能性

現行の「誰でも他人の項目を編集できる」方針は維持する。[1] 共同利用時には、編集の自由度を保ちながら操作主体を内部記録する案を検討する。

匿名の評価件数を人数と同一視しない。評価者の識別方法を変える場合は、現行方針との関係を整理する。

### 全文非保存と再検証

抜粋、出典キー、処理の版を残して根拠を追えるようにする。ただし、元データを参照できなければ全文による再検証はできない。この制約を仕様に残す。

### 物理削除禁止と機密情報の消去

通常操作はアーカイブとする。誤保存した機密情報を取り除く管理手順は別に設け、バックアップに残る情報も対象にする。

### 将来の拡張とPoCの簡潔さ

単一アプリの構成とアダプタ分離を維持する。情報源が増えることを見込みつつ、未承認の接続や現段階で不要な基盤は先に作り込まない。

### 段階ごとの到達条件

Phase 0では架空データを使い、収集から自動採用、登録後評価までを動かす。整合性、保存範囲、通信制限、再実行、評価手順を確認する。

Phase 1では承認された限定実データを使い、抽出と自動採用の品質、レビュー負荷、公開範囲、運用手順を検証する。実LLMは利用条件を確認した後に限定導入する。

Phase 2では責任分担、訂正の運用、復旧手順、業務効果を確認し、継続利用に移る。
