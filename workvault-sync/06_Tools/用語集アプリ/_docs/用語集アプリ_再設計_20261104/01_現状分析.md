## 1. アプリの位置づけ（確認済み）

| 項目 | 内容 | 根拠 |
|---|---|---|
| 目的 | 社内用語を定義と用例つきで蓄積・検索する。全件の事前承認はせず、自動判定が採用まで行い、人は登録後の評価・訂正に回る | `README.md` 冒頭、`社内用語集アプリの設計・実装方針.md` §2 |
| 実行形態 | 127.0.0.1:8000 のみで待ち受け。外部接続なし。ログインなし | `README.md`、`src/glossary/web/app.py`（middleware・待受の記述） |
| スタック | FastAPI + Jinja2（サーバー描画 MPA）+ 素の JavaScript + SQLite（`data/glossary.db`） | `README.md`、`src/glossary/web/`、`pyproject.toml` |
| 変更しない前提 | 用例必須・履歴必須・楽観ロック・物理削除禁止（アーカイブ）・評価は版に紐付く・送信前マスキング・CSRF 拒否 | `README.md` の「データの約束事」表、`src/glossary/db/models.py`、`src/glossary/web/app.py` |

UI 改善の要請（確認済み）: `_docs/用語集アプリ_進捗_1002.md` 末尾に「UI において改善可能である。使っていて楽しくない。使用率の向上につながるので UI の改善はマスト。一般的なサイトでは見られないようなエフェクトや体験を」という指示がある。今回の再構築の起点とする。

## 5. 現行 UI の特性と課題

### 5.1 特性（確認済み。根拠は各ファイル）

- 色は変数集約、明暗自動切替、下線はリンクのみ、badge は色＋文字併記、`:focus-visible` 統一、reduced-motion で全停止（`style.css`）。
- キーボード: `/` で検索欄、キューで j/k/a/r/x、Tab 順序不変、skip link（`app.js`、`base.html`）。
- 情報設計: 一覧＝探す、キュー＝確定させる、見直し＝手入れする、登録＝入れる、CSV＝持ち出す（`_docs/用語集アプリ_全体改修設計案_20261030.md` §1.1 の整理と一致）。
- 視覚の基準: 統計カード 4 枚・パンくず＋ヒーロー（「語」のすかし）・明朝定義・確からしさメーター・SVG アイコン（`style.css`、`term_detail.html`、改修案 20261030 の「採用済み 6 変更」）。

### 5.2 課題（確認済みの事実＋提案）

| ID | 課題 | 区分 | 根拠 |
|---|---|---|---|
| P-01 | 検索が「フォーム送信して一覧を絞り込む」一段構え。入力から結果まで 1 回のページ遷移が必要で、連続して語を引く作業に向かない | 事実＋提案 | `terms_list.html`（form GET）、`queries.py` `list_terms` |
| P-02 | ゼロ件検索が終点になっている。「条件に合う用語がありません＋解除リンク」のみで、探していた語を登録候補に変える導線がない。調べたが無かった語という需要が失われる | 事実 | `terms_list.html` の空状態 |
| P-03 | 一覧から「語義の評価状況」が見えない。未評価・要修正は見直し画面に行かないと把握できない | 事実 | `terms_list.html` の列構成、`evaluations.py` |
| P-04 | 履歴が「版の縦並び＋pre の diff」。評価がどの版に付いたかを履歴から追えない。版に紐付くという設計の強みが画面に出ていない | 事実 | `history.html`、`models.py` `Evaluation.sense_revision` |
| P-05 | 関連語が種類別のリスト列挙のみ。語と語のつながり（混同注意・同義）が構造として見えない。関連語を開く前にどの語かの確認（プレビュー）もない | 事実 | `term_detail.html` 関連語セクション |
| P-06 | 見直し画面が読み取り専用の一覧。評価・編集は詳細へ遷移してからで、1 件あたりの操作が長い | 事実 | `review.html`、`term_detail.html` |
| P-07 | 書き込み操作の成功フィードバックがない（エラー帯のみ） | 事実 | 改修案 20261030 A-C5/D-C2（`style.css` に `.success` は無い） |
| P-08 | 提案の絞り込みが状態のみ。種別（語義/関係/用例）が選べず、語義の確定作業に関係提案が混ざる | 事実 | `proposals.html`、`app.py` `proposals_list` |
| P-09 | 表現の個性: 全体は「きちんとした業務画面」だが、固有の視覚言語（辞書・校正の文脈）が弱い。定義文の明朝はあるが、見出し語・読み・語義番号の階層は h3+p の流れ込みで、辞書の組版として完成していない | 事実＋提案 | `term_detail.html` 語義カード、`style.css` `.definition` |
| P-10 | 画面遷移が全体切替。一覧→詳細で視点（見出し語）が途切れる | 事実＋提案 | MPA・View Transitions 未使用（`base.html`） |
| P-11 | キーボード操作の発見性: `/` と j/k/a/r/x は存在するが、対応する画面にしか効かず、一覧できるヘルプがない | 事実 | `app.js` |
| P-12 | 重複・表記ゆれ（同じ読み・別の見出し）を画面が扱わない。統計側の懸念として既に記録がある（「同音異表記を統計で見つける手段が無い」） | 事実 | `_docs/用語集PoC_Phase0_実装報告.md` §7、`queries.py`（読み一致の照合なし） |

### 5.3 UI 以外で画面に影響する既知の制約（確認済み）

- 書き込み経路は `proposals.accept` とレビュー画面の 2 つのみ（`sense_writer` 集約）。UI で新しい書き込み操作を作る場合はこの経路を通す（`README.md` 約束事表、`src/glossary/domain/sense_writer.py`）。
- POST は同オリジンのみ（403）。GET は読み取りのみ（`app.py` middleware、改修案 20261030 A-C3）。
- 評価の重複防止・取り消しは未実装（ログインが無いことが理由。方針上は既定のまま）（`_docs/用語集アプリ_社用PC結果への対応と設計方針の実装_0930.md` §4）。
- テスト 155 件が回帰の基準（改修案 20261030 §0。本分析では実行していないため件数は資料からの引用）。

## 6. 改修案 20261030 の要約（基準線）

根拠: `_docs/用語集アプリ_全体改修設計案_20261030.md`。

- 方針 5 項目: ①情報階層は画面の役割に沿う・視覚部品は新規に作らない ②フィードバックは帯に一元化 ③密度と可読性の両立 ④キーボードファースト維持 ⑤a11y 下限を新規要素にも同じ規則で適用。
- 確定案の中心: 成功帯（D-C2）・更新列（D-T1）・種別絞り込み（D-P2）・用例省略 details（D-P3）・評価セクション折りたたみ（D-D1）・見直しの badge 列挙（D-R1）と採用列文言統一（D-R2）・error.html の javascript: 削除（D-C1）・text-wrap（D-C3）・プレビュー幅固定（D-T3）。
- 推奨（ユーザー採否待ち）: ソート既定の維持（D-T2）・条件付き CSV（D-X2）。
- 保留: ページャー強化（D-T4）・見直しのページング（D-R3）・ミニグラフ（案3、日次履歴機構が前提）。
- 不採用推奨: トースト（案1・帯で代替）・0.9 秒カウントアップ（案2・0.5 秒維持）・左サイドバー（案4）・テーマ手動切替。
- 範囲外: 接続受付 UI（台帳 A-04→A-06 の順序依存）、投票機能（別線 20261028）。
