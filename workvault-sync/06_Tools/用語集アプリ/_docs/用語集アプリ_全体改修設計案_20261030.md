# 社内用語集アプリ 全体改修設計案（2026-10-30）

> 保管庫副本。正本とモックはワークスペース `20261030_用語集アプリ全面改修/`（全体改修設計案_20261030.md・mock_第3段/モックアップ_第3段.html）。更新時はこの副本を上書きする。
> 作成者: 設計（UI/UX）担当。実装は行わない（次ラウンドで別レーンが実装する。逐次ルール）。
> 出典の URL 管理と外部指針の比較は並行の curator レーンが行うため、本書は既知資料への対応づけのみを行う。
> 実装差分（コード）は、本書の受け入れ条件を実装レーンが具体化する形で作る。

## 0. 範囲と前提

- 対象: 対象A（用語集・社内限定）の 6 画面（用語一覧・提案キュー・語詳細・見直し・用語登録・CSV出力）と共通部品（base・error）。語義編集・用語編集・修正して採用・競合・履歴は付随画面として扱う
- 対象外: 接続受付UI（台帳 A-04 採否 → A-06 提案の順序依存。設計は A-06 提案後に別途）
- 維持する前提（変更しない）:
  1. 採用済み 6 変更（統計カード 4 枚・パンくず＋ヒーロー・明朝体定義・確からしさメーター・SVGアイコン・自動ダークモード）。平準化しない
  2. 第1段の実装（一括処理・語義プレビュー・密度切替・キーボードトリアージ・数値バッジ・保留チップ黄・空状態統一）と第2段（`error=rule` 帯・選択バー sticky）
  3. テスト 155 件（pytest）。既存の文言・条件が見ている箇所は §1 の監査に明記した
  4. CDN 不使用・サーバーレンダリング（Jinja2）・素の JS・ダークモード自動追従。罫線トークン（--line/--line-soft/--border 系）の置換・削除をしない
- 判断の区分（本書での表記）:
  - 【確定】設計として確定。実装ラウンドへ渡す
  - 【推奨】ユーザー採否待ち（モック 4 案・機能追加）。最終判断はユーザーが行う
  - 【保留】依存または規模の条件が付く後回し
  - 【記録】変更なし。判断と根拠の記録のみ

## 1. 現状UIの監査

### 1.1 情報構造と導線の現状（事実）

- ナビ 5 項目（用語一覧・提案キュー・見直し・用語を登録・CSV出力）。aria-current で現在位置を示し、提案キューには未処理件数の数値バッジ（0 件で非表示）。ヘッダーに「外部接続なし・このPCの中だけで動作」の安心表示
- 画面の役割分担: 一覧＝探す、キュー＝確定させる、見直し＝手入れする、登録＝入れる、CSV＝持ち出す。詳細は語義ごとの評価と履歴の拠点
- キーボード導線: `/` で一覧の検索欄へ、キューで j/k/a/r/x、Tab 順序は不変、skip link あり
- 戻る導線: 詳細にパンくず、編集系に「取り消して戻る」、履歴から詳細へ戻る
- 導線の弱い点（事実）: 提案を採用したあと、結果の語義（語の詳細）への確認経路が無い。採用はキュー上で完了し、ユーザーが自発的に一覧から探す必要がある（→ D-P1 で扱う）

## 2. 全体改修の設計方針（5 項目）

1. **情報階層は画面の役割に沿って整える。視覚部品は新規に作らない** — すでに一覧と詳細にある視覚の強さ（統計カード・ヒーロー・明朝定義）を基準とし、キューと見直しは「確定させる・手入れする」の作業画面として情報量と縦長の管理に手を入れる（D-P3・D-D1・D-R1）。装飾の追加はしない
2. **フィードバックは帯に一元化する** — 操作結果の伝え方を帯（エラー=赤・注意=黄・成功=緑）に統一する。色は状態の意味に使い、動き（トースト・アニメーション）は状態の伝達に必要な場面に限る（→ §2-2 はモック案 1・案 2 の評価軸にもなる）
3. **密度と可読性は両立させる** — 密度切替（compact）を軸に、列の追加・文言の整え・用例の省略表示で情報を足す。省略は「開けば全件見える」details に限り、判断材料を隠さない
4. **キーボードファーストを維持する** — `/`・j/k/a/r/x・Tab 順序不変・全操作の代替経路（キーボードショートカットが無くても成立する）の原則を守る。新規の折りたたみはネイティブ details/summary に限る
5. **a11y 下限を新規要素にも同じ規則で適用する** — コントラスト・ラベル（id＋label・sr-only）・`:focus-visible`・reduced-motion・色非依存（badge は色＋文字併記・メーターはパーセント読み上げ）を維持する。`test_all_inputs_have_labels` の条件（id 必須・重複禁止・label 対応・hidden 除外）を回帰として使う

## 6. 懸念と自己点検

1. **D-C2 の URL 付き帯は既存エラー帯と同じ「URL に残る」性質**。リロードで帯が再表示される。Cookie セッション flash 方式は実装とテストの影響が大きいため第一案は URL 方式（既存方式との一貫性を優先）
2. **折りたたみは「情報を隠す」変更**（D-D1・D-P3）。トリアージと評価の判断材料（用例・集計・理由）は 1 開閉で見える形に限定し、summary 文に状態を含める規則を守る。これ以上の折りたたみ（語義カード全体の折りたたみ等）は本設計では行わない
3. **テスト文言への影響箇所は特定済み**（test_evaluate_from_screen の 3 文字列・test_empty_and_error_states・test_nav_links_exist・test_all_inputs_have_labels・test_bulk_rule_violation_reports_the_reason）。各案の受け入れ条件に回帰条件を明記した。ただし pytest の全件通過は実装後の確認であり、本書の時点では未確認
4. sticky 選択バーの top 3.2rem（第2段懸念 1）と、main の登場アニメーションは本設計では変更しない（動作に影響を与える既知要素への手入れは行わない）
5. 負担の見積もり（小/中/大）は推定。実装レーンが着手時に更新する
6. 本書の妥当性の自己点検は設計担当の範囲。実装・実画面検証・独立レビューは各レーンの領域であり、本書で完了扱いにしない
