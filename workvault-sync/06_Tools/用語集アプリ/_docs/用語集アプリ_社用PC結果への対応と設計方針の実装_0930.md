## 2. 設計方針のうち実装したもの

**自動判定**（取り込みのたびに、候補語を3つに振り分ける）

- **用例の追加：** 登録済みの語なら、まだ無い用例を足す。定義は変えない（人が直した定義を上書きしないため）。語義の版も上がらないので、付いている評価は有効なまま
- **自動採用：** 新しい語で、用例2件以上・出典2種類以上・LLM の確からしさ0.7以上・「用例が定義を支えている」をすべて満たすとき。しきい値は `config/adoption.yaml` で変えられる
- **保留：** それ以外。理由つきで提案キューに残る（例：「保留：出典が 1 種類（2 種類以上が必要）」）
- モック（今の既定）の定義文は中身が無いので、**必ず保留**になる。LiteLLM を使うまでは、新しい語は人が定義を書く運用のまま
- 自動でも人でも、書き込みは同じ経路（提案の受理 → sense_writer）を通る。用例必須・履歴・楽観ロックは自動採用にもそのままかかる
- 語義ごとに「自動採用」か「人が採用」かを記録し、画面にも出す

**登録後の評価**

- 語義ごとに「正しい／修正が必要／判断できない」「役に立つ／役に立たない」のボタンと、理由・修正案の欄
- 評価は押した時点の**語義の版**に結び付く。定義が直されたら、旧版への評価は今の版の評価として数えない
- 評価は定義を書き換えない。評価は追記だけで、書き換え・削除は DB のトリガーで止める
- ログインが無いので、件数は「押された回数」と表示し、人数ではないと明記した（設計方針のとおり）
- 「見直し」画面：修正が必要／意見が割れている／役に立たない／自動採用のまま未評価／未評価 で絞り込める

**安全対策**

- 別のサイトのページからこのアプリへフォームを送らせる攻撃（CSRF）を止めた。127.0.0.1 で待ち受けていても、ブラウザ経由では送れてしまうため

**DB の更新**

- マイグレーション 0002（評価の表・語義の採用者・用例追加の提案）。既存の DB を上げても**データが1件も欠けない**ことと、削除禁止のトリガーが付き直ることを確認した

## 3. LiteLLM（2026-09-29 の画面の画像から）

- OpenAI 互換の API。アプリ用の鍵は発行済みで、Azure の gpt-5 系が使える。埋め込み用のモデルは画像の範囲では見えなかった
- アダプタを実装した。標準ライブラリだけで呼ぶので依存が増えず、会社の証明書ストアをそのまま使える。https 以外は拒否し、エラーの文面に鍵が混ざらないようにした
- **既定では使わない。今回は一度も接続していない。** 使うときは `LLM_BACKEND=litellm` と、URL・鍵・モデル名を環境変数で渡す（README の「LiteLLM を使うとき」）
- 使う前に決めること：マスキング済みの用例を LiteLLM に送ってよいか、送る範囲、使うモデル

## 4. 設計方針のうち、まだやっていないこと

- 定義の自動更新（登録済みの語の定義を LLM で書き換える）：人の編集を上書きしない条件が決まっていないため
- 評価の取り消し・変更、重複評価の扱い：誰が押したか分からない（ログインが無い）ため、決められない
- 処理の実行ID・ルールの版の記録、途中からの再開：件数が増えてから
- マスキングの独立した期待値付きテストの拡充、実データでの品質測定：Phase 1（承認された実データ）で行う

## 社用PCでやること

1. Work_Vault の `06_Tools\用語集アプリ` を、**OneDrive の外**（例：`C:\work\用語集アプリ`）へフォルダごとコピーする
2. そのフォルダで `python tasks.py` を実行する（VS Code の実行ボタンでもよい）。初回は準備に数分かかり、終わるとブラウザが開く
3. 準備が pip のエラーで止まったら、画面のメッセージを控える。開発PC側で USB に Python 3.14 用の wheel を入れて渡す
4. 動いたら `python tasks.py check` の最後の行（「〜 passed」）を控える
