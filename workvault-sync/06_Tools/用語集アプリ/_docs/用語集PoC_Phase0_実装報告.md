## 2. 採用した設計と理由

- **ポートとアダプタ構成。** 決まっていないのは「どこから本文を取るか」と「どの LLM を使えるか」の2点だけ。この2つを外側に閉じ込めれば、決まったときに書き換えるのはアダプタだけで、コア（前処理・統計・DB・画面）は触らずに済む
- **DB は SQLite。** 社用PCに Docker がある保証が無いため。「用例の無い定義は保存できない」は表をまたぐ制約で、CHECK では書けない。そこで**遅延外部キー**で守った。語義は「自分の用例」を1件指していなければならず、それをコミット時に確かめる。PostgreSQL でも同じ書き方が使える（付け直しは必要）
- **約束事はアプリ層と DB 層の両方で止める。** 片方だけだと抜け道が残るため。アプリ層だけなら SQL を直接流されたら素通りし、DB 層だけならどのコードが書いたかを区別できない
- **語義に書き込める場所はコード上で1つ（sense_writer）だけ。** 呼んでよいのは「提案の受理」と「レビュー画面」の2つで、実行時のガードと静的なテストの両方で確かめる
- **履歴は flush のたびに自動で追記する。** 書き忘れる余地を残さないため。編集理由が空なら保存そのものを止める
- **日時は UTC に揃えて保存し、画面では日本時間で出す。** SQLite はタイムゾーンを保存しないので、揃えないと同じ値が履歴の差分に出てしまう（実際に出たので直した）
- **社用PCへの配慮。** make・Docker・.ps1 は使わない。ファイルの入出力はすべて文字コードを明示する。CSV は BOM 付き UTF-8 で書く（Excel でそのまま開ける）。pip が社外に出られない場合は、wheel を集めて運ぶ手順を用意した

## 4. fixtures を使った最初から最後までの動作結果

- **前処理：** 50通 → マスキング件数（名乗り50・金額13・シリアル7・URL 6・電話4・メール2）。マスキング後の本文に、架空の人名・アドレス・電話番号・金額が1件も残っていないことをテストで確認
- **統計：** 候補語71件・共起ペア363件。**上位13件がそのまま fixtures に仕込んだ架空の用語だった**（ドラゴンミルク・霧抜き作業・スカイポスト・MGK・竜車・卵温計・雲切り・FLT・FLT点検・浮遊石・星読み台帳・ほうき便・竜舎）
- **提案：** 語義の提案20件・関係の提案20件
- **採用（デモ）：** 語義13件を採用。関係は「関連」4件と、手で足した「混同注意」（竜舎⇔竜車）1件。1件を係争中にした
- **画面（実際のブラウザで確認）：** 一覧・検索・絞り込み、詳細（混同注意の赤枠・係争中の表示・用例と日時）、キーボードだけでの編集と保存、古い版からの保存が 409 になり上書きされないこと、履歴の差分

作業中に見つけて直した不具合も書いておく（どれも今はテストで押さえてある）。
- alembic.ini の日本語コメントが cp932 として読まれて落ちた → 英数字だけにした（社用PCでも必ず踏む）
- シリアル番号のルールが電話番号まで拾っていた
- 「霧島です。」のような名乗りの名前が伏せられずに残っていた → 名乗りのルールを足した
- 品詞によるルールが、置換済みの `<PHONE>` の中身を人名と判定していた
- 処理中の表示と絞り込み欄の id が重複し、状態の絞り込み欄が見えなくなっていた
- デモ処理の巻き戻しが、採用済みの語義まで消していた
- 同じ日時が DB を往復すると別の値に見え、履歴の差分に出ていた

## 7. 現時点で分かっている設計上の懸念

- **敬称の無い人名の取りこぼし。** 敬称付き・冒頭の名乗り・辞書が人名と判定するものは伏せる。ただ「霧島」のように辞書が地名と判定する姓が文中に裸で出ると抜ける。実データで漏れを数えるまでは、安全とは言えない
- **出典キーにメールの Message-ID を使っている。** 実際の Message-ID には送信サーバー名や社内ドメインが入ることが多く、そのまま DB に残る。本文ではないのでマスキングの対象外にしている
- **TF-IDF はどこにでも出る語を低く見る。** fixtures でも一番重要そうな「竜舎」が13位だった。実データでは、部署名や主要設備のような中心的な語が埋もれるおそれがある
- **PMI は少ないデータで荒れる。** 同じ点数が並び、「来週⇔浮遊石」のような一般語どうしのペアが上位に来た。最低出現数と一般語の除外を詰める必要がある
- **同音異表記（竜舎／竜車）を統計で見つける手段が無い。** しかも関係の算出方法（method）の選択肢に、読みで見つけたことを表す値が無い。今回は人が足した扱いにした
- **編集者の表示名は任意入力で、ログインが無い。** 履歴の「誰が」は自己申告にすぎない。社内で共有するなら認証が要る
- **モックの定義文は固定文言。** なので「定義草案の採用率」は Phase 0 では測る意味が無い。計算の仕組みとテストだけを完成させた
- **SQLite は同時の書き込みに弱い。** 数人のレビューなら足りるが、人数が増えるなら PostgreSQL への移行を考える
