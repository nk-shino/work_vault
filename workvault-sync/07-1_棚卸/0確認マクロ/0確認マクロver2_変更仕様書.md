## 2. 何が起きていたか

ver.2 を実行しても何も起こらず、CSVを取り込んでも0件と見えていた。

**実際には0件だったのではなく、マクロが一度も実行されていなかった。**
VBAはプロジェクト全体をコンパイルしてから実行するため、どこか1箇所でも
コンパイルが通らなければ、そのモジュールに限らず**全機能が動かない**。

原因は宣言部の記述2種。いずれも業務ロジックとは無関係な箇所である。

### 原因A：`PtrSafe` の欠落

64bit版のExcelでは、外部DLLを呼ぶ `Declare` に `PtrSafe` が必要になる。
本ブックでは4本の `Declare` にこれが無かった。

| 位置 | 対象 |
| --- | --- |
| Module1 126行 | `GetCursorPos` |
| Module1 127行 | `SetCursorPos` |
| Module1 130行 | `mouse_event` |
| Module2 314行 | `GetCursorPos` |

同じブックの79〜118行にある他のAPI宣言は `#If Win64` と `PtrSafe` で
正しく書かれており、**この4本だけが対応から漏れていた。**

適用先PCのExcelは64bit（`EXCEL.EXE` が `C:\Program Files\` 配下にあり、
32bit版が置かれる `C:\Program Files (x86)\` ではない）。
したがって、このエラーが最初に発生する。

### 原因B：同名の公開宣言が2つ

`Type coordinate` と `GetCursorPos` が Module1 と Module2 の両方で宣言されていた。
標準モジュールでは宣言の既定が公開（Public）のため、同じ名前が2つ存在し、衝突する。

この重複は [[0確認マクロ_Excelデータ仕様書]] が 2026-09-16 時点で既に指摘していた。

### 副次的に判明した2点

コンパイルが通った後に顕在化する問題として、以下を同時に修正する。

| # | 内容 | 根拠 |
| --- | --- | --- |
| C | 取り込んだシリアル番号の先頭に空白が残る | 入力CSV 29,246行のうち **12,218行**が `    160096C100792` の形で先頭に空白を持つ。そのままリール消費画面へ送ると照合が一致しない |
| D | 取り込み時にA列を初期化していない | 上書きのみのため、前回の取り込み件数のほうが多いと古い行が下に残り、件数表示と実際の行数がずれる |

## 3. 変更内容

変更は3ファイル相当・**実質7行**。全体像は次のとおり。

| 箇所 | 変更の種類 | 原因 |
| --- | --- | --- |
| Module1 宣言部 | `#If VBA7` で分岐し `PtrSafe` を付与、`Private` 化 | A・B |
| Module2 全体 | 同上（ファイル差し替え） | A・B |
| Sheet1 `Input0_Click` | `Columns(1).ClearContents` を追加 | D |
| Sheet1 `Input0_Click` | `cols(0)` → `Trim(cols(0))` | C |

### 3-1. Module1 宣言部

```vba
' 変更前
Type coordinate
    x As Long
    y As Long
End Type
Declare Function GetCursorPos Lib "user32" (lpPoint As coordinate) As Long
Declare Function SetCursorPos Lib "user32" (ByVal x As Long, ByVal y As Long) As Long
Declare Sub mouse_event Lib "user32" (ByVal dwFlags As Long, _
    Optional ByVal dx As Long, Optional ByVal dy As Long, _
    Optional ByVal dwDate As Long, Optional ByVal dwExtraInfo As Long)
```

```vba
' 変更後
Private Type coordinate
    x As Long
    y As Long
End Type

#If VBA7 Then
    Private Declare PtrSafe Function GetCursorPos Lib "user32" (lpPoint As coordinate) As Long
    Private Declare PtrSafe Function SetCursorPos Lib "user32" (ByVal x As Long, ByVal y As Long) As Long
    Private Declare PtrSafe Sub mouse_event Lib "user32" (ByVal dwFlags As Long, _
        Optional ByVal dx As Long, Optional ByVal dy As Long, _
        Optional ByVal dwDate As Long, Optional ByVal dwExtraInfo As Long)
#Else
    （同じ宣言を PtrSafe 無しで記述）
#End If
```

### 3-2. Module2

同じ考え方で全体を書き直し、`Module2_修正版.bas` として差し替える。
実体は `解決課題\Module2_修正版.bas`。

### 3-3. Sheet1 `Input0_Click`

```vba
' 追加（ファイル選択の直後）
Columns(1).ClearContents

' 変更（書き込み行）
Cells(writeRow, 1).Value = Trim(cols(0))    ' 変更前: cols(0)
```

完全なコードと適用手順は `解決課題\0確認マクロ_修正版コード.txt` にある。

### `#If Win64` ではなく `#If VBA7` を使う理由

既存コードは `#If Win64` で分岐している。今回追加する分岐は `#If VBA7` にした。

`PtrSafe` を解釈できるかどうかは**ポインタ長ではなくVBAのバージョンで決まる**ため。
32bit版のOffice 2010以降は `Win64 = False` だが `PtrSafe` は使える。
`Win64` で分岐すると、この環境で不要に旧記法へ落ちる。動作はするが、判定の根拠が誤っている。

## 4. なぜこの変更が安全といえるか

### 4-1. 業務ロジックを一切変更していない

抽出条件の判定式は1文字も触っていない。

```vba
If Left(loc, 3) = "0確認" And IsNumeric(cols(5)) Then
    If CLng(cols(5)) <= 9 Then
```

「ロケーション名称が `0確認` で始まる」「在庫数が9以下」という
[[0確認マクロ改修仕様書]] §6 の抽出条件は、変更前後で同一である。

### 4-2. 取り消せない処理に触れていない

本マクロには性質の異なる2つの処理がある。

| 処理 | 影響先 | 取り消し |
| --- | --- | --- |
| CSV取り込み（`Input0_Click`） | ExcelのA列のみ | **可能**。保存せず閉じれば戻る |
| 消し込み（`ゼロ確認`） | EG-Proのリール消費。ラベルが消える | **不可能** |

**今回の変更は取り込み側のみ。** 消し込みループは1行も変更していない。
既に運用で確認されている消し込みの挙動は変わらない。

宣言部の変更は `Private` 化と `PtrSafe` 付与であり、
いずれも**呼び出し先のWindows APIの動作を変えるものではない**。
`PtrSafe` は「64bit環境で安全に呼べることを開発者が宣言する」ための記述であって、
APIの引数や戻り値を変えるものではない。

### 4-3. 変更が外部システムへ波及しない

取り込み処理が触るのはExcelのA列だけである。
EG-Pro、Pana-CIM、データベース、共有フォルダのいずれにも書き込まない。
ネットワーク通信も発生しない。

### 4-4. 合否を機械的に判定できる

適用後の期待値を、変更前に確定させてある。
入力CSV `2026_09_25_113916_EGProWhereHouse.csv`（29,246行）に
同一の判定条件を機械的に適用した結果は次のとおり。

| 項目 | 期待値 |
| --- | --- |
| 取り込み件数 | **5,848 件** |
| `0確認(L3)` / `(L1)` / `(L2)` | 3,088 / 1,422 / 1,338 |
| 在庫数 1個 / 2個 / 3個 | 1,913 / 1,463 / 778 |
| 在庫数 4〜9個 | 600 / 325 / 301 / 206 / 170 / 92 |
| 品番の種類 | 1,080 |
| A列 1行目 | `160096C100792` |
| A列 5,848行目 | `T9000031021100011` |

**この数と一致しなければ、変更が正しく入っていないか入力ファイルが異なる。**
「たぶん動いた」で先へ進まずに済む。

在庫数1〜3個で4,154件、全体の71%を占める。これは
[[0確認マクロ改修仕様書]] §2 の「切り替わりで残る数量は一つから三つ程度が多い」
という現場の説明と整合し、抽出条件が妥当であることの傍証になる。

### 4-5. 適用を段階に分けられる

コンパイル（手順1〜4）と取り込み実行（手順5）と消し込みは、それぞれ独立して止められる。
コンパイルだけ通して終える、取り込みだけ実行して目視で終える、という進め方ができる。
不可逆な消し込みに進むかどうかは、A列の中身を確認してから判断できる。

## 6. 適用後の確認手順

1. VBEの [デバッグ] → [VBAProject のコンパイル]。**何も表示されないこと**
2. 取り込みを実行し、`5848 件を取り込みました。` と表示されること
3. A列1行目が `160096C100792` であること
4. A列の値が空白で始まっていないこと
5. A列の最終行が5,848行目で、`T9000031021100011` であること
6. **B列が空のままであること**（値が入っていると消し込みが途中から始まる）
7. 消し込みは少数件から開始すること

1〜6がすべて満たされるまで、消し込みへ進まない。
