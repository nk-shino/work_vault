目的: idouSQL（倉庫移動SQL）を安全に運用に投入するために、あなたが「何を」「どのように」実行すべきかを優先順と具体手順で示す。即座に着手できるチェックリストと意思決定ポイントを含む。

前提（重要）
- idouSQL は UPDATE を行うが在庫数そのものは変更せず、ロケーション等を書き換える実行方式です。VBAはSQLをテキスト出力し、人が中身を確認してから実行する運用になっています。SQLはトランザクション（SET XACT_ABORT ON; / BEGIN TRAN;）で囲み、更新件数・@@TRANCOUNT を表示してから担当者が COMMIT / ROLLBACK を選ぶ形式です 。

---

思考フレーム（意思決定の枠組み）
1. 安全第一（Fail-safe優先）  
   - 実行前に「元へ戻す方法」と「失敗時の挙動」を必ず確認する。失敗からの復元手順が無い状態で実行しない。
2. 小さく試す（スモールバッチ→拡大）  
   - まず少数のシリアルで流して結果を確認、次に本番件数へスケールする。
3. 目視確認を入れる（自動化は最後）  
   - VBAはSQLを出力するだけ。実行は人が目視して判断する運用を維持する。
4. 記録と後追い可能性を担保する  
   - バックアップ取得・実行ログの保管・切り戻し方法を事前に明確化する。

優先順位（直近であなたが行うこと）
1. 実行前の最終目視チェック（最優先）
2. `serialList` と `locCode` の妥当性確認（データ検証）
3. ステージングでの実行テスト（小規模）→ 差異確認
4. 仕様書（idouSQL節）と図解（drawio）の差し替え・反映
5. 運用手順（実行者マニュアル）整備と承認
6. 本番実行（段階的に）→ 確認→ 記録保存
7. 横展開時の権限・保管ルールの整備（別環境対応）

具体タスク（ID・目的・ステップ・入力・出力・所要時間目安）

T-001: 実行前最終目視チェック（OUT-001: 実行OK判定）
- 目的: SQLを流す前に致命的なミスを除去する
- 入力: VBAが出力した tmp_sql.txt（完全なSQL）
- ステップ:
  1. ファイルを開く（メモ帳等）して全文を目で追う
  2. WHERE のシリアル列挙が期待値（個数・フォーマット）と一致するか確認
  3. locCode（A55）の値を確認し、仕様で決めた倉庫コードと合致するか確認
  4. SELECT @@ROWCOUNT／@@TRANCOUNT の位置と注意コメントが正しいか確認
  5. 不要な重複（COMMIT/ROLLBACK が二組ないか）をチェック
- 出力: 実行可/不可の判断メモ（1行で「OK」か「NG: 理由」）
- 所要時間: 5〜15分
- 合格条件: targetCount と SELECT @@ROWCOUNT が一致することが期待できる状態であると判断できる
[過去データで実証済み：出力自体は問題なし]

T-002: `serialList` フォーマット検証（OUT-002: フォーマット修正）
- 目的: IN(...) の値が正しくクオートされ、前方スペースなどが維持されることを保証する
- 入力: 元データ（現場部品リスト）、VBA生成の serialList
- ステップ:
  1. 生成された serialList をサンプル抽出（先頭5件・末尾5件）して確認
  2. シリアルが「'    667449A100418'」のように前方スペースを含め括弧で囲まれているか確認
  3. クォート内の単一引用符が '' へエスケープされているか確認
  4. 不備があればマクロの該当処理（連結・エスケープ）を修正して再生成
- 出力: 修正済 serialList、問題点ログ
- 所要時間: 10〜30分
- 参照注意点: 前方スペースが必要な業務ルールなら保持する。不要であればトリムで統一。
[前方スペースを含め括弧で囲まれているか確認済み]

T-003: small-batch ステージング実行（OUT-003: ステージング結果）
- 目的: 本番前に小範囲で動作確認して副作用を観測する
- 入力: tmp_sql.txt を小さなシリアル集合に調整したSQL（例: 5件）
- ステップ:
  1. バックアップテーブルに該当サンプルを退避（SELECT * INTO で日時付きテーブル）
  2. BEGIN TRAN; → UPDATE → SELECT @@ROWCOUNT; → SELECT @@TRANCOUNT を実行
  3. 想定件数と一致なら COMMIT を選択（ただしまずはROLLBACKで戻すことも検討）
  4. バックアップからの復元手順（切り戻し）をテスト（ROLLBACK 後に復元SQLを試すかどうかは検討）
  5. 結果をログに出す（何が変わったか、EG-Pro上で確認）
- 出力: ステージング実行ログ（更新件数、差分スクショやSQL実行ログ）
- 所要時間: 30分〜2時間（環境依存）
- 合格条件: ステージングで想定どおりに動いたことを確認

T-004: 仕様書 idouSQL 節の差し替え（OUT-004: 仕様書v2 更新）
- 目的: 実装と運用手順を仕様書へ反映し、レビュアー質問に即答可能にする
- 入力: 確定版のVBA実装（AppendLine全文）、既存仕様書v2
- ステップ:
  1. idouSQL 節に「何が変わったか」と「なぜ安全か」を短く追加（件数確認、XACT_ABORT、バックアップ、切り戻しの3点）
  2. 手順に「UTF-8→Shift-JIS の変換は取り込みマクロ側で自動処理される」旨を一文追加（取り込みの運用注意）
  3. 未確定項目は未確定欄へ残す（テーブル14、列定義など）
  4. 図解（drawio）更新依頼を作成（差し替え用XMLを付ける）
- 出力: 置換済み仕様書草案（.md）
- 所要時間: 30〜60分
- 参照: 仕様追記はレビュアー向けQ&Aを付けると審査が速い

T-005: 図解（drawio）差し替え（OUT-005: 更新済drawio）
- 目的: 図解に idouSQL の安全化を反映し、作業者の視認性を上げる
- 入力: drawio の全文（XML）と仕様書追記文
- ステップ:
  1. 指示済みの付箋4枚を実情報で置換（計算マクロ概要、Tanaoroshi/Wherehouse の使い分け、idouSQL中身、トランザクション要旨）
  2. 既存のレイアウトやエッジは保持、付箋の value を置換
  3. 置換後のXMLを保存して関係者へ共有
- 出力: drawio 更新ファイル（XML）
- 所要時間: 20〜60分（XML編集が得意であれば短時間）

T-006: 実行者マニュアルとチェックリスト整備（OUT-006: 実行手順ドキュメント）
- 目的: 実行時のミスを減らすため、1枚のチェックリストを作る
- 入力: tmp_sql.txt の様式、仕様書（idouSQL節）
- ステップ（チェックリスト例）:
  1. 出力ファイルを開く
  2. serialList の先頭/末尾を確認（5件ずつ）
  3. targetCount と SELECT @@ROWCOUNT の想定コメントを合わせる
  4. locCode を確認（202 or 指示のコード）
  5. 「操作手順ブロック内」の COMMIT/ROLLBACK 本体行の位置を確認
  6. 実行は 1) 全SQL を F5 して更新件数を確認 2) 一致なら COMMIT の行だけ選択して F5、異なれば ROLLBACK の行だけ選択して F5
  7. 確定後に SELECT @@TRANCOUNT が 0 であることを確認してウィンドウを閉じる
- 出力: 実行者向け PDF/Markdown チェックリスト
- 所要時間: 30分

T-007: 本番段階的実行（OUT-007: 本番完了ログ）
- 目的: 本番に段階的投入してリスクを最小化する
- 入力: 上の全て（確認済みSQL、バックアップ確認、承認）
- ステップ:
  1. 小規模→中規模→全件の順で実行（各段階でログ保存）
  2. 各段階で EG-Pro 上の反映状況を確認
  3. 想定と一致しない場合は即 ROLLBACK し、バックアップから切り戻しを実施
- 出力: 本番完了報告書（件数比較、問題点、対処履歴）
- 所要時間: 環境と件数に依存（数時間〜半日）

未確認／要確認（事前に埋めるべき前提）
- 移動先コードの最終確定（202 と 203 のどちらを採用か）→ 実行前に確定すること（仕様書と実機値を合わせる）。  
- バックアップテーブルの保管期間・削除ルール（運用ルール）→ 放置すると蓄積問題に。  
- 実行者の権限（管理者権限でない環境へ横展開する場合の差し替え要否）→ SELECT INTO が使えない環境では INSERT 固定テーブル方式へ変更が必要。  

実行前チェックリスト（短縮版）
- [ ] tmp_sql.txt を開いて全文を目視した（T-001）
- [ ] serialList のフォーマットを確認した（T-002）
- [ ] locCode（A55）を仕様値と突合した
- [ ] バックアップテーブルが作成されることを確認した
- [ ] ステージングで小規模テストを実施し、ログを保存した（T-003）
- [ ] 仕様書・図解・実行マニュアルを最新版に更新した（T-004/T-005/T-006）
- [ ] 実行承認を得た（誰が GO を出すか記録）

短期の「次の一手」（今すぐできる3つ）
1. tmp_sql.txt を開き、T-001 を実施して「実行可/不可」を1行で出す（5〜15分）  
2. serialList の先頭/末尾を確認して、不整合があれば修正依頼を出す（10〜30分）  
3. 仕様書 idouSQL 節に「トランザクションで何が安全になったか」を1段落入れて配布（30分）

補足（運用上の注意）
- SQL を全文再実行すると UPDATE が二重に走る恐れがあるため、全文再実行は原則しないこと。必ず「COMMIT 行だけを選択して実行」か「ROLLBACK 行だけを選択して実行」とする。COMMIT/ROLLBACK の重複がないことを事前に確認すること 。  
- 実行後は @@TRANCOUNT が 0 になっていることを確認してからクエリウィンドウを閉じる。ウィンドウを閉じるタイミングを誤ると未確定のまま自動的に巻き戻るなどの不整合が生じる。  

参考（実装に関する根拠）
- VBA が SQL をテキストに出力し、実行は人が行う運用である点、トランザクション／バックアップ／件数確認の設計は VBA 実装で確認済みです（AppendLine による出力、SET XACT_ABORT ON / BEGIN TRAN / SELECT @@ROWCOUNT / SELECT @@TRANCOUNT の位置など）。
