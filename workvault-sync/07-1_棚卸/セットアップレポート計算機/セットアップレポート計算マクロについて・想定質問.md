Q1: マクロの実行順序  
A1:

1. EG_Import → HAIRETSU_Import → SETUPREPORT_Import で各データを取り込む
2. 計算結果_整形シートで自動照合
3. GenbaList（現場部品リスト）を作成・目視確認
4. 不足部品リストを出力
5. idouSQL で SQL テキスト生成 → 人が開いてバックアップ/更新件数を確認し、DB に適用

Q2: GenbaList を実行しないとどうなりますか？  
A2: シリアル列にヘッダー文字や古いデータだけがある状態でも idouSQL が動いてしまい、リールだけを移動指示してしまう恐れがあります。必ず GenbaList → D列の実データを目視確認してください。

Q3: テーブル番号 14 を除外している理由は？  
A3: 現行マクロでは Field8（テーブル番号）が 14 の行を対象外にしていますが、理由は手順書に記載がありません。  
要確認: 除外理由（仕様的・運用的根拠）は手順書・仕様書で明確化する必要があります。

Q4: idouSQL で 0 件判定された場合の対応は？  
A4:

- 警告が出たら処理を中止し、GenbaList の出力結果（対象シリアル数）とマクロ実行!A55 の移動先コードを再確認します。
- 本当に対象が 0 件で正しい場合は中止して問題ありません。

Q5: バックアップテーブルの保管期間や削除ルールは？  
A5:

- マクロ名: SELECT INTO で `T_在庫データ_移動前BK_yyyymmdd_hhnnss` を作成しますが、保管期間・運用ルールは未定義です。  
    要確認: 保管期間・削除タイミング・担当者を運用規定に追加してください。

Q6: FaildSplice_OK はいつ使えば良いですか？  
A6:

- 原則使わず、現物のスプライシングを実施→セットアップレポート再出力が標準です。
- FaildSplice_OK は「どうしてもレポートを出し直せない例外時」に限り、Excel 上の取込データを書き換える専用ツールです。  
    要確認: 使用条件・承認者・記録方法を正式化し、運用手順に明記してください。

Q7: 計算結果_整形シートの A〜G 列と 20 列目の中身がわかりません。  
A7:

- GenbaList（現場部品リスト）を必ず作成・目視確認してから idouSQL を使う。見出し文字や古いリストだけが残っていると誤った対象でSQLが生成される。

- idouSQL はDBを自動実行しない。SQLテキストを出力するだけなので、tmp_sql.txt を開いてバックアップ取得・更新件数を確認し、担当者が COMMIT / ROLLBACK を選ぶ運用を徹底すること。

- バックアップ（SELECT INTO）には DB 側で CREATE TABLE 権限が必要。権限が無い環境ではあらかじめ差替え手順を用意しておくこと。

- 0件判定の落とし穴：現場部品リストにヘッダ「シリアル」が残ると0件
- FaildSplice_OK 等の例外用マクロは原則使用禁止。これを使うと Excel 内だけを書き換え、現物・EG‑Pro と不整合になるリスクが高い（例外的使用時は承認と記録必須）。

- 【2026-09-14訂正】旧記述は逆でした。EG‑Pro 在庫CSV は棚卸しでは Tanaoroshi 形式(Get_EG_Tanaoroshi.cgi)を使う。WhereHouse 形式はB列更新専用で、棚卸しに使うと在庫が全件0扱いのTanaoroshiと取り違えて合計が壊れる。根拠: [[セットアップレポート計算機]]、[[固定テーブル棚卸し方法_手順書]]。マクロ実行シートD6のリンク自体もGet_EG_Tanaoroshi.cgiを指している。

- 文字コードは取込時に UTF‑8 → Shift‑JIS へ変換する（ADODB.Stream を使用）。文字化けや列ズレがないか確認すること。

- 列参照はマクロで固定参照している（例：EGProシートの5列目がステータス、6列目がロケーション等）。取り込んだCSVの列順やヘッダが想定と異なると処理が崩れる。

- スプライシング（リールのつなぎ）関連の行はメイン側／後側で扱いが分かれるため、スプライス有無の判定・出力結果を必ず確認すること。
- idouSQL ではシリアルを文字列として IN 句に連結する際、単一引用符のエスケープ（' → ''）を行っているが、生成されたSQLを必ず開いてエスケープや構文を確認すること。
- マクロの実行順・サブルーチン順序を誤ると（例：main() の安易な再実行）EG‑Pro値や理論値が上書きされる恐れがあるため、手順書の順序に従うこと。
- 所在不明抽出（tana）は「ステータスが貯蔵以外」を基準に抽出する設計になっている。タイミングは「すべての入庫処理が完了した後」に実行すること。

運用上の必須確認項目（チェックリスト）

- 取込ファイル：EGPro（棚卸しはTanaoroshi形式。WhereHouse形式は別用途なので取り違えない）、セットアップレポート（UTF‑8）、配列データが正しいか。
- 文字化け・列ズレの有無（特に材料バーコード＝シリアルが9列目で取り込まれているか）。
- GenbaList を作成し、D列（シリアル）に実データが並んでいることを目視確認。
- マクロ実行!A55（移動先ロケーション）が空でないか、数値かを確認。空欄/非数値なら処理を中止する仕組みあり。
- tmp_sql.txt の先頭にバックアップ取得・トランザクション枠があるか、想定の対象件数コメントが正しいかを確認。
- SQL 実行は担当者が DB で更新件数を確認してから COMMIT を行うこと（切り戻しSQLはコメント状態で出力される）。
- 例外処理を運用化する場合は、使用条件・承認者・実行記録（誰がいつ何をしたか）を必ず定義する。DB側に実行者記録は残らないため、別途作業記録を残す必要がある。
