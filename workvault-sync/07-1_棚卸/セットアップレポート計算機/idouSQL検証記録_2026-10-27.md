# セットアップレポート計算機原本_v2.0 の SQL生成プロシージャ(idouSQL)検証記録

## 概要

`\\nksv569\...\篠原\セットアップレポート計算機原本_v2.0.xlsm` のVBA内にあるSQL生成プロシージャを検証した。Docker上のSQL Server 2022で生成SQLを実際に実行し、動作を確認した。

## 対象の特定

- SQL生成プロシージャは `Module1` の `Sub idouSQL()`(698〜857行目)のみ。他モジュールにSQL生成は無い(SELECT/UPDATE等の文字列は Select Case 等の誤一致のみ)
- 動作: 「現場部品リスト」D列のシリアルを「マクロ実行」A55のロケーションへ移動するT-SQLを組み立て、テキストファイルに出して開く。DB自動実行はせず、人がSSMSで確認してから流す方式
- 生成物: バックアップ退避(SELECT * INTO)→ SET XACT_ABORT ON → BEGIN TRAN → UPDATE(ロケーション/ステータス/ライン/設備/Z軸/更新日時)→ 更新件数・未確定トランザクション数の表示 → 操作手順コメント → 切り戻し用コメントブロック

## 検証方法

1. VBAソースの忠実な再現: Module1.bas(CP932)から idouSQL ブロックの AppendLine 文66本を原文のまま抽出し、式評価器(VBAの & 連結・文字列リテラル・Format(Now)・4変数のみ対応・未知の構成要素はエラー)で評価して生成SQLを組み立てた。テンプレートはVBA原文なので、生成SQLは実コードから導出可能。serialList組み立て・3ガード(空/非数値/0件)は移植し、原文と突合
2. Docker: SQL Server 2022 コンテナに、生成SQLが参照する2データベース([EGProKOHDEN-Warehouse].T_在庫データ + [EGProKOHDEN-MST].M_ロケーション)を列名推定で作成し、生成SQLを1バッチとして実行(SSMSのF5と同型)。COMMIT/ROLLBACKは同一バッチ末尾への付加で再現(手順書どおり同一セッション内での確定/取消に対応)
3. 検証スクリプト: `C:\work\sql_verify\`(gen_sql.py・run_tests.py・fixtures.sql・gen/*.sql)

## 観察点(不具合ではなく動作の性質)

1. ROLLBACKしてもバックアップ表は残る: SELECT * INTO が BEGIN TRAN の前(自動コミット)のため。移動前データは失われないので害は無い
2. 切り戻しブロックは更新日時をGETDATE()に設定する: 元の更新日時は復元されない(バックアップ表には残っている)
3. MST未登録のロケーションコードを入れるとSQLはそのまま通り、ステータスコードがNULLになる: VBAのガードは「数値か」のみ。現場でA55に入力する値はM_ロケーションに実在するコードかの確認が別途必要(SSMSでの実行前確認が効く場面)

## 限界

- fixtureのテーブル定義は生成SQLから参照される列名からの推定。実DBの列型・制約とは異なる可能性がある(検証は生成SQLのロジックが正しいことの確認であり、実DBでの結果を保証するものではない)
- MsgBox/WSH出力部分は実行していない(VBA側ガードは静的確認+条件再現)。生成テキストの書き出し(Print #)はANSI(CP932)で行われるため、実環境のSSMS貼り付け時も文字化けは無い想定だが実機未確認
