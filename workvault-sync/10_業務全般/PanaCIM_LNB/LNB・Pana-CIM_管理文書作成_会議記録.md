# LNB・Pana-CIM 管理文書作成 会議記録

## 3. 再起動

| 項目 | 内容 |
| --- | --- |
| 実施時期 | 月に一度、SMT点検日の朝 |
| 実施条件 | Pana-CIMが動いていないこと |
| 根拠 | SMTはラインが全く動かない日がある。Eg-Proは部品管理と絡み点検日を決めにくい |
| 記載先 | 管理手順書に手順として記載する |
| チェックシート | 「再起動しましたか」を月次の必須確認項目とする |
| 残る運用 | 異常発生時の随時再起動は従来どおり残る。定期と随時の二本立てになる |

点検の周期は日次とする。再起動のみ月次。

## 4. 相関図

目的は二つある。点検実行者がシステム間の関係を視覚的に把握すること。異常発生時に原因箇所を特定すること。ER図はデータベースの実体と関連を表す記法のため用いず、次の二層で作る。

| 層 | 内容 |
| --- | --- |
| 第一層 システム相関図 | 全体を一枚に収める。対象はPana-CIM、LNB、DGS、稼働モニタ、アンドン、SMT設備側の端末 |
| 第一層の箱に書く情報 | システム名、設置場所、管理担当、点検対象か、再起動の可否 |
| 第一層の線に書く情報 | データ名称、向き、自動か手動か、更新の頻度 |
| 境界の扱い | Eg-ProとAsprovaは箱を一つ置き、中身は描かない。別チーム管理と注記する |
| 第二層 事象別の切り分け図 | 一事象に関わる経路だけを抜き出す。初版はアンドン異常発生時と稼働モニタ異常発生時の二枚 |

粒度の基準は次の一文で判断する。その箱が止まったときに点検実行者の取る行動が変わるなら箱を分ける。変わらないなら一つにまとめる。第一層が一枚に収まらない場合は粒度が細かすぎるとみなし、統合する。

## 6. トラブルシューティング

| 項目 | 内容 |
| --- | --- |
| 記載する事象 | アンドン異常発生時、稼働モニタ異常発生時 |
| 対処 | いずれも再起動 |
| 併記するもの | 正常に動いている画面 |
| 前提 | 稼働モニタはPana-CIMから出力されている |
| 目的 | 問題発生時の解決を早め、知見を蓄積する |
| 現状 | 発生中の不具合はない。想定される不具合を先に書き出す |

記録媒体はPC上のフォームとする。紙は更新しにくい。入力項目を固定できるため記録の粒度がそろい、蓄積が表として残るため検索と集計ができる。

記入項目の案

| 区分 | 項目 |
| --- | --- |
| 発生 | 発生日時、気づいた人、気づいた経緯、発生場所 |
| 事象 | 事象の種別（選択式）、画面の表示、添付画像 |
| 影響 | ラインを止めたか、影響範囲、相関図上のどの箱か（選択式） |
| 対応 | 実施した操作、連絡先、復旧の可否、復旧までの時間 |
| 事後 | 原因、再発防止の要否、手順書へ反映したか |

管理手順書のトラブルシューティングの章からフォームの蓄積を参照先として指す。文書本体に事例を書き写さない。

## 7. チェックシートの項目

埋まっているのは再起動の確認のみ。残る候補は次のとおり。

| 候補 | 確認すること | 頻度 | 正常とみなす状態 |
| --- | --- | --- | --- |
| 稼働状態の確認 | 稼働モニタとアンドンの表示 | 日次 | 要確認 |
| バックアップ結果の確認 | 最終実行日時と成否 | 日次 | 要確認 |
| 保存領域の確認 | 空き容量と増加傾向 | 要確認 | 要確認 |

判定基準は実機の画面を見ながら決める。

これ以外に検討する論点

| 論点 | 理由 |
| --- | --- |
| 復旧の確認 | 取得できていても戻せるかは別。実施条件と頻度を決める |
| LNBの点検項目 | 項目名すら定まっていない。相関図の作成と並行して洗い出す |
| 記録の確認者 | 記録するだけでは検知の遅れを防げない。誰がいつ見るかを項目に入れる |
| Windows更新後の扱い | RPA機では更新の翌日に再起動する決まりがある。同じ扱いにするか |
| 随時再起動 | チェックシートに随時実施の記入欄を設けるか |

会議のメモ:

サーバー運用の標準化とリスク認識: ISHIIとKURABAYASHIは、デッドロックやバックアップ停止を契機に、サーバー運用を特定者の知識に依存させず、管理・点検・復旧手順を文書化して定期確認する方針を確認した。
障害の経緯: 8月のデッドロック発生を受けてサーバー再起動を実施した際、サブサーバーへの自動バックアップが正常に動作していなかったことが判明した。バックアッププログラムは見直され、現在は復旧しているが、過去の一定期間にバックアップが取得できていなかった。
検知体制の不足: 自動処理が設定されていても、実際にバックアップが取得されているかを確認できていなかったため、定期点検、ログや最終実行結果の確認、保存データの確認を運用に組み込む必要があると整理された。
属人化への対応: 操作・復旧方法やシステム構成の知識が特定の担当者に偏り、責任範囲や異常時の判断・連絡先も曖昧だった。今後は機器構成、データの流れ、設定、保存先、復旧方法、関係者を文書化し、担当者の交代や不在時にも対応できる状態を目指す。
段階的な文書化: 最初から完全な手順書を作るのではなく、まずサーバー管理と定期点検に必要な内容を整備し、運用中に課題や不足項目を抽出して改訂する方針が示された。過去のトラブル対応例やデッドロック時の処置も、再利用可能な事例として手順書に反映する。
管理範囲と文書体系の決定: ISHIIらは、対象をPana-CIMとEg-Proを中心とするシステム単位で整理し、操作手順、管理手順、点検チェックシート、復旧・トラブルシューティングを分けて整備する方向で合意した。
対象範囲: 標準化の対象は、会議中の整理に基づきPana-CIMとEg-Proを中心とする範囲とし、それぞれについて対象機器、関連システム、データ、設定、保存先、関連作業を明確化することになった。共通化できる管理項目と、システム固有の操作手順は分けて扱う。
文書の分け方: 既存の操作資料との重複や運用上の分かりにくさを避けるため、システムごとに操作手順書と管理手順書を分け、さらに定期点検用のチェックシートを設ける方向で議論された。必要に応じて復旧手順やトラブルシューティングも各システムの文書に含める。
手順書の内容: 手順書には目的、適用・除外範囲、機器構成、関連システム、実施方式、確認方法、失敗時の処置、日常・定期管理、異常判定、エスカレーション、変更承認、改訂履歴、教育・引継ぎ、保管場所を盛り込む。バックアップについては取得結果だけでなく、復旧可能性の確認、記録、レビューまで定義する。
登録と改訂: 文書は既存の社内文書管理の登録ルールに合わせて保管し、操作・管理・点検の資料を追跡できる形にする。点検頻度や記録様式など、会議時点で確定できない細部は各チームが作成時に検討し、運用結果を踏まえて改訂する。
責任体制と作業権限の明確化: ISHII、KURABAYASHI、茂木さんらは、管理責任者と主担当・副担当を明確にし、サーバー操作は権限付与と教育を受けた担当者に限定する方針を確認した。
責任者の設定: 管理責任者は茂木さん、ISHII、副担当・主担当側にKURABAYASHI、茂木さんを含む体制で進める方向となり、トラブル時はこの中心メンバーが対応することになった。最終責任、日常点検、代行、専門支援の役割を文書上で分けて明記する。
操作権限: これまでサーバーを誰でも触れる状態にしていたことがトラブル要因になり得るため、今後は管理責任者の権限の下で、教育・訓練を受けた人だけが操作できる仕組みにする。担当者が不在の場合の連絡先、代行者、相互確認も事前に定める。
立会い確認: 単に起動作業を実施するだけでなく、第三者が操作内容を確認し、誤操作や異常をその場で検知できるようにすることが重要と説明された。立会いによってメーカーや関係者への確認を早め、生産への影響を抑えることを狙う。
現場作業者の扱い: 教育を受けたオペレーターに一定の操作を担わせる案が出た一方、トラブル対応まで現場作業者に負わせるのは適切でないため、操作担当と障害時の責任担当を分ける必要があると整理された。茂木さんと松井さんが、具体的な教育対象者と役割分担を持ち帰って検討する。
文書作成チームとスケジュール: ISHIIは、参加者を二つのチームに分けてPana-CIM／Eg-Pro関連の文書を作成し、石井さんと茂木(絵)さんが進捗を管理しながら、2026年12月末までの登録と2027年1月からの試行運用を目指す方針を示した。
チーム編成: 一人に全作業を集中させず、知識を持つメンバーを分散して二つのチームを編成する方針となった。チームごとに対象システム、点検項目、実施頻度、記録方法、必要なトラブル対応を具体化する。
進捗管理: 石井さんと茂木(絵)さんが主リーダーを務め、各メンバーが担当部分に責任を持って作成する体制とされた。各チームは役割と期限を設定し、進捗を確認しながら文書を完成させる。
完了期限: 最終期限は2026年12月末とし、各文書を社内登録できる状態まで仕上げる。期限だけでなく、未決事項が残る場合は確認方法、担当者、期限を明記することが完了条件とされた。
試行運用: 登録後は2027年1月から仮トライアルを開始し、約3か月運用しながら実際の点検・管理手順を確認する。試行中に不足や問題を抽出し、手順書を改訂する予定である。
