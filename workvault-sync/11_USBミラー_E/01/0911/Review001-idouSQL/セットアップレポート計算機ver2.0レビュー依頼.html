セットアップレポート計算機 ver2.0 レビュー依頼

依頼者 篠原 想詩　/　レビュー担当 倉林 様
作成日 2026-09-07　/　対象 倉庫移動SQL生成処理 idouSQL

見ていただきたいのは、倉庫移動SQLを組み立てる idouSQL の一箇所です。原本と ver2.0 を突き合わせた結果、在庫データの取り込み、各種リストの印刷、所在不明リールの抽出、現場部品リストの作成といった処理はすべて原本と同一で、手が入ったのは idouSQL に限られます。確認はここに絞っていただければ足ります。

どこから見始めればよいか

お忙しいなか恐縮です。次の順に進めていただくと、確認箇所を最短でたどれます。他のプロシージャは開く必要はありません。

  • VBAエディタ（Alt+F11）で両ファイルを開き、Sub idouSQL() を検索する。原本・ver2.0とも、このプロシージャはコードの一番最後にあります（GenbaListの次）。
  • まず原本の idouSQL を見る。UPDATE文を組み立ててファイルに書き出し、そのまま開くだけの短い作りです（確認もバックアップもトランザクションもありません）。
  • 次に ver2.0 の idouSQL を見る。原本と同じUPDATE本体の前後に、安全確認の処理が挿入されています。ver2.0では idouSQL の直前に AppendLine という短いヘルパーが1つ増えている点だけ先に把握しておくと読みやすくなります。
  • 下の「生成SQLの違い」と「確認していただきたいこと」を照らしながら、追加された安全機構が意図どおり入っているかを見る。
  • 確認し終えたら、末尾の記入欄に結果を入れて返送する。

idouSQL 以外は原本と ver2.0 で一致しているため、読み比べる必要はありません。まず idouSQL、それも「UPDATEの前後に何が足されたか」に注目してください。

今回の改修は、原本にはなかった安全機構をまとめて追加したものです。原本の idouSQL は、確認画面もバックアップもトランザクションもなく、本番テーブルへのUPDATE文を生成してそのまま開いていました。ver2.0 はここに歯止めを何重にも入れています。危険性を増やす変更ではなく、逆に大きく減らす方向の改修です。

なぜ直したか

原本の倉庫移動SQLは、移動先ロケーションが空でも数字でなくてもそのまま埋め込み、対象が0件でも IN() という壊れたSQLを作り、内容を確認するメッセージも出さずにUPDATE文を書き出していました。バックアップもトランザクションもないため、間違ったSQLを実行すれば在庫データがそのまま書き換わり、元に戻す手立てもありません。この状態を放置すると、押し間違いや入力漏れがそのまま在庫の誤更新につながります。そこで、実行前に止める仕組みと、実行後に戻せる仕組みを入れることにしました。

何を変えたか

処理の骨格は同じまま、前後に安全確認を足しました。移動先ロケーションが空や非数値なら理由を出して止め、対象が0件でも止めます。シリアルに引用符が混ざっても壊れないよう二重化し、出力前に移動先と件数を見せて押し間違いを防ぎます。更新の前に対象行を日時付きのバックアップテーブルへ退避し、UPDATE本体はトランザクションで囲んで、件数を見てから確定か取り消しを選べるようにしました。あわせて未確定トランザクション数の表示と操作手順、切り戻し用SQLの雛形、完了時の注意メッセージを加えています。

生成SQLの違い

【原本】UPDATE文をそのまま生成して開くだけ
- UPDATE [...].T_在庫データ SET ロケーションコード = (A55の値) ...
- WHERE シリアル番号 IN(...); （確認・バックアップ・トランザクションなし）
【ver2.0】前後に安全機構を追加
+ SELECT * INTO [...].[移動前BK_日時] ... （更新前をバックアップ退避）
+ SET XACT_ABORT ON; BEGIN TRAN;
UPDATE [...].T_在庫データ SET ロケーションコード = ..., 更新日時 = GETDATE()
WHERE シリアル番号 IN(...);
+ SELECT @@ROWCOUNT AS 更新件数; -- 想定件数と照合
+ SELECT @@TRANCOUNT AS 未確定トランザクション数;
+ -- 一致なら COMMIT TRAN、不一致なら ROLLBACK TRAN の行だけを実行
+ -- 全文の再実行禁止。ウィンドウを閉じない。確定後は0を確認
+ -- 切り戻し用UPDATE（バックアップから復元）の雛形を併せて出力

確認していただきたいこと

追加した安全機構が意図どおり働き、原本より危険性が下がっていると言えるか、次の点を見てください。確認できた項目にチェックを入れてください。

  • ロケーションの空欄・非数値チェックと0件チェックが、壊れたSQLの生成を確かに止められている
  • 更新前のバックアップ退避が、UPDATEより前に実行される順序になっている
  • トランザクションの構造が正しく、件数を見てから確定・取消を選べる作りになっている
  • 引用符の二重化により、シリアルに特殊文字が混ざってもSQLが壊れない
  • DBへ自動実行せず、人が確認して手で流す運用が原本から変わっていない
