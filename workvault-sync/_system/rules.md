**下位構成・件数・個別の判断表は `_system/保管庫マップ.md` が持つ（P-012）。**
§2 は「どのフォルダがあるか」、保管庫マップは「何がどこにあるか」を担当する。
階層を変えても本ルールの改訂は不要。

**フォルダ名の差分について（P-002）。** 提示された構成と実体が7箇所ずれていたが、
**`03_Thinking`→`04_Thinking`、`解決課題`→`09_解決課題`、個別フォルダ→`20_Projects/` への

得るのは階層が1段深くなることだけで、案件は4件しかない。

棚卸しを触るときは3種類を同時に開くため、種類で割ると毎回フォルダを往復することになる。
2026-09-25 にこの方針で `07-1_棚卸` へ4件を集約した。

## 3. フロントマター

```
---
type:    note | task | spec | report | idea
phase:   develop | operate | maintain | organize
status:  active | waiting | done | archived
project: 案件名（なければ空）
updated: YYYY-MM-DD
---
```

**開発/運用/保守/整理はフォルダではなく `phase` で表す。** 横断ビューは Bases で作る。

## 4. 操作権限 Tier

### Tier A（自動実行・事後報告のみ）

- フロントマターの付与、`updated` の更新
- Daily / Weekly の生成
- `decision-log.md` への追記
- `Todo.md` の非固定領域を、移送完了後に空にする

### Tier B（提案 → チャットで承認 → 実行）

- ノートの移動、`99_archive` への退避
- 新規フォルダの作成
- 0バイトファイル等の削除

### Tier C（提案のみ・実行禁止）

- フォルダのリネーム・統合・削除
- `rules.md` / `taxonomy.md` の書き換え
- 一度に20件を超えるファイル操作

**ハーネス側の制約:** 削除操作は分類器が「Irreversible Local Destruction」で止めることがある。
その場合は候補一覧とコマンドを提示し、本人に実行してもらう。

## 5. 分類ルール（上から順に判定）

1. 緊急 / 新規設計 / 改修要 → `解決課題/`
2. 単発の行タスク → `00_inbox/Todo.md`
3. 複数ステップ・期限ありの案件タスク → `05_Tasks/`
4. 特定案件に属する資料 → その案件のフォルダ（`07-1_棚卸` 等）
5. 業務の汎用ナレッジ → `10_業務全般/`
6. 判定不能 → **移動せず** `pending.md` に記録して質問する

### USBミラーをやめた理由（2026-10-13）

**`11_USBミラー_E` は「USBの写し」として保護していたが、保護する前提が崩れていた。**

| 前提 | 実際 |
|---|---|
| USBが壊れたら写しから戻す | **E: は空で `FOUND.000`/`FOUND.001` だけが残っていた。USBは既に一度壊れている** |
| 写しなのでパスごと残す価値がある | **1,619件のうち1,064件（802 MB）は保管庫の他の場所と内容が同一だった** |
| 編集しないので安全 | **固有分が案件フォルダに届かず、USBミラーの中だけで埋もれていた** |

**埋もれていたものの例。**

- `buckup/15575/BK/bk/*.cgi`（32本）— **`05_Tasks/WIP.md` 1番が「見つからない」と書いていた cgi 一式**
- `01/SSMS/*.sql`（23本）— `T_在庫データ` `T_在庫ログ` `T_作業ロス数` 等のクエリと修正パッチ
- `01/在庫管理システム関連データ/差異の発生理由について.txt` — 在庫差異の説明
- `97_引用資料/富岡サーバーの構築/`（46件）— サーバー構築・証明書・HDD交換の記録
- `98_Pass/passwordfile.md` — **本体側から消えていた認証情報**

**「触らないフォルダ」にしていたことが、中身を見ない理由になっていた。**
**写しを守るより、中身を正しい置き場へ出すほうが先だった。**

### 代わりの方針

**業務USBから取り込んだものは、ミラーとして置かずに最初から案件フォルダへ振り分ける。**
振り分け先が決まらないものは `00_inbox/` に置き、`pending.md` へ起票する。
**「あとで見る置き場」を作らない。**作ると見ない。

`12_用語集PoC` も同じ形だった（wheels込み304MBを除外対象にしていた）。
**除外対象にしたフォルダは、容量が増えても中身が古くなっても気づけない。**

---

**`07_specs/` は使わない（P-005）。** 仕様書は案件フォルダへ置く。
書類の種類でフォルダを割らない方針（§2）と衝突するため、分類先から外した。
フォルダ自体は空のまま残す。削除は Tier C で手間が見合わない。

**Zettelkasten は本ルールの対象外（P-004）。** 個人的な着想・学習は `life-log` スキルが
書き先を持つ。Work_Vault は消えると困る業務記録、Zettelkasten は思いついたら書く場所で、
要求される厳密さが違う。同じ承認フローを被せると後者が書かれなくなる。

## 6. 維持ルール

### 00_inbox

**統合は Tier A、削除は Tier B（P-003）。**
00_inbox から正本への統合・上書きは承認不要。**削除だけ承認を要する。**
統合は間違えても Drive の版履歴から戻せるが、削除は戻せない。
**取り消せるかどうかで線を引く。** 全面 Tier B にすると inbox が受け皿として機能しない。

- ToDo以外は移動先を決めて移す
- `Todo.md` は `<!-- FIXED:START -->` 〜 `<!-- FIXED:END -->` の間のみ恒久保持。
  それ以外は完了・移送後に削除する
- **2026-09-30 に FIXED マーカーを挿入済み（P-006）。** 自然文の「本文章より上側」だと
  範囲が読み手の解釈になり、実際に削除範囲を判断する場面があった。マーカーなら機械的に決まる

### 拡張子の無いファイルの受け入れ手順（P-011、Tier A）

**00_inbox で拡張子の無いファイルを見つけたときは、次の順で処理する。**

1. **中身を読む。**先頭の見出しかフロントマターを見る
2. **`.md` を付ける。**Markdown として読めるなら `.md`。読めないなら中身に合う拡張子
3. **見出しに合わせて改名する。**`QA` のように中身が分からない名前は、見出しの文言へ寄せる
4. **移動先は通常の分類ルール（§5）で決める**

拡張子を付けるのは中身を変えない操作で、間違えても付け直せるため Tier A とする。
**3（改名）を省かないこと。**拡張子だけ付けても、一覧から内容が分からない状態は残る。
**経緯:** 社用PCからの持ち出しで拡張子が落ちる。2026-10-02 に8件発生（`QA` ほか）。

### ルート直下

- **フォルダのみを置く。** ファイルを検知したら移動を提案する
- 1MB超の添付・HTMLは Vault 外への退避を提案する

### アーカイブ・削除

- `updated` から90日経過 かつ `status` が active/waiting 以外 → `99_archive` へ移動提案
- 0バイトファイルは削除ではなく**復元候補**として報告する。
  原因は2台同時オープンで、中身は Google Drive の版履歴に残っている可能性がある

## 7. 変更記録

Tier B / Tier C を実行したら、**同一セッション内で必ず記録する。**

- 保存先: `02-2_Weekly/changelog/`（`03_Weekly/` は実在しないため変更）
- ファイル名: `YYYY-MM-DD_changelog.md`
- 記載: 実行日時 / 対象 / 変更前→変更後 / 理由 / 未処理・要確認事項

## 8. レポート

- **Daily:** 当日の完了ToDo・新規ノート・未処理を `02_Daily/Daily Report YYYY-MM-DD.md` へ。
  **様式は `01_Templates/様式/Daily report.md`、生成は `01_Templates/プロンプト/業務日報作成プロンプト.md` に従う**
- **Weekly:** 毎週金曜、当週Dailyを集約して `02-2_Weekly/YYYY-Www.md` へ。
  構成は (1)実施内容 (2)完了 (3)未完了と理由 (4)来週の重点 (5)解決課題の残件 (6)自己レビュー

**営業日のない週は作らない。** 2026-09-19〜23 のシルバーウィークのように、
書くことが無い期間に空のレポートを作ると、後から「書き忘れ」と区別がつかなくなる。

## 9. 自己成長

### 判断ログ（Tier A）

分類・移動のたびに `decision-log.md` へ1行。ルールに無い判断は ルールID = `AD-HOC`。

### 新規フォルダの提案条件（すべて満たす場合のみ）

- 同一テーマのノートが5件以上
- 最初と最新の作成日が14日以上離れている
- 既存フォルダの受け入れ条件に合致しない

### ルール改訂の起票条件

`proposals.md` へ起票する。

- 同種の AD-HOC が3回以上 → 明文化を提案
- `pending.md` の同種保留が2件以上 → 判定基準の追加を提案
- 既存ルールが連続2回 実態と合わなかった → 改訂を提案

### 承認・却下

- **承認時のみ** `rules.md` を更新。version +0.1、last_updated 更新
- 更新前を `rules_history/rules_vX.X.md` に残す
- 却下も `proposals.md` に理由つきで記録し、同一提案を再提出しない

---

## 10. 安全則

- 既存ノート本文を、要約・整形を理由に短縮・削除しない
- `rules.md` を承認なく書き換えない
- 自身の禁止事項・Tier区分・承認プロセスを緩める方向の改訂は提案しない
- 「学習した」「記憶した」と言わない。**ファイルに記録したか否かで表現する**
- 判断に迷ったら実行せず質問する
- **絵文字を使用しない**
