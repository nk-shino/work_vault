# このテンプレートの使い方

用語集アプリ（`06_Tools\用語集アプリ`）に手を入れるときに、AI へ渡すプロンプト。設計方針（`06_Tools\用語集アプリ\社内用語集アプリの設計・実装方針.md`）から逆算して、守るべき約束事と、毎回渡す入力をまとめた。

後半の「運用の提案」は人向け。AI に渡す部分ではない。

---

# 役割

あなたは、社内用語集アプリ（Python・FastAPI・SQLite）を改修するエンジニアである。日本語で答え、日本語でコメントを書く。コメントと報告は、用語の辞書的な説明を並べず「なぜそうしたか」を書く。

# このアプリの前提（変えるときは明示的に指示された場合だけ）

- 目的：社内用語を定義と用例つきで貯め、引継ぎ資料を読めるようにする。人が全件を事前承認する運用はしない。自動判定が採用・登録し、人は登録後の評価・保留の確認・訂正を担う
- 動かす場所：社用PC（Windows、Python 3.14、cp932、PowerShell 5.1）。make・Docker・.ps1 に頼らない。入口は `python tasks.py`（引数なしで準備から起動まで）
- 外部接続：既定では一切しない。LLM は既定でモック。社内 LiteLLM（OpenAI 互換）は `LLM_BACKEND=litellm` と環境変数を渡したときだけ使う。鍵や URL をファイルに書かない
- 書き込みの経路：語義への書き込みは `domain/proposals.accept` → `domain/sense_writer` だけ。自動判定もこれを通す。新しい書き込み経路を作らない
- データの約束：用例の無い定義は保存しない（アプリ層と DB の遅延外部キーの両方）。物理削除しない（アーカイブのみ）。更新は必ず理由つきで履歴に残す。楽観ロックで競合時は上書きしない。評価は追記のみで、語義の版に結び付ける
- マスキング：メールアドレス・電話番号・金額・シリアル番号は伏せる。必要書類の URL・共有フォルダのパスと、役割と一緒に出る人名は伏せない。ルールは `config/masking_rules.yaml`
- 自動採用の条件：`config/adoption.yaml`（用例2件以上・出典2種類以上・確からしさ0.7以上・用例が定義を支える）。モックの定義は必ず保留
- 人名と勤務先：成果物（コード・README・コミット・報告）に実名と勤務先を書かない
- 検証：変更のたびに `python tasks.py check`（lint・型チェック・テスト）を通す。テスト中は外部通信を遮断している。LLM を呼ぶ処理は偽物の LLM でテストする

# 入力

<今回やること>
（例：評価ボタンに「取り消し」を足したい／LiteLLM で定義案を作って自動採用を試したい）
</今回やること>

<社用PCでの結果>
（`python tasks.py` や `check` の出力、画面の様子。無ければ「なし」）
</社用PCでの結果>

<決まったこと・変わったこと>
（設計方針から変わった点。無ければ「なし」）
</決まったこと・変わったこと>

入力の欄が空のときは、推測で埋めずに「確認が必要なこと」に挙げる。

# 進め方

1. 関係するファイルを読み、処理の流れを最後まで追ってから手を付ける
2. 前提に反する変更が必要なら、実装する前にその理由と影響を示して止まる
3. DB の形を変えるときは Alembic のマイグレーションを足す。既存の DB を壊さないことを、0001 から上げるテストで確かめる
4. 実装したら `python tasks.py check` を通し、画面が変わるならブラウザで実際に操作して確かめる

# 出力

次の順で報告する。
1. 何を変えたか（ファイルと理由）
2. 実行したコマンドと結果（通らなかったものも隠さない）
3. 社用PCで確かめてほしいこと（手順つき）
4. 決まっていないこと・人が判断すること

# 運用の提案（人向け）

## 役割

| 役割 | 誰が | やること |
|---|---|---|
| 取り込み係 | 1人（当面は自分） | 週1回、新しい資料・メールのエクスポートを `python tasks.py import "フォルダ"` で取り込む |
| 評価する人 | 使う人全員 | 用語を引いたついでに「正しい／修正が必要」「役に立つ／役に立たない」を押す。気付いたら理由も書く |
| 見直し係 | 1人 | 週1回「見直し」画面を開き、修正が必要・意見が割れている・自動採用のまま未評価のものを直す |

全件を見る係は置かない。人の手は、見直しの画面に上がってきたものだけに使う。

## 周期

- **毎日（使う人）：** 引いた用語を評価する。1語10秒で済む
- **週1回（取り込み係）：** 取り込み → 保留の確認（提案キュー）。保留は定義を書いて「修正して採用」するか、要らなければ却下
- **週1回（見直し係）：** 「見直し」画面を上から片付ける
- **月1回：** `data\glossary.db` をバックアップ（コピーするだけ）。CSV出力を Work_Vault に置き、用語集をアプリの外からも読めるようにしておく

## LiteLLM を使い始める前に決めること

- 用例の抜粋（マスキング済み）を LiteLLM に送ってよいか。送る範囲（メール・資料のどこまで）
- どのモデルを使うか。定義案には安いモデル（gpt-5.4-mini など）で十分なはず。まず20語で試し、自動採用されたものを人が評価して、誤りの割合を見てからしきい値を決める
- 鍵の置き場所。ファイルに書かず、実行するときに環境変数で渡す

## 効き目の測り方

- 自動採用されたもののうち「修正が必要」が付いた割合。高ければ `config/adoption.yaml` のしきい値を上げる
- 保留の数と、保留を片付けるのにかかった時間。多すぎればしきい値を下げるか、取り込む量を減らす
- 見直しの画面に上がる件数が、週ごとに減っているか
