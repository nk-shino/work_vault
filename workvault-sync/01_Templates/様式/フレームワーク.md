# SOP（標準作業手順書）のフレームワーク

## SOPとは

- Standard Operating Procedure
	決められた作業を、担当者が誰であっても同じ手順・同じ品質・同じ結果で実施できるようにするための文書。
	手順を文章として固定することで、作業のばらつき、属人化、引き継ぎ漏れを防ぐ。
	教育、監査、トラブル時の判断など、複数の場面で共通の拠りどころになる。
## 標準フレームワーク（構成順）

1. 管理情報
2. 目的
3. 適用範囲
4. 用語と定義
5. 責任と権限
6. 事前準備と安全上の注意
7. 作業手順本体
8. 点検と確認項目
9. 異常時対応
10. 記録と様式
11. 改訂履歴

## 各構成要素の役割

| 要素          | 記述する内容                                 |
| ----------- | -------------------------------------- |
| 管理情報        | 文書番号、版数、作成者、承認者、作成日と改訂日。最新版を識別できるようにする |
| 目的          | この手順で達成したいことを簡潔に述べる                    |
| 適用範囲        | 対象となる設備、システム、工程、部署。対象外の線引きも示す          |
| 用語と定義       | 略語や独自の呼称を定義し、解釈のずれをなくす                 |
| 責任と権限       | 実施者、確認者、承認者、管理責任者の役割分担を明記する            |
| 事前準備と安全上の注意 | 必要な道具、権限、前提条件、実施前の確認事項、禁止事項            |
| 作業手順本体      | 番号を振ったステップで、何をどうするか、どうなれば正常かを動詞中心に書く   |
| 点検と確認項目     | 何を、どの頻度で確認するか。正常と異常の判断基準を含める           |
| 異常時対応       | 想定される異常とその対処。連絡先やエスカレーションの基準を示す        |
| 記録と様式       | 実施の証跡を残すためのチェックリストや記録票                 |
| 改訂履歴        | いつ、誰が、どこを、なぜ変更したか                      |
## 良いSOPが備える条件

- 手順どおりに進めれば、初めての担当者でも同じ結果にたどり着ける
- 判断を要する場面には具体的な基準を書き、感覚的な表現に頼らない
- 運用と実態がずれてきたら改訂する
- 承認と版数管理によって、常に最新版が明らかである

## 管理書＋SOPの二層構造（複数システムの点検・保守を文書化するとき）

2026-09-16、PanaCIM・LNB点検文書の作成方針検討で採用。既存SOPフレームワークの「7. 作業手順本体」を、運用が決まっていない・検証環境がない状態で書き起こすときの補強パターン。

### 使う場面

- 新規の手順設計ではなく、現在実施している手順を後から文書化するとき
- 検証環境がなく、本番でしか手順の正しさを確認できないとき
- 頻度・役割・保守範囲などの「運用を決める情報」と、「その場で見ながら手を動かす操作」が同じ文書に混在しがちなとき

### 二層＋記録の構成

| 層 | 文書 | 様式 | 読む人 | 読む場面 |
| --- | --- | --- | --- | --- |
| 上位 | 管理書 | 管理規程型 | 運用を決める側 | 頻度や役割を決めるとき、見直すとき |
| 下位 | 点検手順書 | SOP | 実施者 | 実施中 |
| 記録 | 記録票 | チェックシート | 実施者と確認者 | 実施の都度 |

参照は上位から下位への一方向。管理書が「この項目群を日次で実施する」と定め、SOPが「その項目をこの画面でこう確認する」と書く。SOP側に頻度・役割・承認者を再掲しない（再掲すると変更のたびに両方を改訂することになる）。

### 分ける理由（一冊にまとめた場合との比較）

| 観点 | 二層に分ける | 一冊にまとめる |
| --- | --- | --- |
| 作業中の可読性 | 操作だけが並ぶ | 運用情報が操作の間に入り、読み飛ばす癖がつく |
| 改訂の影響範囲 | 変わった側だけ直す | 一行直すたびに全体を改訂 |
| 決定事項の所在 | 管理書に集まる | 手順の中に散る |
| 承認の対象 | 管理書と手順書で分けられる | 一括承認になる |

### 検証環境がない・本番のみという条件でSOPに足す三欄

一般的なSOPの型（上記「標準フレームワーク」の7〜9）には含まれない追加欄。試し実行で確認できない分、文書側に止まる仕組みを持たせる。

| 追加する欄 | 書く内容 | 対応する課題 |
| --- | --- | --- |
| 操作の種別 | 読み取りのみか、状態を変えるか | 読み取りと状態変更が同じ点検に混在すると、新人に危険な操作をさせてしまう |
| 取り消し可否 | 元に戻せるか、戻す方法 | 同上。戻せない操作ほど手前で目立たせる |
| 中断条件 | 想定外の表示が出たとき、進むか止めるか | 判断に迷った新人は「進む」を選びがち。止まる根拠を先に書いておく |

### 中身を埋める前の情報収集シート

聞き取り前に「A. 対象の定義」「B. 保守範囲」「C. 体制」「D. 実施条件」「E. 接続と認証」「F. 点検項目」「G. 異常時の対応」「H. 記録」の欄を持つ情報記入シートを1システム1部作るとよい。埋まった欄がどの文書のどの章へ転記されるかを記入欄自体に明記しておくと、聞き取りから文書化までの手戻りが減る。テンプレは [[LNB_点検文書_情報記入シート]] を参照（PanaCIM/LNB以外にも流用可）。

### この様式で解決しないこと

- 手順の正しさは保証されない。検証環境がなければ、経験者のレビューと立ち会いでしか確認できない
- 点検項目の網羅性も保証されない。聞き取りで挙がらなかった項目は載らない。一巡目で気づきを記録し、二巡目で追記する前提で運用する
- 様式を決めても中身は埋まらない。判定基準・接続先・実施者は別途確定させる必要がある
