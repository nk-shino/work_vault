# 01_基盤構築

# タスク:issue看板運用リポジトリの新規構築

以下の設定で「issue起点・人間は看板レビューのみ」の運用基盤を、
検証完了まで一気に構築する。作業は `20261013_issue-kanban-ops/` で行い、
段階ごとに宣言してから進める。

## 設定(埋め済み)
- リポジトリ名:{{例: task-board}}
- 公開区分:{{private または public}}
- 看板タイトル:{{例: task-board 看板}}
- レビュアー(GitHubユーザー名):{{例: ss80751}}
- 主な使い方:{{例: 調査タスク管理 / 開発タスク管理}}

## 前提チェック(実行前に必ず行う)
1. `gh` CLI の有無を確認する。未インストールなら `winget install GitHub.cli`
   を提案し、インストール後に `gh auth login` を案内して中断する
   (認証は人間が行う。勝手に進めない)。
2. `gh auth status` でログイン済みを確認してから以降へ進む。

## 構築手順
1. **リポジトリ作成**:`git init` → `.gitignore` 作成 →
   `gh repo create {{リポジトリ名}} --{{private|public}} --source=. --push`
2. **看板作成**:`gh project create --title "{{看板タイトル}}" --owner @me`
   → Project番号とIDを記録する。
3. **ステータス列の整備**:Project の Status フィールドに
   「Backlog / 作業中 / レビュー / 完了」があることを確認する
   (不足オプションは `gh project field-update` で追加)。
   各option IDを取得して `scripts/board.sh` に埋め込む。
4. **自動追加ワークフロー**:Project への issue 全自動追加を案内する。
   CLIで設定できない場合は GitHub UI の操作手順(Project → ⋯ →
   Workflows → Auto-add to project)を最後にまとめて伝える。
5. **雛形作成**(リポジトリにコミット):
   - `.github/ISSUE_TEMPLATE/task.md`:
     ゴール/受け入れ基準/既知情報([事実|推定|未確認]形式)/出典 の4項目
   - `AGENTS.md`:下記「運用ルール」をそのまま記載
   - `scripts/board.sh`:
     使い方 `board.sh <issue番号> <Backlog|作業中|レビュー|完了>`。
     内部で `gh project item-edit` を呼ぶ。完了列への移動は
     引数が「完了」かつ `--force` がない場合に拒否して、
     「完了列への移動は人間が行ってください」と表示する。
6. **検証**:
   - `gh issue create` でテストissueを作成 → board.sh で
     Backlog→作業中→レビュー を移動し、各回 `gh project item-list` で
     実際に列が変わったことを確認する(確認結果をログに残す)
   - 「完了」移動の拒否動作を確認する
   - テストissueをクローズして片付ける
7. **動作確認手順の納品**:ユーザーが最初のタスクを回す手順
   (issue作成 → レビュー → 完了移動)を3行で出力して終了。

## 運用ルール(AGENTS.md に書く内容)
- すべての作業はissue起点。issueなしで着手しない
- 着手時:計画をissueコメントし「作業中」へ。完了時:成果物と根拠を
  コメントし「レビュー」へ
- 「完了」列への移動はレビュアー({{レビュアー}})のみ。Claudeは
  `--force` が明示された場合のみ移動可
- コミットメッセージは Conventional Commits で `Refs #N` を付ける
- issueコメントの指摘は対応して再度「レビュー」へ

## 制約
- 秘密情報(APIキー等)をコミットに含めない
- 各ステップの実行ログを `20261013_issue-kanban-ops/実行ログ_YYYYMMDD.md`
  に残し、自然な停止点ごとにコミットする
