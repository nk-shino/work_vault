# 01_基盤構築

# タスク:issue看板運用リポジトリの新規構築

以下の設定で「issue起点・人間は看板レビューのみ」の運用基盤を、
検証完了まで一気に構築する。作業は `20261013_issue-kanban-ops/` で行い、
段階ごとに宣言してから進める。

## 設定(埋め済み)
- リポジトリ名:{{例: task-board}}
- 公開区分:{{private または public}}
- リポジトリ配置先:{{例: C:\Users\ss80751\repos\task-board}}。
  ワークスペース(kohden-code-workspace)の外に作る(AGENTS.md原則)。
  実行ログはワークスペース内 `20261013_issue-kanban-ops/` に置く
- 看板タイトル:{{例: task-board 看板}}
- レビュアー(GitHubユーザー名):{{例: ss80751}}
- 主な使い方:{{例: 調査タスク管理 / 開発タスク管理}}

## 前提チェック(実行前に必ず行う)
1. `gh` CLI の有無を確認する。未インストールなら `winget install GitHub.cli`
   を提案し、インストール後に `gh auth login` を案内して中断する
   (認証は人間が行う。勝手に進めない)。
2. `gh auth status` でログイン済みを確認し、`project` スコープの有無を
   確認する。スコープが無いと issue の看板追加・board.sh がすべて失敗する
   ため、`gh auth refresh -s project` を案内して実行してから進む
3. `git config --global user.name` / `user.email` を確認する。
   未設定なら新規リポジトリのコミットが必ず失敗するため、
   ユーザーに氏名とメールアドレスを確認して `git config --global` で
   設定してから進む(推測で設定しない)。

## 構築手順
1. **リポジトリ作成**:配置先フォルダで `git init` → `.gitignore` 作成 →
   `gh repo create {{リポジトリ名}} --{{private|public}} --source=. --push`
2. **看板作成**:`gh project create --title "{{看板タイトル}}" --owner @me`
   → Project番号を記録する。
3. **ステータス列の整備**:既定の Status フィールド(Todo/In Progress/Done)
   の選択肢はCLIでは編集できないため、**新しい単一選択フィールド
   「ステータス」を作成して使う**:
   `gh project field-create <project番号> --owner @me --name "ステータス"
   --data-type SINGLE_SELECT --single-select-options "Backlog,作業中,レビュー,完了"`
   → field ID を記録しておく(名前指定でも動くが、IDがあると確実)。
   看板のグループ化を「ステータス」に変更する手順を納品時に案内する。
4. **自動追加ワークフロー**:Project への issue 全自動追加を案内する。
   CLIで設定できない場合は GitHub UI の操作手順(Project → ⋯ →
   Workflows → Auto-add to project)を最後にまとめて伝える。
5. **雛形作成**(リポジトリにコミット):
   - `.github/ISSUE_TEMPLATE/task.md`:
     ゴール/受け入れ基準/既知情報([事実|推定|未確認]形式)/出典 の4項目
   - `AGENTS.md`:下記「運用ルール」をそのまま記載
   - `scripts/board.sh`:
     使い方 `board.sh <issue番号> <Backlog|作業中|レビュー|完了>`。
     実装は `gh project item-edit <project番号> --owner @me
     --url <issueのURL> --field "ステータス" --value <列名>` の
     名前指定方式(公式推奨。option ID の事前埋め込みは不要)。
     issue URL は `gh issue view <番号> --json url -q .url` で解決する。
     完了列への移動は引数が「完了」かつ `--force` がない場合に
     拒否して、「完了列への移動は人間が行ってください」と表示する。
6. **検証**:
   - `gh issue create` でテストissueを作成 → board.sh で
     Backlog→作業中→レビュー を移動し、各回
     `gh project item-list <番号> --owner @me --field "ステータス"`
     で値が変わったことを確認する(確認結果をログに残す)
   - issue 作成直後は自動追加ワークフローが「ステータス」を空のまま
     載せる(ワークフローはフィールド値を設定しない仕様)。
     board.sh が空欄から正常に値を設定できることをテストissueで確認する
     これが Backlog 初期配置の役割を兼ねる
   - 「完了」移動の拒否動作を確認する
   - テストissueをクローズして片付ける
7. **動作確認手順の納品**:ユーザーが最初のタスクを回す手順
   (issue作成 → レビュー → 完了移動)を3行で出力して終了。

## 運用ルール(AGENTS.md に書く内容)
- すべての作業はissue起点。issueなしで着手しない
- 着手時:計画をissueコメントし「作業中」へ。完了時:成果物と根拠を
  コメントし「レビュー」へ
- 「完了」列への移動はレビュアー({{レビュアー}})のみ。Claudeは
  `--force` が明示された場合のみ移動可
- コミットメッセージは Conventional Commits で `Refs #N` を付ける
- issueコメントの指摘は対応して再度「レビュー」へ

## 制約
- 秘密情報(APIキー等)をコミットに含めない
- 各ステップの実行ログを `20261013_issue-kanban-ops/実行ログ_YYYYMMDD.md`
  に残し、自然な停止点ごとにコミットする
