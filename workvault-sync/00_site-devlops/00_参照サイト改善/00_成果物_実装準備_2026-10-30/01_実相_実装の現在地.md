## 1. 先に知っておく落とし穴

ここを知らずに触ると、エラーも出ないまま壊れる。

| 落とし穴 | なぜそうなっているか | 踏むとどうなる |
|---|---|---|
| **`setup.ps1` を走らせてはいけない** | リポジトリ直下にある132行の初期構築用スクリプト。使い捨てなのに**gitに追跡されている**ので、正規の手順書に見える。`Test-Path` の確認も `-NoClobber` も無い `Set-Content` で、骨組みの文面を**無条件で書き込む** | 現物が消える。CSS 3,354行が十数行に、用語24件が `[]` に、`js/main.js` 184行が4行に戻る。内訳は下の表。git管理下なので追跡ファイルは `git checkout` で戻せるが、未コミットの作業（§2-2）は戻らない |
| `tsc` を片方だけ走らせない | `npm run build` は `tsc -p tsconfig.json && tsc -p tsconfig.hero.json` の2本立て。1本目の `include` は `src/**/*.ts` なので `src/hero/ambient.ts` まで拾い、`module: "none"` のまま `js/hero/ambient.js` を書く。正しい形は2本目が上書きして作っている | 1本目だけ走らせると `import * as THREE from "three"` が `require("three")` に化ける。ブラウザに `require` は無く importmap も効かないので、HOMEの3D層だけが黙って出なくなる。型検査は両方とも終了コード0で通るので、エラーは出ない。**`npm run watch` は1本目だけを見張る指定**なので、保存するたびにこの形が書かれる |

| `<head>` にインラインスクリプトを足すと配信が止まる | `tools/build-site.js` が `<script>` の開いたタグ数・`src` 付きの数・中身を拾えた数を突き合わせ、合わなければ**停止**する | 止まるほうが親切な側。拾い漏れたまま配ると、そのスクリプトはハッシュに入らずブラウザに拒否され、テーマ先読みやimportmapだけが死ぬ。ハッシュは中身1文字で変わるので、整形しただけでも書き直しが要る |
| **改行コードを揃えずに比較を書かない（手元が既に混在している）** | `core.autocrlf` が有効で `.gitattributes` が無いまま育ったので、**作業ツリーの中で既にLFとCRLFが混ざっている。** 下の内訳を参照 | 揃えない比較を書くと、clone を待たず**今日この作業ツリーで落ちうる。** 下の「改行コードの実測」を先に読むこと |

## 2. いま止まっていること

着手すれば前に進むもの。事実だけを並べ、方針の選択は残してある。

### 2-1 `npm test` が落ちている（着手前から赤い）

終了コード1。6本中5本合格、1本不合格。

| # | 検査するもの | 結果 |
|---|---|---|
| 1 | 配信するJSON全11本がパースできる | 合格 |
| 2 | CSPが許していない外部サブリソース参照が無い | **不合格** |
| 3 | 参照されていないJSの顔ぶれが変わっていない（固定2本） | 合格 |
| 4 | 読み込み失敗の表示が空状態と同じクラスを使っていない | 合格 |
| 5 | 各ページに charset / viewport / title / lang が揃っている | 合格 |
| 6 | 共通部品とデータの読み込みが根からの絶対パスのまま | 合格 |

**これは既知で、方針の判断待ち。あなたの変更のせいではない。** 画面を1枚足して `npm test` が赤くなったときは、まず落ちた本数と番号を見ること。「6本中5本合格・落ちたのは2だけ」なら元からの状態で、触った箇所とは関係ない。1本でも別の番号が増えていたら、そこが自分の持ち込んだ分。

原因は `js/tools-kirinuki.js` が外部の動画サムネイル配信ホストから `<img>` で画像を読む行が1行残っていること。CSPの `img-src` は `'self' data:` だけで、そのホストを許していない。`tools/build-site.js` のコメントがこれを**既知として明記**している（押す前から外部へ接続してしまうので許さない、という理由つき）。つまり検査は意図どおり鳴っている。

残っている道は三つ。ただし `README.md` が挙げているのは**二つだけ**で、「画像を手元に置くか、方針の方を見直すか、先に決めてください」と並べるにとどめ、どちらが本命かは書いていない。

1. その行を消す（`README.md` には無い選択肢）
2. CSPにそのホストを足す（＝「方針の方を見直す」側）
3. サムネイルを手元に置く（＝「画像を手元に置く」側）── `img-src 'self'` のままで通る

**3が「訪問者のIPを第三者に渡さない」という方針を曲げずに済む唯一の道だ、という評価はこの資料側の判断で、`README.md` はそこまで書いていない。** 決めるのは本人。

**いつ壊れるかは決まっている。** `clips.json` が空のあいだは何も起きない。切り抜きを1件登録した瞬間に、そのページの画像が出なくなる（`README.md` もこの発現条件をそのまま書いている）。いま画面が正常に見えることは、直さなくてよいことの証拠にならない。

### 2-2 未コミットの作業がある

触る前に状態を把握しないと、他人の作業途中を巻き込む。

| 区分 | 内容 |
|---|---|

やろうとしていることは「出典へのID付与」と「出典と作品の結びつけ」、およびその表示。動いている（`npm run check` は3本すべて合格・終了コード0）が、完成待ちなのか作業途中なのかは本人にしか分からない。

**失いかたが2通りある。**

- 新規の2本はどのコミットにも入っていない未追跡ファイル。`git clean -fd` と `git stash -u` で消える。`git checkout .` と既定の `git stash` は追跡ファイルだけを戻すので、この2本は残り、代わりに `package.json` の変更が消える（＝`check` の連結が外れて帳尻は合う）。危ないのは前者。

### 2-6 デプロイ経路が未確認

`package.json` の `deploy` は `npx void deploy --platform cloudflare`。ところが `void` は依存にも `node_modules`（トップレベル8件）にも**無い**。`npx` が都度取得する前提になっており、`void.config.ts` 自身に「実際のデプロイで通ることはまだ確かめていない」と書かれている。

ただし**配る道が無いわけではない。** `README.md` に Void を経由しない手順が記録されている（§9「配る」）。

### 2-7 空ディレクトリが4つ

`assets`・`data/data`・`tools/js/lib`・`server/.media`。gitは空フォルダを記録しないので、clone した環境にはどれも現れない。

- `assets/` は意図された置き場（§2-4）。画像を入れればそのまま使う
- `server/.media/` も意図的。`server/.gitignore` の `/.media/` で除外した、取り込み画像の控え置き場（仕分け用で公開しない）。`server/` 側を見た人が「資料に無い」と引っかからないよう、ここに挙げておく
- `data/data/` と `tools/js/lib/` は出自が追えていない。消して差し支えないかの判断材料が無い（§15）

配信物に出るのは `data/data/` だけ。`build-site.js` が `data` をまるごと写すため `dist/data/data` として空フォルダ1つが入る。`tools/` と `server/` は配信対象外なので、残り2つは外へ出ない。

### ローカルで開く（着手の第一手）

`package.json` に `dev` も `serve` も無い。立て方は `README.md` が1通りだけ書いている ── **VSCode の Live Server 拡張**。リポジトリの根のフォルダをVSCodeで開き、`index.html` を右クリックして起動する。`.vscode/settings.json` はこの拡張の案内表示を黙らせる1行だけで、この経路の支えはこれ1つ。

HTMLを直接開く（`file://`）経路は使えない。データ読み込みが全部 `fetch` のため。

**document root はリポジトリの根でなければならない。** §1のとおり共通部品とデータは `/components/…`・`/data/…` と根からの絶対パスで読んでいるので、`pages/` や1階層下を根にすると、CSSだけ当たってナビとデータが消える。配信後の姿を見たいときは `dist/` を根にして同じように開く。スモークテストが見ているのはこの `dist/` の側。

**根元の `serve.json`（`cleanUrls: false`）は、いま誰も読んでいない。** これは `serve` 系の静的サーバー（URLから `.html` を省くかどうかを決める設定ファイル）の持ち物で、Live Server はこのファイルを見ない。そして `serve` は `package.json` の依存にも scripts にも無く、`README.md` も `docs/project-rules.md` も触れていない（grep 0件）。**立たないときにここを疑うと時間を損する。** 別の静的サーバーに乗り換えた日に生き返る置き土産、という位置づけで扱うこと。

### 生成物を作り直す手順

下の「scripts と実行結果」は**測るために走らせた形**で並べている（`--check`・`--noEmit`）。実装する人が打つのは素の形で、順序に意味がある。

**`npm run check` は作り直すより先に打つ。** `make-catalog.js:155-158` 自身がそう書いている。理由は検査3（資料に固定したIDが消えていないか）の作りで、ディスク上の `catalog.json` と作り直した結果を見比べて「消えたID」を探す。先に作り直してしまうと、題を1文字直して行き場を失ったIDが新しい採番で埋まり、**検査3が見たいものがもう残っていない。** 資料どおりに後ろで打つと、せっかく入れた検査を毎回無力化することになる。

`data/*.json` を手で直したあと:

```
npm run check                     # ① 作り直す前の検算。消えたIDはここでしか見つからない
node tools/make-catalog.js        # catalog.json を組み直す
node tools/assign-source-ids.js   # 番号の無い出典に S-nnn を振る
node tools/link-sources.js        # 群単位で作品に結ぶ（照合が合わなければ結ばず終了コード1）
npm run check                     # ② 作り直した結果の検算。ここは全部合格になるはず
```

①は「`data/catalog.json` が元データと合っていない」で落ちるのが正常。データを直した直後だから当たり前で、これは不合格の報告ではなく「作り直せ」という指示。検査は落ちた項目をまとめて出すので、同じ出力の中に「ID … が消えた」が並んでいないかを見る。並んでいたら、作り直す前に目録棚側の題をそろえて採番を引き継ぐこと。

`src/*.ts` を直したあと:

```
npm run build        # js/ へ実書き出し。--noEmit を付けない
npm run build:site   # dist/ を作り直す
npm test             # dist/ に対するスモークテスト
```

実書き出しは一時フォルダで確認済みで、現在の `js/home.js`・`js/hero/ambient.js` と**バイト単位で一致**する（どちらもLF。`tsconfig.json` が `newLine: "lf"` を指定している）。2本の `tsc` を `&&` で繋ぐ順序を崩してはいけない理由は §1 の2行目。最後の `npm test` は**合格6本にはならない**（§2-1）。期待値は「6本中5本合格・落ちるのは2だけ」。
