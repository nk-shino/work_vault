## 2. 実測の結果（確認済み）

### パイプラインの構成

ファイル名（=人物名）の画像群 → 顔検出の連鎖（OpenCV Haar → アニメ顔 LBP → 検出不可なら need_manual）→ 最大顔を主顔に選択 → 余白拡張（左右60%・上45%・下90%）→ 3:4 に収め → 600×800 JPEG 出力 → mapping.csv（人物名・検出器・顔数・クロップ枠・状態）と連絡シートを生成。

### 8枚の実測（テストデータ・難case 4種を意図して含む）

| 項目 | 実測値 |
| --- | --- |
| 自動処理 ok | **6/8（75.0%）** |
| 検出器の内訳 | haar=5・animeface=1・none=2 |
| 1枚あたり平均処理時間 | 0.213秒 |
| 複数顔（2人1枚） | 大きい方の顔を主顔に選択して ok |
| 連鎖の補完 | アニメ絵1枚は Haar 不発 → アニメ顔検出器が補完して ok |
| 検出不可（need_manual） | 2枚: 広いホール背景の極小顔・両検出器とも0件のイラスト |

ok の6枚は出力JPEGを目視確認し、主顔が框内に収まった妥当なクロップ。need_manual の2枚は失敗として記録（0件を成功扱いにしない）。

### 分かったこと

- **可能**。ただし全自動ではなく「検出不可を人確認に落とす半自動」。need_manual への落ち先の設計が実測で機能した。
- 検出連鎖は実写・絵画・アニメを補完し合う実績があるが、画風によっては両方とも不発になる（実測2枚）。

### 実装上の教訓（技術詳細）

- OpenCV 5.0 は CascadeClassifier を削除済み → 4.14 を使用（requirements の固定が要る。現状 requirements ファイルは無し）。
- OpenCV の FileStorage は Windows の日本語パスを開けない → XML は読み込み時のみ ASCII 名の temp にコピー。画像の入出力は np.fromfile/imdecode で回避。
- 横長原図を3:4へ事前リサイズすると微歪みが残る → **本番では CSS の object-fit で枠に収めるのが本来の形**。ピクセル単位の事前リサイズは不要（サイト側実装の教訓）。

## 4. 限界（明示）

- **テスト画像は生成画像**。検証対象は機構（検出連鎖・クロップ・CSV紐づけ）であり、**実画像（本物の肖像画・イラスト）での精度は別途実測が要る**。
- N=8 での75.0%は統計的信頼区間が広い（site-review 指摘）。この数値は**機構の動作実績**であって**期待精度ではない**。運用計画の前提数字にしないこと（正本 §G-8: 実測していない数値を事実として書かない・報告では「生成画像での値」を併記）。
- 検出不可2枚が示すとおり、背景に埋もれた極小顔や特定の画風では自動化が効かない。人確認フローが前提。
- 読めてしまう不適切な画像（権利未確認素材・他人の肖像）は**一切の検査を通らず ok 扱い**になる（site-review 指摘・静的根拠）。重複・権利の検査は運用手順側で担う。
- 肖像権・著作権の確認（F系法務接続）が済むまで本番掲載はできない。

## 6. 運用シナリオ別の評価（継続運用の対応可否）

### 6-1. 新規での取り込み — **条件付きで対応可（実測つき）**

- **実測（親・2026-11-04）**: 画像を1枚追加して再実行 → 9件全部を処理（**差分処理ではなく全件再処理**）。0.245秒/枚のため実害なし。新規分は問題なく ok（haar・2顔）。mapping.csv は9行に全再生成され、既存行も維持された。
- 全件再処理でも1枚0.2秒強のため、百件程度まで実害なし（推定・site-review も同評価）。
- **破綻点（静的根拠・コード行単位）**: ①PNG 以外（JPG 原図・webp）は**無音で無視**（L148・エラーすら出ない） ②同名人のファイルで出力が衝突（L197） ③対応表がなく「ファイル名=人物名」のみ（L156）。表記ゆれ・打ち間違いは**警告なく別人物として CSV に載る** ④読める不適切画像は重複・権利の検査ゼロで ok 扱い ⑤need_manual の解消手段（手動完了フラグ・skip リスト）がコードに無い。
- **必要な追加**: 対応表の正本との照合＋不一致で止める・PNG 以外への対応（または明示エラー）・need_manual の解消手段。

### 6-2. 改修（差し替え・削除・名前変更・手動修正） — **現行のままでは不可。保持機構が必須**

- **実測（親・2026-11-04）**: 再実行すると既存出力6枚のタイムスタンプが**すべて再実行時刻に更新**された。つまり**人が手動で直したクロップ結果は次回実行で無条件に上書きされ消える**。継続運用の肝である「人確認で直した結果が消えない」保証がゼロ。
- **静的根拠（site-review）**: ①画像を削除すると CSV から行は消えるが **samples/ に孤立 JPEG が残る**（削除・掃除のコードなし） ②ファイル名（人物名）を変えると**別人物扱い**で旧出力が孤立 ③差し替え（同名）は再実行で成立するが、新原図の ok 出力は**再び目視確認が必要**（前回 ok だから自動で正しい保障は無い）。
- S-04（表示名を主キーにした採番・解決済み「可能なら移行を行う」）が進むほど**表示名の変更は日常化する前提**になり、ファイル名=人物名の規約は脆弱になる。
- **必要な追加**: 手動結果の保持機構（`manual/` ディレクトリを自動出力より優先、または入力側対応表の `verified` 列）・削除時の samples 掃除・改名検知。**これらを満たさない場合、改修系の操作は不可**（確実に手動成果を失う。「再実行しない」という規律で回避する運用は人の注意に依存して脆弱）。

### 6-3. 変更（サイト側・パイプライン側の改修への追従） — **対応可。構造は拡張向き、調整は未実測**

- **可能な変更**: 比率（`ASPECT_W, ASPECT_H`・L35）・余白係数（L32-34）・出力サイズ（L36）・品質は**定数1箇所**。検出器の追加は連鎖への追加で可（L171-178。animeface が Haar を補完した実効は実測済み）。object-fit 採用と**構造的に相性が良い**: resize（L196）と出力サイズが不要になり、横長原図の微歪み問題が消える。サイト側は aspect-ratio 枠に object-fit を足すだけ。
- **注意（site-review）**: 余白係数（左右60%・上45%・**下90%**）は「顔下に胸まで余らせる3:4構図」に調整された値。正方形など別比率では意味が変わるため、**比率変更は係数の再実測セットとして扱う**。
- **破綻点（静的根拠）**: 全パラメータがハードコード（CLI 引数・設定ファイルなし・L23-37・L104）。変更のたびに「コード編集＋全件再処理＋目視再確認」が強制される。画像が100件を超えると（推定）運用を止める規模。
- **サイト側の結合**: characters.json の `image` フィールドが受け口として既存（全員空）だが、CSV→json を繋ぐ機構は未実装。現状は手書き結合。表示形式の変更（J-01 決定済み・現行流を既定）とは独立で、image フィールド経由の設計なら影響を受けない。**サイト反映の設計判断は S-03 の「絵が入った日の案」として別途通す**。

## 8. 受け入れ条件（採用時に運営者が確定するもの）

1. **対応表の正本化**: ファイル名↔サイト側 id/表示名（characters.json の id・`image` フィールドと接続）。不一致は**警告で止める**（無音崩れの禁止）。
2. **need_manual は自動掲載しない**。人の裁きの結果を受け取る解消手段（手動完了フラグ等）を持つ。
3. **全出力（自動 ok を含む）は掲載前に人の目視確認を経る**。75.0% は自動検出率であって掲載可能率ではない。
4. **手動修正の結果が次回実行で消えない機構**（manual/ 優先または verified フラグ）を運用開始前に実装する。満たさない場合、改修系の操作は不可。
5. **枠への収めは CSS object-fit**（パイプラインの事前リサイズに依存しない。微歪みの回避）。
6. **本画像での精度実測を本導入前に1回実施**する。75.0% は生成画像実測として明記し続ける。
7. **権利確認（F系）が済むまで本番掲載しない**。
8. **サイト側の結合設計は S-03 の「絵が入った日の案」として設計判断を通す**。
- 補足（実装に含める）: 環境の requirements 化（OpenCV 4.14 固定）・孤立出力の掃除・読み込み失敗と検出0件の CSV 上の区別。
