# F系5本の確定事項（横断の食い違いを1本にしたもの）

改訂担当がこれだけ読めば、5本のどこを何に書き替えるかが決まるようにしてある。
ここで決めていないものは「決められない」と書いてあり、その場合は5本に同じ印を付けるところまでが指示である。

数字と実装の話は、記憶ではなく 2026-10-31 に `C:\Projects\name-info-site` を読んで測った。
条文は e-Gov の法令API（`https://laws.e-gov.go.jp/api/1/lawdata/415AC0000000057`）から本文XMLを取得して写した。
これは法的助言ではない。専門家に相談する材料と、相談前でも安全側に倒せる運用案を作ったもの。

**法令名を省かない。** 5本とも「法第25条」のような書き方をやめる。
情プラ法第25条第1項（申出者への通知・14日以内）と個人情報保護法第25条（委託先の監督）はまったく別の条文で、
F-C は両方の法律を引いているので読者が引き違える。以後はすべて法令名を付けて書く。

## 1. 「起因タグ」の語彙 ── 1語で指していた4つを2本の欄に割る

### 決めたこと

**欄を2本に割る。語彙表はこれ1枚で、5本はこの表を参照する。**

| 欄名（JSONの鍵） | 画面に出す名 | 何を分類するか | 値 | 確定の度合い |
|---|---|---|---|---|
| `cause` | 起因 | 訂正が**どこから起こったか** | `reader`（閲覧者の指摘）／`self-check`（自己点検）／`source-update`（出典の更新）／`rightsholder`（権利者の依頼） | **確定。** 台帳 A-04 要点の「起因タグreader追加」がそのまま読める唯一の形 |
| `issue` | 指摘の種類 | 閲覧者が**何が違うと言っているか** | 誤記（書き間違い・数字違い）／出典が足りない／解釈が違う／リンクが切れている／リンク先の中身が違う／その他 | **値6つの採否は A-06 §9 の判断待ち。** 欄を別に置くことと欄名は確定 |

`cause` が付くのは訂正1件すべて。`issue` が付くのは `cause` が `reader` の行だけで、他の3つでは空になる。

**集計の単位は `cause` ではなく `issue` で束ねる。** A-06 §3-1 が書いている「対象ID × 起因タグ」は
「対象ID × 指摘の種類」に直る。閲覧者の指摘はすべて `cause` が `reader` なので、起因で束ねると1つの塊にしかならない。

`kind` という欄名は使えない。`data/sources.json` の出典1項が既に `kind` を持っていて、
そこには出典の性質（一次情報／二次情報と、どこの誰が出したか）が入っている。実測で確認した。
同じサイトの中で `kind` に2つの意味を持たせると、いま解いている衝突をもう一度作ることになる。

### なぜそう決めたか

台帳 A-04 の要点の文言が「接続方式の4点（別経路受付・**起因タグreader追加**・readerは自動受理しない・起因別集計）」で、
`reader` が起因タグの1値として書かれている。`reader` は「誰が起こしたか」であって「何が違うか」ではない。
だから起因タグの軸は起こり元に確定し、F-C §3-3 の4値がそのまま正になる。

いっぽう F-B §5 の3値（誤記・出典欠落・解釈違い）と F-A §2-3/§2-4 が足す2値（リンク切れ・内容が違う）は、
どちらも A-06 §1-3末の6値の部分集合である。**だから新しい語彙は要らず、欄を1本増やすだけで3本の要求が同時に入る。**

6値そのものを確定させないのは、A-06 §9 が自分で判断待ちに置いているから。
欄の分離は設計の話で安全側にしか振れないが、閲覧者に必須選択させる選択肢の文言は運営者が見て決めるもの。

### `data/corrections.json` のスキーマ案（受付と反映を1行で表す）

```json
{
  "updated": "2026-11-07",
  "legend": [
    { "cause": "reader",        "label": "閲覧者の指摘" },
    { "cause": "self-check",    "label": "自己点検" },
    { "cause": "source-update", "label": "出典の更新" },
    { "cause": "rightsholder",  "label": "権利者の依頼" }
  ],
  "items": [
    {
      "seq": 1,
      "target": "S-004",
      "cause": "reader",
      "issue": "出典が足りない",
      "state": "受付",
      "received": "2026-11-07",
      "decided": "",
      "what": "",
      "why": "",
      "basis": ""
    }
  ]
}
```

- `state` は `受付` ／ `反映` ／ `一部反映` ／ `不反映` の4値。F-C §3-3 の `result`（3値）はここへ畳む。
  `受付` を値として持たせないと、A-06 §4-3 の「受け付けた」が表せる場所がどこにも無い。
- **受付から反映へ進むとき、行は増やさず同じ `seq` の `state` を進める。**
  行を増やすと同じ「対象ID × 指摘の種類」が2回数えられて、集計の数え方が崩れる。
  いっぽう `seq` の連番の欠けは「行が消されたこと」の手がかりとして保たれる（F-C が唯一の改竄対策と呼んだもの）。
  `state` の書き換えのほうは git の差分に残る（`data/*.json` 11本すべて追跡下。ただし項目4の手0を先にやること）。
- `date` を `received`（受付日）と `decided`（反映・不反映を決めた日）に割る。どちらも `YYYY-MM-DD`、`decided` は空を許す。
  A-06 §4-1 の「受付した月」は**画面に出す粒度**であって保存の粒度ではない。
  `received` から月だけを出して描けば、F-C §3-3 の検査3（`YYYY-MM-DD` 必須）と両立する。
- `who`（指摘者）の欄は作らない。F-C §2-3・§2-6 のとおり。

**検査は新しい道具を立てず、既にあるものへ寄せる。** `tools/assign-source-ids.js --check` が
`data/sources.json` を読んで id を集めているので、`target` が id にあるかの検査はそこに相乗りできる（実測で確認）。
`seq` の連番・`state` と `cause` が上の値のどれか・`received` と `decided` の形も同じ場所で見れば、
`npm run check` に4本目を足さずに済む。

### 区分の判定は `url` の有無で決める。`kind` では決めない

**決めたこと:** 読者がたどれるかどうかは `url` が入っているかだけで判定する。`kind` は出典の性質の欄として触らない。

**なぜそう決めたか:** 出典S-008・S-009 がその証拠である。この2項は `kind` が
「一次情報（公式運営アカウントによるアナウンス）」で、`source` も招待制サーバーの告知チャンネルを指しているのに、
`url` には `https://www.youtube.com/watch?v=...` が入っていて読者がたどれる。閉じた場で告知を見て、
公開されている動画へリンクを張ったという経緯がそのまま残っている形で、これは誤りではない。
`kind` で判定すると、この2項が公開URLを持ちながら「運営者のみ確認」に落ちる。
`url` で判定すると、経緯は `source` に残ったまま、読者の経路だけが正しく出る。

しかも `js/sources.js` がこの3分岐を既に描いていて、理由までコメントに書いてある。
「リンクが張れないことと、出典が無いことは別物。Discordの投稿や電子書籍のように、
出どころははっきりしているのに読者が直接たどれないものがあるので、3通りに分ける」
──そして `item.url ? （リンク付き） : item.source ? （リンクなし） : （出典：確認できず）` で描き分けている。
実測の 45／15／3 がそのまま F-A の3値（公開URL／運営者のみ確認／未確認）に1対1で対応する。
**だから台帳に列を足さない。凡例に語を当てるだけで同じことが出る。**

2軸として扱う、ということをはっきり書いておく。

- 読者がたどれるか ＝ `url` の有無（既存2欄から導出。新しい欄も入力作業も要らない）
- 出典の性質 ＝ `kind`（既存欄。一次情報と二次情報の書き分けが既にある）

この2軸が別だと決まると、事典7項のうち5項に「確認済」が付いている問題も `kind` のまま扱える。
`tools/assign-source-ids.js --check` が既にこの5件を基準値として押さえており、増えたときだけ止める作りになっている。
扱いは「基準値を下げる（5項の `status` を直す）」か「`kind` の書き方を直す」の2択に落ちて、新しい欄は要らない。

## 3. 「現在の静的構成で個人情報取扱事業者に当たるか」── 両方の論点を含む1つの文

### 決めたこと

**どちらも勝たせない。入口を2つに分けて両方を書いた下の1文を正とし、5本はこの文を参照する。**
F-C が正しくて F-D・F-B が間違っている、という形にはしない。見ている対象が違うので、両立する。

> **統一文（5本がこの文を引く）**
>
> 現在の静的構成で個人情報保護法第16条第2項の「個人情報取扱事業者」に当たるかは、**入口が2つあり、どちらも条文の当てはめなので運営者には決められない。**
>
> **入口A ── 閲覧者から受け取るデータ。** 氏名・連絡先・識別子の欄を置かず、閲覧者を識別できる情報を保存しなければ、
> 同条第1項第1号が挙げる「特定の個人情報を電子計算機を用いて検索することができるように体系的に構成したもの」を持たないので、
> 同条第2項の「個人情報データベース等を事業の用に供している者」に当たらない読みが素直になる。**この入口は、開けないという選択で閉じられる。**
>
> **入口B ── 掲載しているデータ。** このサイトは実在の制作者について書いている。
> 実測では出典63項すべてが `S-001` 形式の id を持ち、`claim` と `supplement` にその人についての記述が入っている。
> 同法第2条第1項第1号の「生存する個人に関する情報であって…特定の個人を識別することができるもの」に当たる記述が
> id で引ける形に並んでいるなら、入口Bは**受付を置くかどうかと無関係に、すでに立っている**可能性がある。
>
> 入口Bが立つかどうかで、第32条第1項（柱書の「本人の知り得る状態（本人の求めに応じて遅滞なく回答する場合を含む。）」と
