# 設計論点

**題材を必要としない4件。**『レイアウト骨格.md』と合わせて使う。

数値はすべて 2026-10-16 の実測。

---

## 前提（どの論点にも効く）

### データの形

| 集合 | 件数 | 備考 |
|---|---|---|
| 主体（人物相当） | 13 | 画像欄が**全件空** |
| 作品 | 13 | **画像のフィールドが無い** |
| 年表 | 9 | |
| 用語 | 24 | |
| 出典 | 8群 | 群の中に項目 |
| 横断目録 | 61 | 生成物。他から組む |
| 動画・画像・催事の一覧 | **各0** | 3つとも空 |

### 外せない制約

1. **公開されるのは素の静的ファイルだけ。** サーバー処理を使わない
2. **外部リクエストはゼロ。** ライブラリも自前で同梱する（訪問者のIPを第三者に渡さないため）
3. **色の16進数を直接書かない。** 必ずCSS変数
4. 折り返しは **1024px と 768px の2つだけ**
5. 記録性が最優先。**演出が可読性を邪魔したら演出を捨てる**

## 論点1：時系列を横方向に辿らせる部品

### やりたいこと

主体ごとに、関わった作品を**左から右へ時系列で並べて追えるようにする。**
縦のリストでも順番は出せるが、**横に流すと「進んでいる」という形そのものが順番を説明する。**
矢印や番号を足さなくても左が先だと分かる、という狙い。

### **先に見るべき事実 ── 大半が1コマで終わる**

主体1件あたりの関連作品数を数えた。

```
[3, 1, 0, 1, 1, 1, 4, 1, 1, 1, 1, 1, 1]

13件中  10件 が 1 コマ
         1件 が 0 コマ
         2件 が 3コマ以上（3 と 4）
```

**横スクロールで辿らせる部品を作っても、13件中10件は1コマで終わる。**
「進んでいる形が順番を説明する」という狙いは、**2件でしか成立しない。**

これは好みの問題ではなくデータの形の問題なので、**最初に決めるのはここ。**

| 案 | 内容 |
|---|---|
| A | **作らない。** 1〜2件なら既存の一覧で足りる。データが増えてから作る |
| B | **3コマ以上の主体にだけ出す。** 1件以下は通常表示のまま |
| C | **全件に出す。** 1コマでも「1件しかない」という情報として見せる |
| D | **軸を変える。** 主体ごとではなく、作品全体を1本の時系列にする（13コマになる） |

**Dは別物になる。** 要件の言い換えではなく、作るものが変わる点に注意。

### 軸の論点

| | 埋まり具合 |
|---|---|
| 発表日 | **13/13 すべて埋まっている。全件「確定」** |
| 作中の序列 | **10/13 のみ。3件は番号が無い** |

**序列を既定にすると3件が置けない。**
推奨は発表日を既定にして、序列へ切り替えられるようにすること。
「いつ出たか」は事実、「作中の何番目か」は解釈が入る。
**事実のほうを既定に置けば、解釈が変わっても表示が壊れない。**

### 残りの論点

| # | 論点 | 補足 |
|---|---|---|
| 1 | 1コマに何を出すか | 画像は**無い**ので、題と番号と日付のどれを出すか |
| 2 | 置き場所 | 専用ページか、詳細ページの中に埋めるか |
| 3 | 0コマのとき何を出すか | 空の部品を出すか、部品ごと消すか |

### 実装の注意

**横スクロールは狭い画面で嫌われる。** 画面幅に収まらない横並びは、
縦スクロール中に指が引っかかって誤爆する。

- **スクロールスナップでコマ単位に止める**
- **矢印キーだけで読めるようにする**
- 折り返しは2つしかない（1024 / 768）。中間の幅は既定の形で耐える必要がある

### 答えに求めること

- 上の A〜D から1つを選び、**なぜ他を捨てるか**
- 選んだ案での受け入れ条件（何ができたら完成か）
- 1コマ・0コマのときの表示
- キーボードだけで端から端まで読める手順

## 論点2：0件の一覧をどう見せるか

### いまの状態

**3つの一覧が0件のまま動いている。** 共通して中央に「準備中です」＋説明1行を出す。

```
┌───────────────────────────────────────┐
│                                       │
│            ▭ 「準備中です」             │
│            ▭  説明の1行                │
│                                       │
└───────────────────────────────────────┘
```

格子ページの一覧でも、絞り込みで0件になったとき同じ形が出る。

### 論点

| # | 論点 | なぜ決めないといけないか |
|---|---|---|
| 1 | **「無い」のか「準備中」なのか「募集中」なのか** | 3つで読者の次の行動が変わる。いまは全部「準備中」で一括りになっている |
| 2 | 恒常的に0件のページを**出すか、隠すか** | 入口から辿れるのに毎回空、という体験になっている |
| 3 | **絞り込みの結果0件**と、**元から0件**を区別するか | 前者は条件を外せば戻る。後者は戻らない。いまは同じ見た目 |
| 4 | 0件のときに**次の行き先**を出すか | 戻る導線が無いと行き止まりになる |

**3 が実害に近い。** 条件を外せば戻るのに「準備中」と出ると、読者は無いものと判断して離れる。

### 答えに求めること

- 状態を何種類に分けるか。各状態の文言と導線
- 2 の判断と、その根拠
- 絞り込み0件のときに、**何を外せば戻るか**を示す方法

## 論点3：画像欄が空のまま運用する

### いまの状態

**主体13件すべてが画像を持たない。** 作品にはフィールド自体が無い。
描画側は用意できていて、値が入れば出る。空のときだけ差し替え表示に落ちる。

```
┌─────────┐          ┌─────────┐
│ 額縁     │          │ 額縁     │
│ ┌─────┐ │   実際→  │ ┌─────┐ │
│ │ □   │ │          │ │題箋  │ │   枠は残り、
│ │     │ │          │ │ ▭   │ │   題箋だけが入る
│ └─────┘ │          │ └─────┘ │
│ ▭ 役割   │          │ ▭ 役割   │
└─────────┘          └─────────┘
  想定               いまの全件
```

**これが当分続く前提で決める。**（素材の方針で、代用画像を置けない）

### 論点

| # | 論点 | 補足 |
|---|---|---|
| 1 | 差し替え表示をどう見せるか | 枠だけ残す／紋様を置く／枠ごと消す。印象が大きく変わる |
| 2 | **絵が無い前提で一覧を組み直すか** | 画像が並ぶ想定の配置を、文字主体へ寄せるか |
| 3 | 縦横比を**先に決めるか** | 決めておけば後から入っても並びが崩れない。決めないと入った日に全部ずれる |
| 4 | 作品側にフィールドを足すか | いまは無い。足すなら主体側と扱いをそろえる |

**2 が本体。**

### 必ず分けて出すこと

**「いまの見た目を良くする案」と「絵が入ったときの案」は別物として出す。**
片方だけ出すと、もう片方で破綻する。
いまを最適化しすぎると絵が入ったとき作り直しになり、
絵の前提で組むと当分のあいだ使えない。

### 答えに求めること

- 1 の案を2〜3つ比較
- 2 の判断と、**戻せる形にできるか**（絵が入ったときに作り直しにならないか）
- 3 の比率の提案と、その根拠

## 論点4：表示名を主キーにしている採番

### いまの状態

横断目録61件にはIDが振ってある（資料から参照するため**固定する決まり**）。
採番は「**種別＋表示名**」を鍵に、前回の結果から引き継ぐ作り。

**表示名を1文字直すと、別物とみなされてIDが振り直される。**
実際に表記ゆれを直したとき、既存のIDが行き場を失い、新しい番号が振られた。

いまは生成前に走らせる検査が「**消えたID**」を見つけて止めるようにしてあるが、
**作り自体は直っていない。**

### 論点

| # | 選択肢 | 影響 |
|---|---|---|
| A | **現状維持＋検査で止める** | 直す手間はゼロ。表示名を直すたびに人が介入して採番を引き継ぐ |
| B | **安定した鍵を元データ側に持つ** | 表示名と独立した識別子を各データに足す。移行が要る |
| C | **IDを固定する決まりをやめる** | 資料からの参照を別の方法にする。参照先が広いと影響が大きい |

**Bが筋だが、移行の重さを見積もる必要がある。**
既存61件のIDを保ったまま移れるか、が分かれ目。

### 答えに求めること

- A〜Cの比較。**移行の手数**を含めて
- Bを採るなら、既存IDを保ったまま移る手順
- どの案でも、**既存の参照が切れないこと**をどう確かめるか

## 付録：デザイン側の負債

論点ではないが、触るときに巻き込むもの。

| 内容 | 実測 |
|---|---|
| **罫線のトークンが2系統ある** | 新しい体系が48箇所、古い体系が**29箇所**。置換が途中で止まっている。混在したままだと片方だけ直す事故が起きる |
| 設計仕様のチェックボックスが実態と合っていない | 大半は実装済みなのに全部未チェック。**読むと、できている作業をやり直す** |

---

## 答え方の共通ルール

- **選択肢は2〜3案。** 各案の利点・欠点・実装の重さ・リスクを並べる
- 一般論としての最良ではなく、**この条件下での推奨**を書く
- **実測していない改善率や工数を、事実として書かない**
- コード上の推定と、実画面の観察を**混ぜない**
- 「変更しない」が最適なら、根拠付きでそう書く。それも結論として扱う
- 受け入れ条件（何ができたら完成か）を必ず付ける
