# S-15 デプロイ提案

S-15 の回答は「提案する。フロー及び実装状況、手順まで」。**実行しない。**
本家リポジトリの実物で測った値だけで書いた。

---

## 0. 先に伝えるべきこと3点

### (1) 既定の公開コマンドは、今のままでは通らない公算が高い

`package.json` の `deploy` は `npx void deploy --platform cloudflare` だが、
**`void` は依存にも `node_modules` にも無い。** `npx` が実行時に取りに行く形になる。

さらに `void.config.ts` の冒頭に、書いた本人の但し書きが残っている ──
設定は公式ドキュメントの項目名に沿って書いたもので、**実際のデプロイで通ることは確かめていない。**

**初回の公開を、未検証の経路で試すべきではない。**

### (2) 検証済みの代替経路が既にある

README に、Void を経由しない手順が記録されている。

```
npm run build:site
npx wrangler deploy --name <プロジェクト名> --assets dist --compatibility-date 2026-10-21
```

Cloudflare の素のコマンドで同じものが上がる。**こちらを本命に据えることを提案する。**
Void は後から試せばよく、初回公開を実験にしない。

### (3) 公開前に足りないものが3つある

| 無いもの | 影響 |
|---|---|
| `robots.txt` | 検索エンジンへの指示が無い。非公式サイトとして収集範囲を示せない |
| `sitemap.xml` | 16枚の画面を検索エンジンが辿る手掛かりが無い |
| `favicon.ico` | タブとブックマークが既定のアイコンになる |

いずれも公開を止めるものではないが、**後から足すと一度目の収集に間に合わない。**

## 1. 実装状況（実測）

| 項目 | 状態 |
|---|---|
| 配信物の組み立て | **実装済。** `tools/build-site.js` が `dist/` を作る |
| 配信物の規模 | **50ファイル・1.3MB** |
| 配信ヘッダー | **実装済。** `dist/_headers` に組み立て時に書き出す |
| 公開設定ファイル | `void.config.ts` あり。**未検証** |
| 公開コマンド | `npm run deploy`。**依存が入っていない** |
| 代替手順 | README に記録あり（素のコマンド） |
| 独自ドメイン | **未取得・未設定** |
| robots / sitemap / favicon | **無し** |

### 配るものの決め方

`tools/build-site.js` の `PUBLISH` に**拾う側だけを並べてある。**
外すものを並べる書き方にしていないのは、その書き方だと新しいフォルダを足した日に黙って混ざるため。

**リポジトリの根はそのまま配れない。** 外部APIキーを扱う別アプリ・内部文書・作業用データが
一緒に出てしまうので、配る分だけを組み立てる形になっている。

### 配信ヘッダーが課す制約

`default-src 'self'` で配られ、**`'unsafe-inline'` が無い。**
インラインのスクリプトはハッシュで個別に許可していて、組み立てのたびに数え直される。

| 書き方 | 配信後 |
|---|---|
| CSSファイル内の指定 | 通る |
| JSから要素の `style` を書く | 通る |
| HTMLに `style="…"` を書く | **止まる** |
| JSで `<style>` を差し込む | **止まる** |
| 外部から画像を読む | **止まる** |

**この最後の1件が、今まさに検査で引っかかっている。**
切り抜き画面のJSが外部のサムネイル配信ホストから画像を読む行を1つ持っていて、
`npm test` は6本中5本合格・1本失敗の状態にある。**既知・方針判断待ち。**

## 2. 提案するフロー

### 段階1: 公開前に埋める（公開とは独立に進められる）

1. **検査1本の赤を解消する。** 外部サムネイルの扱いを決める
   （手元に置く／ヘッダーで許す／サムネイルを出さない）。
   赤いまま公開すると、以後ずっと「元から赤い」のか「今壊した」のかが分からなくなる
2. `robots.txt` と `sitemap.xml` を作る。16画面ぶん
3. `favicon` を用意する
4. 独自ドメインを使うか決める。使うなら取得する

### 段階2: 初回公開（**承認が要る**）

1. `npm run check` と `npm test` を通す
2. `npm run build:site` で `dist/` を作り直す
3. Cloudflare と繋ぐ（初回のみ・ブラウザでサインイン）
4. **素のコマンドで上げる**（§0-2）
5. 上がったものを実際に開いて確かめる（§3）

### 段階3: 公開後の確認

公開は「上がった」で終わらない。**配信ヘッダーは手元のサーバーでは再現されない**ので、
止まる書き方があっても手元では気づけない。公開後に実物で確かめる必要がある。

---

## 3. 公開後に確かめること

| 見るもの | 確かめ方 | 期待 |
|---|---|---|
| 配信ヘッダーが効いているか | ブラウザの開発者ツールで応答ヘッダーを見る | `Content-Security-Policy` が入っている |
| ヘッダーに止められたものが無いか | 開発者ツールのコンソール | CSP違反の記録が0件 |
| 画面が全部開くか | 16枚を順に開く | 読み込み失敗が0件 |
| 存在しないURL | 適当なURLを叩く | 404の画面が返る（階層が深くても崩れない） |
| テーマ切替 | 明暗を切り替えて再読み込み | 選択が保たれる |
| 狭い画面 | 375px幅 | 横スクロールが出ない・ナビが開く |
| データの読み込み | 一覧系の画面 | 0件表示や失敗表示になっていない |

**手元で通ったことを公開後の確認の代わりにしない。** 手元のサーバーは配信ヘッダーを付けない。

## 4. 戻し方

Cloudflare 側に以前の版が残る。**戻す手順を試さずに公開しない。**
初回は戻す先が無いので、**2回目の公開の前に一度戻す練習をしておく**ことを提案する。

手元側は `dist/` を作り直せば元に戻る（`dist/` は生成物で、毎回捨てて作られる）。
