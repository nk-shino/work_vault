## 🎯 結論：採用するなら「Claude Code＋編集エンジン＋Adobe」の構成です

今回の目的には、**動画生成AIだけを導入するより、「既存動画を理解し、編集内容を決め、編集ソフトやプログラムに実行させるエージェント」を作る方法**が適しています。

推奨する構成は次のとおりです。

> **Claude Code Proを開発・実行の窓口にし、FFmpegで前処理と定型編集、Premiereで編集可能なプロジェクト作成と仕上げ、Adobe Media Encoderで書き出す。人は完成動画と検査結果を確認する。**
>
> 短尺動画については、**OpusClipのAPI／MCPを比較対象として試し、自作より品質・手間・費用が優れる工程だけ採用**します。

また、調査でご指定の「フェーブル」に対応する**AnthropicのClaude Fable**を確認できました。**fal.aiとは別物**です。Claude ProではFableが追加従量課金の対象になっているため、ご説明と整合します。

以下は、**2026年10月6日時点で確認した公式情報に基づく調査・設計案**です。実際の素材・参考動画・PC上での動作検証はまだ行っていません。「公式に機能があること」と「今回の環境で一連の処理が動作すること」は区別します。

## 📌 1．前提と、最初に決めておくべき制作単位

| 項目 | 今回の前提 |
|---|---|
| PC | Windows、メモリ32GB。CPU・GPU・空き容量は未確認 |
| 使用可能ソフト | Adobe Creative Cloudの契約に含まれる製品。実際のインストール状況・バージョンは確認が必要 |
| AI | Claude Code Proを基本。必要に応じてFable、Codexを追加 |
| 元動画 | 3本ほど。各動画の長さは未確定 |
| 短尺 | トピックごとに1本、30秒前後。縦1080×1920 |
| 横長 | 内容をテンポよく短縮した10分前後。横1920×1080 |
| 頻度 | 週2本 |
| 権利 | 編集・公開・外部送信は許可済み |
| 公開先 | 自社サイトを含む |
| 運用 | エージェントが制作・書き出し、人が確認する |
| 参考動画 | 存在するが、今回の調査では未閲覧 |

**「週2本」が、完成ファイル2本なのか、元動画2本分の制作なのかで工数が変わります。**

以降は比較しやすいよう、**1制作単位＝横長1本＋採用したトピック数分の短尺**とします。例えば短尺3本なら、週2制作単位で完成動画は週8本です。これは見積もり用の仮定であり、確定条件ではありません。

「Streaming HUB」は、今回の検索では、ご説明に合う公式サイトを特定できませんでした。類似名の製品へ置き換えず、**当面は、現在お使いのダウンローダーで取得したファイルを入力フォルダーへ置く方式**とします。URLや製品情報が分かれば、取得工程の自動化可否を別途確認できます。

## 🧰 2．具体的なツールと、今回の用途での位置付け

### A．中核として使うツール

| 正式名称・公式サイト | 役割 | 今回の判断 |
|---|---|---|
| **[Claude Code](https://code.claude.com/docs/en/overview)** | プログラム開発、編集案作成、ツール実行、失敗時の調査 | **必須の司令役**。動画を直接レンダリングするソフトではない |
| **[Adobe Premiere／Premiere Pro UXP](https://developer.adobe.com/premiere-pro/uxp)** | タイムライン編集、字幕・図版・テンプレート配置、編集可能なプロジェクト保存 | **Adobe連携の中心**。専用UXPプラグインを開発する |
| **[Adobe Media Encoder連携API](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/encodermanager)** | 書き出し、キュー処理、進捗・完了・失敗イベント取得 | **最終書き出し候補**。Premiereとの実機連携試験が必要 |
| **[FFmpeg／ffprobe](https://ffmpeg.org/)** | 動画情報取得、音声抽出、カット、結合、拡縮、音量処理、書き出し、技術検査 | **自動処理の土台**。AIではないが、再現性が高い |
| **[faster-whisper](https://github.com/SYSTRAN/faster-whisper)** | 日本語を含む音声認識、時刻付き文字起こし | ローカル文字起こしの第一候補。CPU動作可能、GPU環境で高速化 |
| **[PySceneDetect](https://www.scenedetect.com/docs/latest/)** | 映像のカット変化の検出 | 補助採用。**場面転換と話題転換は別**なので単独で編集判断しない |
| **[Adobe After Effects](https://helpx.adobe.com/after-effects/desktop/render-and-export/automate-rendering/automated-rendering-network-rendering.html)** | タイトル、説明アニメーション、ブランド演出 | 演出が必要になった段階で追加。`aerender`によるコマンドライン書き出しが公式に存在 |

Premiereの文字起こし・文字ベース編集は日本語に対応しています。ただし、**画面上で利用できる機能が、すべて同じようにAPIから呼べるわけではありません**。このため、無人処理を重視する文字起こしは、最初はfaster-whisperなどの独立した処理にする方が構成を管理しやすくなります。

出典：[Adobeの文字ベース編集と言語一覧](https://helpx.adobe.com/nz/premiere/desktop/edit-projects/edit-video-using-text-based-editing/overview-of-text-based-editing.html)

### B．短尺の自動切り抜きを早く実現するサービス

| 正式名称・公式サイト | 得意なこと | API・連携の確認状況 | 採用時の注意 |
|---|---|---|---|
| **[OpusClip](https://www.opus.pro/api)** | 長尺からの短尺候補作成、字幕、縦への再構成 | **公式API・公式MCPあり**。日本語対応の案内あり | 第一比較候補。API利用権、FHD出力、透かし、出力形式を契約単位で確認 |
| **[Klap](https://klap.app/api)** | 発話中心の切り抜き、字幕、被写体を追う縦再構成 | **公式APIあり**。日本語対応案内あり | 対談・講演などに向く。無言の作業映像への適性は別途試験 |
| **[Vizard](https://vizard.ai/api)** | 長尺から短尺、字幕、複数配信先向け加工 | **公式APIあり**。日本語の文字起こし案内あり | Web版とAPIの対応範囲・課金条件を分けて確認 |
| **[Descript](https://www.descript.com/)** | 文字ベース編集、音声中心の制作 | 今回は日本語用途に制約 | 公式ヘルプでは日本語の入力文字起こしが未対応。**日本語主軸の第一候補にしない** |

Descriptは、日本語への翻訳・吹き替え機能の案内と、日本語音声の文字起こし対応を混同しないことが重要です。

出典：[Descriptの文字起こし対応言語](https://help.descript.com/script-editing/supported-transcription-languages)

**OpusClip・Klap・Vizardを全部契約する必要はありません。**
同じ素材で候補を比較し、**「使える短尺1本を得るまでの費用と修正時間」**が最も小さいものを残します。

また、これらは短尺制作に強みがありますが、**3本の素材から論旨を保った10分版を構成する仕事を、そのまま任せられるとは限りません**。横長版は独自の編集設計を持つ方がよいです。

## 🧠 3．ジャンルに依存しない、編集方法の選択肢

「盛り上がった発言を切り抜く」だけに限定しない設計にします。

| 元動画の特徴・目的 | AIが見るべき情報 | 適する編集方法 |
|---|---|---|
| 対談・講演・インタビュー | 発言、質問と回答、話題のまとまり | 文字起こし中心に、話題ごとの短尺と章立てした横長版 |
| 操作説明・実演・作業記録 | 手順、画面変化、操作対象、説明音声 | 重要な手順を保持し、待ち時間を短縮。必要なら一部を倍速化 |
| 無言・音楽中心・イベント映像 | 動作、場面、表情、音の変化 | 映像分析中心。文字起こしだけで選定しない |
| 比較・検証・レビュー | 比較条件、結果、例外、注意点 | 条件と結論をセットで残す。結論だけ切り出さない |
| 商品・サービス紹介 | 使い方、特長、説明図、訴求先 | 既存映像＋説明テロップ＋図版。自社サイトの導線に合わせる |
| 複数の元動画の再編集 | 重複内容、補完関係、撮影時期 | 素材横断で章立て。ただし別時点の発言を一続きに見せない |
| 海外向け素材の日本展開 | 原文、固有名詞、文化的な表現 | 日本語字幕・必要に応じ吹き替え。内容変更と翻訳を区別 |
| 自社サイト用ダイジェスト | 視聴者が知りたいこと、ページの目的 | 冒頭に要点、章・字幕・関連ページへの導線を付ける |

### 参考動画は「コピー元」ではなく「編集仕様」に変換する

参考動画から抽出するのは、例えば次の項目です。

- 冒頭何秒で主題が提示されるか
- カットの平均的な長さと、長く見せる場面
- 字幕の大きさ・位置・行数・強調方法
- BGMと声のバランス
- 図版・補足映像・画面拡大の使い方
- 縦動画で、人物・資料・操作画面をどう配置しているか
- 終わり方と、次の行動への案内
- 「寄せたい点」と「採用しない点」

**同じ参考動画でも、テンポは採用するが字幕演出は採用しない、といった指定が可能**です。参考動画そのものの映像・音楽・固有のデザインを再利用する許可とは分けて扱います。

## 🏗️ 4．推奨するエージェントの構成とAdobe連携

### 全体像

```mermaid
flowchart TD
    source["取得済みの元動画"] --> ingest["入力検査と素材登録"]
    reference["参考動画・ブランド規定"] --> style["編集仕様の抽出"]
    ingest --> analysis["音声認識・場面検出・映像確認"]
    analysis --> planner["Claudeによる構成案と編集指示"]
    style --> planner
    planner --> plan["時刻と出典付きの編集計画"]
    plan --> renderer["FFmpegまたはPremiere連携で編集"]
    renderer --> export["FHD動画と字幕を書き出し"]
    export --> qc["自動検査とレビュー資料"]
    qc --> human["ユーザーが完成動画を確認"]
    human --> revise["修正指示"]
    revise --> plan
    human --> approved["承認済み成果物"]
    approved --> publish["別権限で自社サイトへ公開"]
```

### 重要なのは「編集計画」をファイルとして残すこと

AIに毎回「いい感じに編集して」と頼むのではなく、編集計画をJSONなどで保存します。

編集計画には、少なくとも以下を持たせます。

- 元動画ID
- 使用開始・終了時刻
- 完成動画上の配置位置
- 採用理由と対応する発言
- 字幕と出典時刻
- 縦動画の画角
- テロップ、BGM、図版の指定
- 注意点・人に確認してほしい箇所

**編集の判断と、実際の映像処理を分離することで、修正・再実行・別形式への展開が容易になります。**

### Adobeでの実装方法

今回、公式APIで確認できた範囲は次のとおりです。

| 操作 | 公式情報で確認した内容 |
|---|---|
| タイムラインに素材を入れる | `SequenceEditor`に挿入・上書き・削除などのActionがある |
| MOGRTを配置する | パスやライブラリから挿入するAPIがある |
| シーケンスを書き出す | `EncoderManager.exportSequence`がある |
| Media Encoderへ送る | キューへの書き出し指定がある |
| 書き出し状況を知る | 進捗・完了・エラーなどのイベントがある |
| バージョン条件 | 上記の基本機能は25.6以降の記載。AME起動・バッチ開始の一部は26.3以降 |

出典：
[Adobe SequenceEditor](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/sequenceeditor)
[Adobe EncoderManager](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/encodermanager)

実装は、**Claudeが編集計画を作成し、Premiere内のUXPプラグインがそれを受け取り、APIでタイムラインを組み立てる方式**が本命です。

ただし、次は実機検証が必要です。

- 使用素材に対する正確なイン点・アウト点の適用
- 字幕の作成・スタイル適用
- MOGRTパラメーターの変更
- クロップや追従アニメーション
- 日本語フォント
- 書き出しプリセット
- エラー時の回復、素材の再リンク

**Premiereを、画面もログインも不要なサーバー用レンダラーとして扱う設計にはしません。**
専用Windows環境でPremiereを起動し、プラグインが利用可能な状態を管理する前提です。無人実行の安定性は試験で確認します。

### 最初からすべてをAdobe連携にしない

導入順序は次が現実的です。

1. **FFmpegで、編集計画から短尺・横長の試作品を書き出す**
2. 同じ素材で、**Premiereへの配置→保存→AME書き出しの最小連携**を確認
3. 必要な編集表現をPremiere側へ移す
4. Adobe側で難しい処理はFFmpegまたは事前生成した素材で補完する

最初から2種類の完全な編集エンジンを作るのではなく、**FFmpegで基礎を確認し、Adobe連携は必要な機能から追加**します。

なお、GUIのクリックを繰り返す自動操作は最後の手段です。ウィンドウ位置、ダイアログ、アップデートに影響されやすいため、**API→ファイル連携→GUI操作**の順で検討します。

## 🎞️ 5．FHD・拡張子・納品パッケージの採用案

### 最も重要な注意：横FHDから縦FHDへの切り抜き

1920×1080の横動画から9:16で中央を切り抜くと、使える領域は概ね**608×1080**です。それを1080×1920へ拡大しても、元の細部が増えるわけではありません。

したがって、**「出力がFHD」と「細部までFHD相当の画質」は別**です。

縦動画では場面ごとに使い分けます。

- 人物中心：人物に合わせてクロップ
- スライド・操作画面：全体を残して上下に字幕や図版を配置
- 対談：上下2分割
- 細部が重要：元動画の拡大表示と全体表示を切り替える
- 取得可能なら：元動画を4Kで取得し、FHDへ仕上げる

**AIアップスケールは、機器表示・数値・細かな文字の正確さを保証しません。** 重要な画面では、拡大生成よりレイアウト変更を優先します。

### 形式の推奨

| 形式・拡張子 | 用途 | メリット | デメリット・判断 |
|---|---|---|---|
| **MP4＋H.264＋AAC** | 自社サイト・確認・一般配布 | 再生互換性が高く、扱いやすい | **標準採用** |
| **MOV＋ProRes** | 高品質の中間素材・保存マスター | 再編集や合成に向く。4444は透明部分を扱える | 大容量。必要な素材・マスターだけ |
| **WebM＋VP9／AV1** | Web配信の追加版 | 内容・設定によって容量を削減できる | エンコード時間、再生環境の確認が必要。初期は見送り可 |
| **HLS：m3u8＋分割ファイル** | 通信速度に合わせるストリーミング | 長尺・多数視聴者に対応しやすい | 単一動画ファイルではなく配信一式。初期から自作しない |
| **SRT** | 字幕の修正・編集ソフトへの受け渡し | 単純で対応ソフトが多い | 複雑な見た目は保持しない |
| **WebVTT：vtt** | 自社サイトの字幕 | ブラウザーの字幕表示に向く | サイト側プレイヤーの対応が必要 |
| **PRPROJ** | Premiereの編集プロジェクト | 人が再編集できる | 元素材・フォント・プラグイン等も必要 |
| **JSON** | 編集計画・検査結果 | 自動化・差分管理に向く | 動画として再生する形式ではない |
| **ZIP** | 納品物をまとめる | 一括受け渡しに便利 | MP4自体はあまり圧縮されない |

XML・OTIOなどは編集内容の受け渡しに使えますが、**字幕、エフェクト、フォント、MOGRTまで完全に一致する保証はありません**。初期の正本は「編集計画JSON＋素材＋Premiereプロジェクト」とし、交換形式は実際に必要な場合だけ追加します。

### 初期の書き出し設定案

- 横：1920×1080
- 縦：1080×1920
- 映像：H.264、プログレッシブ
- 色：SDR／Rec.709を基本。HDR素材は適切に変換
- 音声：AAC、48kHz
- フレームレート：素材の主要なfpsに合わせて制作単位内で統一
- ビットレート：**8～12Mbpsを試験の出発点**とし、動き・細かい文字・容量で調整
- Web向け：先頭から再生を始めやすいMP4構造、いわゆるfast start

映像10Mbpsなら、音声等を除いて、10分で約750MB、30秒で約37.5MBです。自社サイトでは容量が効いてきます。

### 自社サイトでは「FHD原本」と「配信用」を分ける

- FHDの完成マスターは必ず保存
- サイトにはMP4＋サムネイル＋VTT字幕＋内容のテキストを用意
- スマートフォン・Safari・Chrome・Edgeで再生確認
- 大容量動画をページ表示時に全部読み込ませない
- 視聴数や帯域が増えたら、CDNや動画配信サービスで可変画質配信を検討
- CMSへの公開は、制作エージェントとは権限を分離

**動画を作ることと、安定して配信することは別工程**として管理します。

## 💰 6．QCDから見た比較と費用の考え方

Q＝品質、C＝費用、D＝導入・納品までの時間です。以下は今回の条件に対する設計上の比較であり、実測順位ではありません。

| 構成 | Q：品質・調整自由度 | C：費用 | D：導入 | 今回の位置付け |
|---|---|---|---|---|
| 切り抜きSaaS中心 | 短尺は早く整う。横長構成・厳密な文脈保持には確認が必要 | 継続利用料・入力分数・出力枠等 | 最も早い | **短尺の比較基準・部分採用** |
| Claude＋FFmpeg中心 | 編集ルールを細かく管理可能。凝った演出は開発が必要 | 利用料は抑えやすいが開発工数がある | 中程度 | **最初の試作に採用** |
| Claude＋Premiere UXP＋AME | Adobe上で修正でき、ブランド表現を作り込みやすい | Adobe追加費用の有無＋連携開発・保守 | やや長い | **目標構成** |
| Claude＋Remotion | 字幕・図表・定型モーションを再現しやすい | 企業ライセンス＋開発・保守 | 中程度 | 演出の量産が増えたら検討 |
| 生成動画API中心 | 補助映像の表現は広いが、原素材の正確な再編集には不向き | 試行回数で費用増 | 生成自体は早いが確認負荷あり | **主軸にしない** |

### Claude Code Proと追加課金

公式料金ページでは、Claude Proは**月払い20米ドル**、年払いは**年200米ドル**です。税等は別で、利用上限があります。

- Claude CodeはProに含まれる
- Claudeのチャット等と利用枠を共有する
- Pro契約だけで、外部APIが無制限に使えるわけではない
- 長時間・大量の開発では利用上限に達する可能性がある
- 自作アプリからClaude APIを呼ぶ場合は、別の課金経路として管理する

出典：[Claude公式料金](https://claude.com/pricing)

最初は、**ユーザーがClaude Codeから実行を開始し、ローカル処理を進め、完成後に確認する運用**で十分です。定時起動や完全無人運転へ拡張する場合は、認証・実行権限・失敗通知を含めて設計し直します。

Claude Codeには非対話実行が公式にあります。ただし、Python／TypeScriptのAgent SDKへ移す場合も含め、**認証方式と利用枠を同じものと決めつけない**ようにします。

出典：[Claude Codeのプログラム実行](https://code.claude.com/docs/en/headless)

### Fableは「難所だけ」でよい

確認できたClaude Fable 5.1の標準API料金は、以下です。

| 項目 | 100万トークン当たり |
|---|---:|
| 入力 | 10米ドル |
| 出力 | 50米ドル |

例えば、キャッシュ等を考慮しない**累計入力10万・出力2万トークンなら2米ドル**です。ただし、エージェントは会話履歴やコードを繰り返し入力するため、見えている指示文の長さだけでは費用を見積もれません。

採用する場面は以下に絞ります。

- Premiere連携の設計が行き詰まった
- 原因不明の不具合が繰り返す
- 複数の処理方式から最適な設計を選ぶ
- 大きな改修をまとめてレビューする

Fableは標準で安全監視のための30日間保持が案内されています。外部送信許可済みでも、**利用する製品の保持条件まで確認**します。

出典：[Claude Fable公式情報](https://www.anthropic.com/claude/fable)

### 開発・運用費は、次の式で比較する

**月間総費用＝固定費＋AI／動画API費＋保存・配信費＋人の確認時間＋開発費の月割り＋保守費**

週2本程度では、API単価よりも、**過剰な自作と修正作業の方が高くつく可能性**があります。

私なら、初期検証では次の予算ルールを置きます。

- 追加従量課金：**月5,000円相当を暫定上限**
- 上限未設定の状態では有料APIを動かさない
- 1ジョブ・月間の両方で上限を管理
- 同じ素材を再処理しないよう結果を保存
- 生成動画は初期段階では無効
- Adobe連携の最小試験が通るまで大規模開発をしない

5,000円はサービス料金の見積もりではなく、**検証時の損失を制限するための提案値**です。

## 🚀 7．準備・開発・運用・継続の進め方

### ① 準備：素材と判断基準を揃える

実施すること：

1. 元動画3本と参考動画を登録する
2. CPU・GPU・ディスク・Adobeバージョンを確認する
3. 参考動画から編集仕様を作る
4. 用語辞書・ロゴ・使用フォント・禁止表現を準備する
5. 制作単位と、短尺の最大本数を決める
6. 追加費用と公開権限を分ける

**ジャンルを固定しない代わりに、内容の正確さ・読みやすさ・出典追跡などの共通基準を固定**します。

### ② 開発：最初は1本で一連の処理を通す

開発を分割します。

| 段階 | 作るもの | 次へ進む条件 |
|---|---|---|
| 最小試験 | 素材情報取得→指定区間カット→FHD書き出し | 出力が正常に再生できる |
| 内容理解 | 時刻付き文字起こし、場面一覧、話題候補 | 元動画との対応を確認できる |
| 編集判断 | 横長構成案、短尺候補、編集計画JSON | 出典時刻に誤りがない |
| Adobe連携 | 素材配置、プロジェクト保存、AME書き出し | 実機で繰り返し成功する |
| 運用機能 | 再開、費用上限、検査、レビュー画面 | 途中失敗しても重複課金・上書きを防げる |

**短い試作は数営業日で作れる可能性がありますが、Adobe連携・復旧・検査まで含む運用版は別です。** 計画用には、実装担当者による**10～20人日程度の枠を仮置き**し、最小試験後に見直すのが無難です。これは見積書ではなく、未検証の計画値です。

### ③ 運用：AIは完成まで、人は内容確認と承認

標準の運用は次の形です。

1. 元動画を入力フォルダーへ置く
2. 制作指示を読み込ませる
3. AIが編集・書き出し・検査する
4. レビュー画面で完成動画、出典、警告を見る
5. 修正点だけを指示する
6. 承認した版を公開担当へ渡す

レビュー画面には、以下を並べます。

- 完成動画
- 元動画と使用時刻
- 削除・並べ替えの要約
- 字幕一覧
- 自動検査結果
- 要確認箇所
- 処理時間・API費用
- バージョン番号

**10分版の内容を確認するなら、少なくとも10分相当の視聴時間は必要**です。短尺確認と修正も含め、初期の目標は**1制作単位あたり20～40分程度の人手確認**とし、実測で更新します。

### ④ 継続：毎回の修正を、ルールとテストに戻す

- 誤認識を用語辞書へ追加
- 採用しなかった短尺の理由を記録
- 字幕の長さ・画角・カットの失敗をルール化
- ツールとモデルのバージョンを記録
- アップデートは既知の素材で回帰試験してから採用
- 月ごとに費用と修正時間を集計
- 再生数だけでなく、視聴維持・内容理解・サイト内の次の行動も確認

週2本ではデータ量が小さいため、1～2本の成果だけで編集方針を頻繁に変えない方がよいです。

## 🛡️ 8．自動運用に必須の品質・安全対策

### 自動検査に向くもの

- 解像度・コーデック・fps・尺
- 音声トラックの有無
- ファイル破損、全編デコードの可否
- 不自然な黒画面・静止・無音の候補
- 字幕の重複、表示範囲外、極端な短時間表示
- ロゴ・フォント・素材の欠落
- 音量の大きな差
- API失敗、書き出し失敗、費用超過

黒画面や無音は意図的な場合もあるため、**検出したらすべて失敗ではなく、仕様と照合して警告**します。

### 人の確認を残すもの

- 発言の切り方で意味が変わっていないか
- 否定、条件、例外が落ちていないか
- 数値・製品名・人名が正しいか
- 発言と画面が対応しているか
- 縦画面で必要な情報が隠れていないか
- 参考動画への寄せ方が適切か
- 公開先に合った内容か

医療機器・医療情報を扱う場合には、**効能・性能・適応・注意事項の編集で誤認を招かないか**を、必要な社内確認へ回します。これは動画のジャンルを限定する意図ではなく、自社サイト利用時の追加条件です。

### エージェントの権限

- 元素材は読み取り専用
- 出力先は制作フォルダー内に限定
- APIキーはコード・ログ・動画内へ書き込まない
- プラグイン・MCPは公式またはコード確認済みのものを使用
- 素材中の字幕・説明文を、システムへの命令として実行しない
- リトライ前に既存ジョブを照会し、重複課金を防ぐ
- 公開・削除・有料プラン変更は自動承認しない
- レンダリング待機中にAIへ無意味な確認を繰り返させない

**「動画を処理するエージェント」と「自社サイトを公開更新するエージェント」は、権限を分ける**のが安全です。

# 動画編集AI・制作エージェント検討：前提情報とこれまでの経緯

本資料は、検討の背景、ユーザーから提示された条件、これまでの議論、未確定事項を整理した引き継ぎ用の背景資料である。
AIへの実行指示、開発命令、毎回の制作プロンプトは含まない。

整理日：2026年10月6日

## 📌 1．検討の背景と目的

既存の動画素材を活用し、AIによる切り抜き・短縮編集を行う方法を検討している。

単に動画生成AIの名称を知ることではなく、具体的なサービスの正式名称・公式サイト・実現方法を把握し、自分で採用できる構成を検討することが目的である。

想定する最終的な運用は、エージェントが動画の分析、構成、編集、書き出しまでを行い、ユーザーが成果物を確認する形である。

検討には、準備・開発・運用・継続改善の各段階を含める。

公開先には自社サイトを含む。主に日本向けの利用を想定しているが、技術的に有用な海外のサービスや手法も積極的に検討対象とする。

## 🎬 2．制作対象と求める成果物

## 🔍 11．技術面で共有した重要な論点

- AIによる新規動画生成と、既存動画の切り抜き・編集は別の機能である。
- Claude Code自体が動画のレンダリングエンジンになるわけではない。
- Premiereの画面にある機能すべてが、同じようにAPIから利用できるとは限らない。
- Premiereのデスクトップ自動化と、完全なヘッドレスサーバー処理は区別する必要がある。
- 場面転換検出と、意味上の話題転換検出は同じではない。
- 文字起こしだけでは、無言の実演や重要な画面変化を十分に評価できない。
- 横FHD素材を縦FHDへクロップすると、元映像の利用領域が減り、拡大が必要になる。
- FHDの出力寸法を満たすことと、細部までFHD相当の画質があることは別である。
- 技術検査の自動化と、内容の正しさの人手確認は分けて考える。
- 自社サイト向けには、動画制作だけでなく保存・配信・字幕・再生互換性も検討対象となる。
