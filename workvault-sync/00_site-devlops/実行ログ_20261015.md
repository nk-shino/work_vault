## 2 実施（1）SSRFの宛先判定がIPv6に対して空振りしていた

### 観察した事実

`assertAllowedUrl`（`server/lib/safeFetch.ts`）の内部アドレス判定が、
**IPv6リテラルのURLに対して一度も発火していなかった。**

原因は2つ重なっていた。

1. `URL.hostname` は IPv6 を `[::1]` と**角括弧付き**で返す。
   `net.isIP('[::1]')` は 0 を返すため、判定の条件が常に false
2. `isDisallowedAddress` の IPv4射影の判定が**点つき十進しか見ていなかった。**
   URL を通すと `::ffff:127.0.0.1` は `::ffff:7f00:1` へ正規化されるので、実経路の表記で素通りする

### 実害の範囲

**NAT64 `64:ff9b::7f00:1` は本物のTCP接続まで進んでいた。**
`safeFetch` が `BlockedUrlError` ではなく4秒のタイムアウトで終わることで確認。
CLAT のある環境ならこの接続は `127.0.0.1:443` に落ちる。

その他のIPv6は名前解決側（`guardedLookup`）が結果的に止めていたが、
**多層防御の1層が完全に死んでいる状態**だった。

### 直したこと

- 角括弧を外してから `net.isIP` へ渡す
- 文字列の前方一致をやめ、**IPv6を8グループの数値へ開いてから範囲で判定**する
  （`expandIpv6`）。射影・IPv4互換・NAT64・6to4 は下位32ビットを取り出して IPv4 側へ回す

### 確かめたこと

```
拒否すべき20件        すべて拒否（直す前は IPv6リテラル が1本も止まらなかった）
通すべき公開5件        すべて通過（巻き添えなし）
URL経路11件            すべて期待どおり
safeFetch('https://[64:ff9b::7f00:1]/')
  直す前  4007ms でタイムアウト（＝TCP接続していた）
  直した後  5ms で BlockedUrlError
```

**変異11件中10件を殺した。** 残る1件（`if (!g) return true`）は到達不能の安全網で、
`net.isIP` が IPv6 と認める19通りの書き方すべてを `expandIpv6` が読めることを確認済み。
**等価変異なので試験で殺せないのが正しい。** その旨をコードのコメントに書いた。

## 3 実施（2）防御本体に試験が届いていなかった

### 観察した事実

36件の試験のうち、**次の6関数は一度も実行されていなかった**（監査の変異試験による。
関数先頭に throw を入れても全件通る）。

`once` / `guardedLookup` / `saveFromUrl` / `getLinkPreview` / `runOcr` / `guardErrorResponse`

**SSRF防御の本体（名前解決の差し替え）がここに入っている。**

あわせて、**自分が一度直し損ねた穴**がここにあった。
`pickImageUrl` を切り出して試験を書いたが、**呼び出し側（`getLinkPreview`）を
元のバグへ戻しても全件通る**状態のままだった。部品を試験しても、
その部品を正しく呼んでいるかは別の話で、1段下がっただけだった。

### 直したこと

既にある `RequestOnce` と同じ形の継ぎ目を2か所に足した。**新しい依存は入れていない。**

| 対象 | 足した継ぎ目 |
|---|---|
| `makeGuardedLookup(resolve)` | 名前解決を差し替えられるようにした。本物のDNSでは「内部へ解決される名前」を用意できず、いちばん効いてほしい分岐が通らないため |
| `getLinkPreview(url, allowHosts, requestOnce)` | 取得を差し替えられるようにした。**呼び出し側から通さないと、部品の試験は飾りになる** |

### 足した試験（9件）

- 既定の上限（`maxBytes` / `timeoutMs` / `accept`）が取得側へ渡っている
- 名前解決: 内部へ解決する名前は接続させない／どの名前かが文面に出る
- 名前解決: 公開と内部が混ざったら内部だけ落とす（`all` 有無の両方の返し方）
- 名前解決: 解決そのものの失敗は握りつぶさず返す
- 取得経路: 長い画像URLが途中で切られない（**元のバグへ戻すと落ちる**）
- 取得経路: 題と説明は300字で切り、画像だけ別扱い。相対URLも解決する
- 取得経路: HTML以外と失敗応答は取り込まない

### 確かめたこと

**変異12件すべてを殺した。** とくに
「画像URLを呼び出し側で切る（元のバグそのもの）」が2件の試験を落とすことを確認。
**同じ穴が再発したら止まる状態になった。**

### 今回やらなかったこと

`once` / `saveFromUrl` / `runOcr` / `guardErrorResponse` は未着手。バックログへ。

### GIF は論理画面サイズで嘘をつける

34KB の GIF が 1x1 と名乗りながら 10000x10000 のフレームを持てる。
`imageProbe` が先頭の論理画面サイズしか見ていなかったので上限の検査を素通りし、
**デコーダはフレームの寸法に従う**ため、OCR が一億画素ぶんを確保して成功していた。
`MAX_PIXELS` は 16,000,000 なので 6.25 倍。

**本物の GIF で確かめた**（合成ではなく System.Drawing で作ったもの）。

| ファイル | 大きさ | 直す前 | 直した後 |
|---|---|---|---|
| `lie.gif`（3000x3000 を 1x1 と偽装） | 10.6KB | probe=1x1 | **probe=3000x3000** |
| `big-lie.gif`（5000x5000 を 1x1 と偽装） | 22.8KB | 1x1 として保存された | **`MediaError: 画素数が多すぎます（5000x5000）`** |
| `real-200.gif`（正直） | 1.8KB | 200x200 | 200x200（巻き添えなし） |

二重にした。**ヘッダが嘘をつけるのは GIF に限らない**ので、
入口で形式ごとに追いかけるより展開の直前にもう一度見るほうが確実。

| 層 | すること |
|---|---|
| `imageProbe.ts` | ブロックを歩いて、実際に展開されうる最大の寸法を返す。グローバルカラーテーブル・拡張ブロック・サブブロックを読み飛ばす。壊れたファイルで回り続けないようブロック数で打ち切る |
| `ocr.ps1` | デコーダに `PixelWidth`/`PixelHeight` を聞いて、`GetSoftwareBitmapAsync` が確保する前に断る |

上限の数字を2か所に持たないよう、`runOcr` から `-MaxPixels` で渡している。
`ocr.ps1` の門も実機で確認した。
