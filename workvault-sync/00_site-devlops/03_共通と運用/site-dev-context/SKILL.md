# サイト開発コンテキストの読み込み

資料サイト（回廊の記録）の作業を始めるとき、このスキルに書いた内容を確認してから着手する。明示的に指示しない限りAIは確認しない項目を、ここに固定する。確認を省略したまま実装や報告をしない。

## 過去に起きたこと（再発させない）

- fixture の件数を別の対象の基準に使った（「作品13」は mock/works.html の件数）。基準値は対象ごとに実測する
- 注記セクションの削除で main dt などの件数基準値が変わった。構造を変える変更のあとは基準値を再実測し、テスト側を同じ変更内で更新する
- ブラウザキャッシュが旧HTML・旧CSSを返し「未適用」と誤判定した。期待と異なる値は、ディスク上の実ファイルとの照合を先に行い、URL にクエリを付けて再実行する（ERRORS.md ERR-20261026-001）
- catalog-a.js の空データ差替ボディは `{"catalog": []}` が必須。`[]` にすると pageerror で落ちる
- 並行セッションが同一ブランチにコミットしている。コミット前は git status と git log を確認し、自分のトピックフォルダだけを add する。git 名義は nk-shino であることを照合する
- 実行ログは指示1件＝エントリ1件（指示／実施／成果物／状態）。完了報告の前に記録の実在を確認する（forced-logging スキル）

## 技術方針（現行）

- デザインシステムは部分採用。採用と不採用を文書に残し、根拠は公式 usage ページに限る
- 文書表現: 下線はリンクのみ。太字は strong に限定。badge は色と文字の併記。見出しは text-wrap: balance、本文段落は pretty
- 設計判断は設計判断の記録に集約する。公開頁に内部文書参照（§番号・ノート名）を書かない
- 色は既存 CSS 変数経由で扱い、ダークモードへ自動追従させる。CDN は使わない（訪問者の IP を第三者に渡さない）

## 実行のしかた

1. 所在と未決の確認結果を短く報告してから作業に入る。不明点は質問で解決する
2. 実リポジトリを基に必要要件を適用する。fixture で整え、基準値は実測、`tools/run-tests.js` を全通させる
3. 成果物は vault-change-and-report スキルで保管庫へ登録する。GitHub 同期は vault-sync スキル（利用者承認のあとに実行）
4. 最終案の提示と支持を求めるときはトークンを節約する。要点と前回からの差分だけを示し、根拠の再掲・全文引用・長い前置きをしない。選択肢の確認は question ツールで行う

## 登録済み MCP の活用

環境に登録された MCP を積極的に使う。手作業で置き換えない。

- Playwright MCP: 実画面検証の主手段。スクリーンショット（ライトとダーク）・getComputedStyle の実測・操作経路の実行・console 確認。ローカル検証の URL にはクエリを付けてキャッシュを回避する
- Google Design MCP: Material アイコン・フォント・配色の一次資料。アイコンを追加するときはここから探す
- Context7: ライブラリ・フレームワークの現在の仕様。既知の知識で書かず引く
- Microsoft Docs MCP: Microsoft/Azure 関連の実装とコードサンプル
- gai_support_docs: 社内AIアプリ（Rapi・Work Tracker 等）の仕様。サイトの作業が社内アプリに触れるとき
- Excel MCP: 表計算ファイルが絡む作業

MCP が無い環境では、目的が同じになる代替手順（公式ドキュメントの取得・ローカルのブラウザツール）で進め、使えなかった MCP と代替を報告する。

## このスキルの更新

- 正本の移動・追加があったら所在一覧を直す。このスキルが所在の案内である
- 新しい失敗は「過去に起きたこと」に1行で足す。詳細は ERRORS.md 側に置く
- 方針が決まったら「技術方針（現行）」を差し替える。旧方針の説明は残さない
- 未決が決まったら「未決事項」から外し、新しい未決を足す。実行ログの「状態」と一致させ続ける
- このスキルの変更と失敗記録（.learnings）は、設定フォルダ・gitignore 配下に置いたままにしない。保管庫の控え（00_site-devlops/03_共通と運用/）へ上書き出力する
