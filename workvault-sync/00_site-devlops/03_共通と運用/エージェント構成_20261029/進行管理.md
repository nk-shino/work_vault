# 進行管理（コーディネータ）の運用

進行管理はサブエージェントではなく、セッション本体（主エージェント）の振る舞いとして定義する。Kohden Code では AGENTS.md・project config・セッション開始プロンプトで実現する。専門役（agent/*.md）の割当と状態管理だけをここに定める。

## 1. 役割割当と並行の上限

| 専門役 | ファイル | 主な成果物 | 権限 |
| --- | --- | --- | --- |
| 調査・要件判断 | agent/site-research.md | 課題記録・根拠台帳・代替案・受け入れ条件 | 読み取り＋Web調査・編集不可 |
| 情報整理・整合性確認 | agent/site-curator.md | 情報整理シート・確認待ち・更新ノート | 編集可（文書・データ） |
| 設計・UI/UX | agent/site-design.md | 設計書・画面案・実装差分案・判断の記録 | 編集可 |
| 実装・デバッグ | agent/site-implement.md | 実装差分・テスト結果・実装記録 | 編集可 |
| 独立レビュー・検証 | agent/site-review.md | レビュー指摘・テスト証跡・残余リスク | 読み取り専用（edit: deny） |

- 同時に動かす専門役は **2体まで**（根拠: 2026-10-29 の事例調査。Anthropic agent teams「まず3〜5・集中した3体が散らばった5体に勝る」／Google Research 2026-01 構造なし並列は誤り17.2倍／個人報告「並列は2〜3体が実用上限」）。設計→実装は逐次とし、レビューは実装完了後に独立して動かす
- 同じファイルを複数担当が同時に編集しない。割当変更時は引き継ぎメモを残す
- 逐次タスク・小さな修正は、専門役を起かさずセッション本体が直接行ってよい

## 2. 進行管理が記録するもの

| 記録 | 内容 |
| --- | --- |
| 計画 | 対象課題・優先順位・割当・並行構成（最大2体） |
| 判断履歴 | 採用・不採用と理由。安全に決定した範囲は推奨案を選び進めた旨を明記 |
| 状態一覧 | 各課題の状態（未着手／進行中／実装・検証済み／変更不要／環境不足／承認待ち） |
| 承認台帳 | 実API・依存追加・commit/push・公開など承認範囲と期限（自律開発ガイド §5 の様式） |
| 再開メモ | 完了・進行中・保留・次の安全な手順 |

## 3. 進行管理の着手手順（セッション開始時）

1. 共通規約を読む。実行ログ・質問台帳・Git 状態で現在地を確認する
2. 課題を受け付け、調査担当に根拠の確定を依頼する（受け入れ条件がない課題を実装に渡さない）
3. 割当と並行構成を決め、状態一覧を書く
4. 専門役の成果物を順次受け取り、次の担当へ渡す。受け渡しはノート越しに残す
5. 区切りごとにチェックポイント（状態・次の1手）を保存し、切断に備える
6. 完了報告の前に、実行ログの実在と記録の整合を確認する

## 4. 完了条件と保留の運用

- 完了は「実装・検証済み」まで。検証担当の指摘が残る状態で完了扱いにしない
- 重大な未確定事項は BLOCKED として台帳に残し、独立した安全な作業を続ける
- 機能の採用判断と本番反映の承認は分離する。採用済みの機能も、公開・commit/push は明示承認を待つ
- 変更不要の結論も、根拠付きで完了判定に含める

## 5. 再開手順（セッション切断後）

1. 保管庫の実行ログ・ノート・再開メモを読み、最後のチェックポイントを確認する
2. Git 差分で実際の変更状態を確認する（成功/失敗を推測しない）
3. 重複実行を避け、未完了の1手から再開する。再試行は回数制限を付け、部分失敗を分離する
