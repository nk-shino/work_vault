# 判断プロトコル — ユーザーの意見・新機能の検証テンプレート

ユーザーから意見・要望・新機能の提案が出されたとき、それを正しいかどうか、実装すべきかどうかを判断するための標準手順。新機能の検討もこのテンプレートに従う。テンプレートとして、この様式をそのまま複製して使う。

## 0. 使い方（進行管理の操作）

1. 意見・提案を1件ずつこのテンプレートへ複製し、ID を振る（例: J-01）
2. site-research に根拠の収集を、site-review（または独立の視点）に反証の確認を依頼する
3. 同じ担当が提案と検証の両方をしない。提出者と検証者を分ける
4. 判断は運営者が行う。エージェントは材料と推奨を出すだけにする

## 1. 検証対象の記入欄

| 項目 | 記入 |
| --- | --- |
| ID / 日付 | |
| 意見・提案の原文 | ユーザーの言葉のまま。要約で置き換えない |
| 提案者が想定する効果 | 提案者の言葉のまま |
| 分類 | 事実確認の対象／設計判断の対象／規律・権利の対象 |

## 2. 分解（必要性・適合性・有効性を混同しない）

*   **必要性**: サイトにとってその意見・機能が必要か。何の問題を解決するか。現状の代替で足りないか
*   **適合性**: それが現在の頁・運用に合うか。置く場所・条件・タイミングは適切か
*   **有効性**: 実装したときに、想定した効果が実際に得られるか。測定可能か

「既存機能でできるから」という理由だけで、必要性の検討を省略しない。既存機能での代替案を対等な選択肢として並べ、比較する。

## 3. 根拠の収集（site-research）

| 根拠 | 出典・日付 | 確認済み/未確認 |
| --- | --- | --- |
| 現状の実測（件数・挙動・ログ） | | |
| 公式資料・仕様 | | |
| 類似事例・先行例 | | |
| 費用・負担の見積り | | |

事実／推論／仮説／不明を分ける。出典のない主張は根拠欄に置かない。

## 4. 反証と多視点の確認（独立の担当）

*   反対意見を最低1件、意図的に作る（自分の案に反対するなら何と言うか）
*   プレモーテム: 導入したと仮定して失敗した場合の原因、不導入の場合の失敗も書く
*   複数の根拠が同じ方向を指すか確認する（1つの根拠だけでの結論を避ける）
*   多数派の意見・AI間の一致を、真偽や適法性の証明として扱わない

## 5. 影響の評価

| 軸 | 評価 |
| --- | --- |
| 作業負担 | 実装・検証・維持に必要な工数 |
| 情報品質 | 出典・訂正・鮮度の管理への影響 |
| アクセシビリティ・性能 | 影響する範囲と確認方法 |
| 権利・プライバシー | 素材・計測・外部送信の影響 |
| テスト | 基準値の変更・追加の有無 |
| 戻し方 | 実装後の取り消し手順 |

## 6. 判断欄（運営者が記入）

| 項目 | 記入 |
| --- | --- |
| 推奨 | 導入／限定導入／保留／不導入／現状維持（根拠付き。現状維持も選択肢） |
| 不確実性 | 残る不明と、それが判断に与える影響 |
| 決定 | 導入／不導入／保留（日付） |
| 次の1手 | 受け入れ条件の作成・モック・保留の再検討時期など |

## 7. 記録

*   検証結果は保管庫のノートへ保存する。台帳（質問一覧_サイト側.txt）に関係する質問があれば状態を更新する
*   実装に進む場合は、調査担当が受け入れ条件を確定してから実装担当へ渡す
