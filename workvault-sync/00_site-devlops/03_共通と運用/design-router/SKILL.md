# デザイン作業の振り分け

デザイン系のスキルは5つに分かれており、相互参照がほとんどない。依頼を受けたら
まずこの表で対象を決め、指定先のスキルを読んでから着手する。

| 依頼の内容 | 使うもの | 要点 |
|---|---|---|
| 画面案を出し、方向性を合意したい | `ui-mockup` → 質を上げる段階で `@designer` | モックは捨てられる前提。撮影必須 |
| 既存アプリのUI/UXを改善したい | `ui-revamp` | 一次資料の部分採用。範囲合意を先に取る |
| 新規に独自性のある見た目を本実装したい | `frontend-design` ＋ `@designer` | 既存アプリの改修には使わない |
| サイト「回廊の記録」の設計 | `site-dev-context` → `@site-design` | サイト固有規約が優先 |
| 納品前の見た目・表記を点検したい | `deliverable-compliance-review` | 項番2・5・8・12・13・14が視覚 |
| 設計済みの変更を機械的に実装したい | `@fixer` | 設計判断を含むなら `@designer` |

## 判断の順序

1. 対象は既存か新規か（既存→`ui-revamp`／新規→`frontend-design`）
2. 成果は「案」か「実装」か（案→`ui-mockup`／実装→`@designer`・`@fixer`）
3. 制作か点検か（点検→`deliverable-compliance-review`）
4. サイト案件か（→`site-dev-context` を最初に読む）

## 共通の禁止

- 既存アプリへ `frontend-design` の独自性重視の指針をそのまま適用しない。
  配色変数・余白のリズム・文言のトーンを壊す（部分採用と範囲合意は `ui-revamp` の手順）
- モックのHTMLを本番コードへ持ち込まない。モックと本実装は別物として扱う
- 制作した担当に自分の成果の点検を完了扱いさせない。独立レビューは `@site-review`
  または `multi-view-review` を使う
- デザインの判断根拠を感覚で書かない。色はHEX、位置は座標、余白は実測値で示す
  （`ui-revamp` の検証節と `deliverable-compliance-review` の根拠記載に従う）
