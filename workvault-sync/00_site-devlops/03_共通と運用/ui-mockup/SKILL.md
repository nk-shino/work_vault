# UIモックアップ一式作成と確認ループ

モックアップの価値は「早く・安く・捨てられる」こと。完成度を追って本実装と
同じコストをかけると目的を失う。このスキルは方向性の合意までを担当する。

## 手順

1. **確定** — 画面一覧・主要操作・ダミーデータの概要を作る前に文章で固める。
   曖昧な点は完璧を狙って質問攻めにせず、仮置きした1案を先に出して修正させる。
2. **作成** — 静的HTML、1ファイル=1画面。共通CSSは外部1枚にまとめる。
   ダミーデータは実データに近い日本語にする(「テスト1」のような無意味な文字列は
   レイアウト判断も含めて評価を歪める)。
3. **撮影** — playwrightで各画面のスクリーンショット(fullPage)を取得し、
   ファイルパスをユーザーへ提示する。撮影せず「できました」は認めない。
4. **反復** — 指摘 → 修正 → 再撮影。1往復では指摘された画面に集中する
   (全画面を一斉にいじると差分が追えない)。
5. **確定** — 確定版を保存し、次ステップ(本実装/棚上げ)を明記して記録する。

## 規模の目安

- 5画面以下: 1往復で一式作ってよい。
- 6画面以上: まず主要3画面だけ作り、方向性を確認してから残りを作る(作り直しコストの抑止)。

## designer へ委任する場合

モック作成を @designer に委任するときは、スキル名を伝えるだけでは手順が守られない
(2026-11-09 時点の実績: モック作成セッションで本スキルの起動0回・すべて委任で処理)。
次の雛形をそのまま委任プロンプトへ転記する。

- 目的: 方向性合意用のモック。完成品ではない。作り直しを前提に捨てられる形で作る
- 画面: 1ファイル=1画面。共通CSSは外部1枚。画面一覧を先に列挙する
- ダミーデータ: 実データに近い日本語。「テスト1」のような無意味な文字列は使わない
- 制約: 既存の配色変数・余白のリズムを壊さない／絵文字を使わずSVGかテキスト／
  状態は色だけで示さずテキストを併記する
- 必須の成果: playwright で各画面の fullPage スクリーンショットを撮り、保存パスを報告する
  (撮影なしの「できました」は不可)
- 反復: 指摘された画面に集中する。全画面を一斉に変えない
- 規模: 6画面以上なら主要3画面で方向性を確認してから残りを作る

## 連携

- 見た目の質を上げる段階 → designerエージェントに委託する。
  デザイン意図(レイアウト・余白・モーション)を壊さず、文言は後から整える。
- 確定後の本実装 → fixer/designerへ設計を渡す。
- 既存アプリへの適用・改修 → ui-revamp(一次資料に基づく部分採用の手順)。
