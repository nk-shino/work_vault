# 改善案（2026-10-16）

**対象は15ページ全体。根拠は手引きと設計論点の実測値のみで、コードも実画面も見ていない。**
種別ごとの一般論と実測を組み合わせ、そのまま箇所レベルの指示としては使えない。
先進的な取り組みは出典を確認できたものだけ挙げ、確認できないものは入れていない。

## 案の比較（A / B / C）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A. 現行を生かした最小修正** | 罫線トークンの置換完了（§7 の負債）と、絞り込み0件の文言分け（設計論点 論点2）に絞る | 手数が小さい。§4 の原則と §3 の制約に触れない。絵が入った日にも無駄にならない | 空データ3ページの行き止まり感は残る。見た目の変化は小さい |
| **B. 発見・比較を重視** | 0件ページに次の行き先を出す。人物一覧を文字主体の配置へ寄せる。一覧同士の横断導線を増やす | 0件でも読者が別の記録へ到達できる。記録性（優先1）に合う | §6-3 の論点2（絵が入ったときの組み直し）と重なる。戻せる形にする条件を付ける必要がある |
| **C. 根拠・確認状態を重視** | 検証状態の表示を目録棚の外へ広げ、詳細ページにも出典と確認状態を並べる | 「不確かさの明示」（§1 の優先1）に最も直結する。既存の sources / catalog の仕組みの延長で組める | 表示項目が増え、可読性と競合する恐れ。実装の重さは未実測 |

**推奨は A を先に、B は「絵が入っても崩れない形」に限って後段に、C は catalog・sources の2ページに限って検討、の順。**
根拠は、A が手引き §7 で既に指摘済みの負債の解消であり新規判断を要しないこと、
B の人物一覧の組み直しが §6-3 で「2 が本体」と書かれた論点と同じであること、
C の表示拡張が sources.json（8群）の既存構造の上に乗ること。この3点は実測に基づく。

## 指摘（観察した問題 → 利用者への影響 → 根拠 → 改善案 → 確認方法）

### 指摘1：絞り込み0件と元から0件の文言が同じ（catalog / works / chara / glossary / tools-goods）

- **観察した問題：** 格子ページの絞り込みで0件になったとき、恒常0件と同じ「準備中です」の形が出る。設計論点 論点2 の「3 が実害に近い」に該当する
- **利用者への影響：** 条件を外せば戻るのに、読者は「このサイトには無い情報」と判断して離れる恐れがある
- **根拠：** 設計論点.md 論点2（3つの状態を一括りにしている指摘）・手引き §6-2。コードは未確認で、実装が共通部品か個別かは分からない
- **改善案：** 絞り込み0件は「条件に合う項目が無い」＋外す条件の提示。恒常0件は「準備中」か「募集中」かを §6-2 の論点1で決めてから出し分ける。案Aでは文言の分けだけ、案Bでは0件面に検索語ハイライト実装済み（§5）の横断検索への導線を足す
- **確認方法：** 目録棚で条件を組み0件を出し、文言と導線が絞り込み由来か確認する。3つの空データページも開いて文言を比べる

### 指摘2：空データ3ページが入口から辿れる（events / tools-fanart / tools-kirinuki）

- **観察した問題：** 3ページが0件のまま、入口（ナビ・HOME）から辿れる位置にある。手引き §2 は「3ページが空のデータを描いている。空状態の見せ方が、いま実際に使われている」と記す
- **利用者への影響：** 辿って毎回空だと、更新が止まっている印象を与える。読者の2度目の訪問に響く恐れ
- **根拠：** 手引き §2（3ファイルが0件）・§6-2（「0件のまま公開するなら、空状態は本番のデザインであって例外ではない」）。入口の実装は未確認
- **改善案：** 案Aではページを残したまま、空状態の文言を §6-2 の3分類（無い／準備中／募集中）へ揃える。案Bでは空の面に関連記録へのリンクを出す（例：events なら history へ）。ページを隠す判断は §6-2 の論点2なので、このノートでは決めない
- **確認方法：** 3ページを開き、HOME・ナビからの導線を通って空状態まで到達できるかを確認する

### 指摘3：人物一覧の画像欄が13件全員空（chara / chara-detail）

- **観察した問題：** 13人全員が「イラスト準備中」で、額縁の枠と題箋だけで並ぶ。手引き §2 は「文字と罫線と余白だけで成立させている」と記す
- **利用者への影響：** 人物の識別が文字だけに頼る。また、絵が入った日に一覧の並びが変わる恐れがある
- **根拠：** 手引き §2（image 13件全員空・描画側は用意済み・「足りないのは絵であって、実装ではない」）・§6-3（論点3「縦横比を先に決めるか」）。実画面の崩れの有無は未確認
- **改善案：** 縦横比を先に決めて空枠の形を固定する（§6-3 論点3）。案Aでは現行の題箋表示を生かす。案Bでは文字主体の配置へ寄せるが、これは §6-3 論点2 と同じ判断なので、このノートでは方向だけ示して要件定義に回す
- **確認方法：** 一覧を開き、枠の縦横比が統一されているか、詳細へ飛んだときの対応関係が取れているかを確認する

### 指摘4：罫線トークン2系統の混在（全ページ・CSS）

- **観察した問題：** 新 `--rule*` が48箇所、旧 `--border-accent` が29箇所残り、置換が途中で止まっている。手引き §7 は「片方だけ直す事故が起きる」と記す
- **利用者への影響：** 2系統の定義がずれたとき、ページによって罫線の色や太さが違って見える恐れがある。ダークテーマの旧系統は §7 に「金のまま・指示自体が古い可能性。未確認」とある
- **根拠：** 手引き §5（置換 途中）・§7（中優先の負債）。未確認の注記は §7 の記載どおりそのまま
- **改善案：** 案Aとして、旧29箇所を新系統へ置換する。色は必ずトークン経由にする（§3 の制約3）。ダークの `--border-accent` の扱いは §7 の「未確認」を解消してからにする
- **確認方法：** 置換後に `grep -c 'var(--border-accent' css/style.css` で0件を確認する。ライト・ダーク両方で一覧・詳細・HOMEを開き罫線を目視する

### 指摘5：HOME の Three.js 671KB（index のみ）

- **観察した問題：** HOMEだけがESモジュールでThree.js（671KB）を読む。手引き §3 は「671KB は重い。記録を読むページには入れない」と記す
- **利用者への影響：** 初回訪問のHOME表示に待ち時間が乗る。ただし記録を読むページへの影響は既に無い
- **根拠：** 手引き §3（ライブラリ一覧）・§1（最優先は記録性で、HOMEは入口）。読み込み時間の実測は無い
- **改善案：** 案Aでは現状維持（記録ページへ入れない運用は守られている）。案Bでは遅延読み込みやGSAPだけで組む軽量化を検討するが、効果は未実測なので数値を出さない。演出が可読性や出典表示を邪魔するなら捨てる方針（§1）と突き合わせて判断する
- **確認方法：** 開発者ツールのネットワークパネルでHOMEの転送量を確認する。キャッシュ有り・無しで2回見る

### 指摘6：出典と検証状態の表示が catalog / sources に偏っている（その他の一覧・詳細）

- **観察した問題：** 「主張と根拠の対応表」が sources、検証状態つきの横断が catalog にあるが、個別の一覧・詳細ページから出典・検証状態へ飛ぶ導線が資料上確認できない
- **利用者への影響：** 読者が一覧で出会った主張の出典を追うまでに操作が増える恐れ。§1 の優先1「出典をたどれること」との距離が伸びる
- **根拠：** 手引き §2（sources は「主張と根拠の対応表」・catalog は横断）・§1 の優先順位。個別ページの実装は未確認で、リンクが無いとは言えない。**確認が先**
- **改善案：** 案Cとして、詳細ページの項目に出典IDへのリンクを付ける（sources.json の群IDがあるため）。実装の重さはデータ側のID対応状況次第で、未実測。案Aでは、導線が既にあるなら何もしない
- **確認方法：** work-detail・chara-detail を開き、出典へのリンク・表記が既にあるかを確認する。あるならこの指摘は取り下げる

## 採用の順序（提案）

1. **先に実測**：指摘1〜3・6は、リポジトリのある環境で画面を開いて裏を取る。5分程度の目視で良い
2. **案A**：指摘1の文言分け＋指摘4の置換。制約に触れず、可逆
3. **案B・C**：§6-2・§6-3 の要件定義の結論が出てから。順序を逆にすると、片方だけの中途半端な形になる恐れがある（§6-3「片方だけ出すと、もう片方で破綻する」）

実測していない改善率・工数は書いていない。全ての確認方法は、実画面の目視か開発者ツールで確かめられる形にしている。
