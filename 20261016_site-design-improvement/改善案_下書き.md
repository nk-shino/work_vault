# サイト改善案（全ページ・下書き）

質問ノートの回答を受けた改善案の下書き。確定後に 00_site-devlops/質問_改善案の対象ページ_2026-10-16.md へ整理して追記する。

## 前提

- 対象: 手引き §2 の15ページ全部。ページ種別ごとに一般論＋手引きの実測で組む
- 根拠: 手引き §1〜§7・設計論点.md の実測値のみ。コードは見ていない。実画面も見ていない
- 業界評価・先進的取り組み: 出典を確認できたものだけ入れる。確認できないものは入れない

## 指摘（5項目形式）

### 指摘1: 空データ3ページの入口（events / tools-fanart / tools-kirinuki）

- 観察した問題: 3ページが0件のまま入口から辿れる。空状態は「準備中です」＋説明1行の一括り（設計論点 論点2）
- 利用者への影響: 入口から辿って毎回空だと、サイト全体の情報が揃っていないという印象になる。「準備中」が恒常化すると、更新が止まっているように読める
- 根拠: 手引き §2（events.json / fanart.json / clips.json が0件）・§6-2（空状態は本番のデザイン）
- 改善案: 案B（発見重視）では、0件ページの入口に件数0の表記を出し、代わりに関連する既存コンテンツへのリンクを置く。案Aでは入口の位置だけ変え、ページ自体は残す
- 確認方法: 3ページを開いて空状態の文言と、入口からの導線を確認する

### 指摘2: 絞り込み0件と元から0件の区別（catalog / works / chara / glossary）

- 観察した問題: 格子ページの絞り込みで0件になったとき、恒常0件と同じ「準備中です」が出る（設計論点 論点2・3）
- 利用者への影響: 条件を外せば戻るのに「無いもの」と判断して離れる恐れ
- 根拠: 設計論点 論点2（3が実害に近い）
- 改善案: 絞り込み0件では「条件に合う項目が無い」文言＋条件を外す導線を出す。恒常0件と文言を分ける
- 確認方法: 目録棚で条件を組み、0件時の文言と導線を確認する

### 指摘3: 画像欄が全件空の人物一覧（chara / chara-detail）

- 観察した問題: 13人全員が「イラスト準備中」。額縁の枠と題箋だけで並ぶ（手引き §2・設計論点 論点3）
- 利用者への影響: 文字主体の一覧で人物を識別する負担が増える。絵が入った日に並びが変わる恐れ
- 根拠: 手引き §2（image 13件全員空・描画側は用意済み）・§6-3（縦横比を先に決める）
- 改善案: 縦横比を先に決めて空枠の形を固定する。案Aでは現行の題箋表示を生かし、案Bでは文字主体の配置へ寄せる
- 確認方法: 一覧の現行レイアウトで、枠の縦横比が統一されているかを確認する

### 指摘4: 罫線トークン2系統の混在（全ページ共通・CSS）

- 観察した問題: 新 --rule* が48箇所、旧 --border-accent が29箇所残る
- 利用者への影響: ダークテーマで旧系統の罫線だけ見え方が違う可能性。片方だけ直す事故の温床
- 根拠: 手引き §5（置換が途中）・§7（既知の負債・中優先）
- 改善案: 案Aとして、旧29箇所を新系統へ置換する。置換は色の16進数を直接書かずトークン経由で行う
- 確認方法: 置換後に grep -c 'var(--border-accent' css/style.css で0件を確認し、ライト/ダーク両方で目視する

### 指摘5: HOME の Three.js 671KB（index）

- 観察した問題: HOMEだけがESモジュールでThree.jsを読む。671KB
- 利用者への影響: 初回表示の待ち時間が伸びる。ただし記録を読むページには影響しない
- 根拠: 手引き §3（671KB は重い・記録を読むページには入れない）
- 改善案: 案Aでは現状維持（HOMEに限る運用は既に守られている）。案Bでは読み込みの遅延や軽量化の余地を調べるが、効果は未実測
- 確認方法: 開発者ツールのネットワークパネルでHOMEの読み込みを確認する

## 案の比較（A / B / C）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A 現行を生かした最小修正 | 罫線トークンの置換完了と、絞り込み0件の文言分けだけに絞る | 工数が小さい。既存の設計思想を壊さない | 空データ3ページの体験は変わらない |
| B 発見・比較を重視 | 空ページに代替導線を置き、人物一覧を文字主体へ組み直す | 0件でも読者に次の行き先がある | 絵が入った日に作り直しになる恐れ。§6-3 の論点2と重なる |
| C 根拠・確認状態を重視 | 出典・検証状態の表示を各一覧へ広げる | 記録性（優先順位1）に直結する | 画面が情報過多になる恐れ。実装の重さは未実測 |

## 推奨

案Aを先に、案Bのうち「絵が入っても崩れない形」のものだけ後段に。案Cは catalog / sources に限って検討する。

未実測の数値（改善率・工数）は書いていない。すべての確認方法は手元での目視か、実画面の操作で確かめられる形にしている。
