## 1. 規約の要点(出典付き·事実と推論の区別)

### 1.1 C4モデル公式の記法ガイダンス 【事実·確認済み】
出典: c4model.com(創案者 Simon Brown 公式·CC BY 4.0)。確認日 2026-11-06。

| 区分 | 要点 | 出典 |
|---|---|---|
| 記法の位置づけ | C4 は **notation independent**(特定の記法·図形·色を規定しない)。「各図が単独で、文脈説明なしに(ほぼ)理解できること」が基準 | /diagrams/notation |
| 図(Diagrams) | ①全図にタイトル(図種別+スコープ) ②全図に凡例(図形·色·境界線スタイル·線種·矢頭のすべてを説明) ③略語は凡例で説明 | /diagrams/notation |
| 要素(Elements) | ①全要素に型の明示 ②全要素に短い説明(一瞥で役割が分かる) ③container/component には technology の明示 | /diagrams/notation |
| 関係(Relationships) | ①線は単方向 ②全線にラベル(方向と意図に整合。「Uses」のような単語を避け具体的に) ③container 間の関係(プロセス間通信)は technology/protocol を明示 | /diagrams/notation |
| 色(Colours) | 青灰箱は C4 の規定ではなく自由。要件は「色分けが**図内·図間で一貫**」と白黒印刷·色覚への配慮 | /diagrams/notation |
| 依存かデータフローか | どちらで描くかは選択。ただし**線の説明文が矢印の方向と一致すること**。より明示的な書き方が好ましい | /diagrams/faq |
| レビューチェックリスト | General(タイトル/図種別/スコープ/凡例)·Elements(名前/型/役割/technology/略語/色/図形/アイコン/境界線スタイル/サイズ)·Relationships(ラベル/方向一致/technology/略語/色/矢頭/線種)の各項目で「読者が意味を理解できるか」を問う | /diagrams/checklist |

### 1.2 各図種の定義(3面の「相当宣言」の照合基準) 【事実·確認済み】
出典: c4model.com 各図ページ。確認日 2026-11-06。

| 図種 | スコープ | 主要素 | 特徴 |
|---|---|---|---|
| System context | 単一システム | 対象システム(中心箱)+人+外部システム | 低レベル詳細(技術·プロトコル)を書かない。非技術者にも提示可。推奨 |
| Container | 単一システム | container(=アプリケーションまたはデータストア)+接続される人·システム | 主要な技術選択と通信を示す。**deployment 情報(クラスタ·冗長化等)は含めず、deployment 図(環境ごと)に分離**と Notes に明記 |
| Deployment | 1つの環境 | deployment node(物理サーバ·VM·コンテナ·実行環境。**ネスト可**)+infrastructure node(DNS/LB/防火壁等) | アイコンは使用可(ただし**凡例に載せる**) |
| System landscape | 組織全体 | 複数システム+人 | 「特定のシステムに焦点を当てない system context 図」 |

**推論**: 現行①は「管理対象2システム+人2+上位+外部」であり、C4 の system context(単一 EoI を中心に置く)より system landscape(焦点なしの context)の構造に近い。③は装置·ネットワーク·VM·AP を描くため、container 図よりも deployment 図(または infrastructure node を含む構成図)に近い。②は container 群+ESXi/VM の配置を同時に描くため、「container 図+配置情報の併記」に当たる。(推定根拠: 上記各ページの定義との構造比較。比較対象は実測 §2)

### 1.3 draw.io での C4 プラクティス 【事実·確認済み】
出典: drawio.com 公式ドキュメント。確認日 2026-11-06。

### 1.4 上位規格 ISO/IEC/IEEE 42010:2022 との整合 【事実(プレビュー範囲)·確認済み】
出典: 規格プレビュー PDF(iTeh 配布の公式サンプル·15頁、スコープ/目次/用語/概念基盤のみ)。確認日 2026-11-06。正本(有償)は iso.org/standard/74393.html。

- スコープ: 「アーキテクチャ記述(AD)の構造と表現の要求」を規定。**「This document does not specify the processes, architecting methods, models, notations, techniques or tools」— 記法そのものは規定しない**(スコープ節の明示)。
- **legend の地位**が確認できる: 「Model-based view components are governed by model kinds and documented by legends. **Nonmodel-based view components are documented by legends.**」(前書きの主要変更)／3.19 view component の注記「**a legend is an informal documentation of conventions**」。つまり 42010 でも「図の約束事を legend で文書化する」ことが標準的な慣行として位置づけられる。
- AD の適合要求(Clause 6)は目次から: 利害関係者の特定·利害関係者の視点·関心事項·アスペクト·ビューポイントの採用·ビュー·ビューコンポーネント·**AD 要素間の対応(correspondence)の記録**·**アーキテクチャ決定と根拠の記録**。

**推論**: 図1枚のレベルで 42010 に「適合」を主張することは構造上できない(図はビューコンポーネントの一部)。図作成に参照できるのは ①legend 慣行、②ビューに「どの関心事項に応えるか」を明示する慣行、③図間·図と文書の対応(correspondence)を記録する慣行、の3点。現行の出典符(T1/T1b/T2/T3)は③の「決定と根拠の記録」に相当する役割を果たしている。

### 1.5 推定(未確定)表現の慣行 【事実+推論】
- 事実: C4 公式サイトの notation/checklist/FAQ のいずれにも「推定·未確定」の表現規約は存在しない(記法非依存の原則から、凡例で説明した上で自由)。42010 も記法を規定しない。
- 推論: UML 慣行では stereotype(«proposed» 等)や dashed の使い分けで示すのが一般的だが、これは UML 側の慣行であって C4 公式ガイダンスではない。
- **結論: 現行の「破線=推定」「枠の破線=推定機器」の独自凡例は規格に反しない。条件は「凡例に書いてあること」のみ**であり、既に満たしている。

## 2. 現行図の実測(適用判断の入力) 【事実·確認済み】
実測: `相関図_pana_20261106.drawio`(3頁)の XML 解析。2026-11-06。LNB冊側ファイルは未確認(不明)。

- **凡例4行(3頁同文)**: 実線=確定した接続 / グレー破線=推定(未確認)の接続 / 矢頭=データの向きが確定(一方向で表記) / 枠の破線=推定機器(当Site未確認) / 灰色破線枠=別図参照 + 分類行 + 略語行 + 出典符行(T1/T1b/T2/T3、T3 は「証跡ではない」と明記)
- **分類色の実値**: サーバ系 `#EDE6F5/#7B5FA3`(VM·ESXi·DB領域)／端末系 `白/#9BBB59`／設備系 `白/#A94438`(LNB N07 は strokeWidth=3 で強調)／推定 `#F2F2F2/#969696 破線`／外部·別図参照 `白/#969696〜#808080 破線`／人 `#E8E8E8/#808080 実線`
- **線**: 確定=黒実線1pt·endArrow=classic。推定=`dashed=1;dashPattern=6 4`。上位向きは `startArrow=classic`(逆向き矢)。多セグメント線の中間は endArrow=none(端点のみ矢)
- **タグ**: S1/S2/E-a/E-b/N01〜N19 を8pt 白地灰枠で全ノードに付与。台帳参照(X02-⑪ 等)は本文テキスト内
- **帯**: `#404040` 地·白字8pt。②はネットワーク情報(192.168.30.xx〔T1〕/172.25.253.0/24〔T1b〕)を帯に併記
- **注記**: expl 7.5pt 灰字·n05 6.5pt(既知の最小値·PDF欠落問題を wrap で収容済み)

**実測で確認した問題2件**:
1. **凡例の分類色行(`g*_leg1`)の色見本が黒文字** — value は「分類: ■サーバ系　■端末系　■設備系　■推定　□外部·参照」でフォント色指定なし、子図形なし。■は5個とも黒のため、**凡例から分類色を直接読み取れない**(図中の紫色ノードと照合する作業が読者に残る)。
2. **`g3_n09_txt` に生マークダウン残存** — 「ノードは確定·**接続エッジは推定**(T3)」。draw.io は html 形式なので `**` は太字化されず**そのまま表示**される。※オーケストレータ追記: この `**` は stage2 Excel 冊子側のテキストに由来する(texts_stage2.json は stage2 実測)。**冊子側の欠陥でもあるため、冊子側は変更リスト(pana47/lnb48)で起票が必要。**

## 4. 現行からの主な差分

**規格適合のため変えるべきもの(小規模·順に適用可)**:
1. **凡例の色見本を実色化**(C3/①②③共通·最重要): 分類行の ■ を font color 付き HTML または小色ブロックに置換。3頁同時。text セルの value 置換のみで幾何は不変。※テキスト内容は変わらない(スタイルのみ)ため drawio 側は即実施可
2. **`g3_n09_txt` の `**` 処理**(③固有の表示欠陥): 「**接続エッジは推定**」は強調意図と解釈し `<b>` 化する(オーケストレータ判断·テキスト内容は保持)。**冊子側(Excel)の同欠陥は変更リストで起票**
3. **③の図種別宣言の見直し**: 注記を「C4モデルのデプロイメント図に相当(装置·ネットワーク構成)」等に。もしくは「コンテナ図に相当」を維持しつつ凡例に「配置·ネットワーク情報を含む」を追加。※テキスト変更を伴う → drawio 採用時に冊子側へも反映する変更として管理
4. **タグ接頭辞の凡例説明の追加**(C4/C14): 「S=システム単位/N=ノード/E·EE=接続線番号」を注記または凡例1行へ。※テキスト追加 → 同上

**慣行にはあるが、現状維持を提案するもの(根拠付き「変更不要」)**:
- 独自分類色(サーバ紫/端末緑/設備赤/推定灰/外部白)の維持 — C4 は色を規定せず、要件は「一貫性」のみ。3頁で一致しており合格
- draw.io C4 公式シェイプ(人形等)への全面置換 — notation independent のため必須でない。印刷冊子の矩形+【型】ラベル方式は checklist(C6)合格。置換するなら別ラウンド(幾何検証の再実行が要る)
- 凡例4行の頁ごとの重複 — C4「every diagram should have a key」に直接整合する意図的重複
- 「破線=推定」の独自凡例 — C4 に推定表現の規約はない。凡例明示の条件を満たすため規格上の問題なし
- ①に IP·プロトコルを書くこと(S1-2) — context 慣行(技術詳細を書かない)との差はあるが、手順書の読者が①から NPM-DGS の IP を確認する用途があるなら用途が優先。**削除は提案しない**

**任意の拡張(draw.io プラクティスとして可能·現行に追加価値)**:
- N 番号タグにメタデータ tooltip(X02-⑪ 等の台帳参照)を置く、頁間リンク(①→②③)を付ける — 印刷では効かないため電子運用時のみ
- 帯タイトルに図種別の短語を追加(「相関図② — コンテナ図相当(PanaCIM環境)」等)→ C1 の残差を解消する最小手(テキスト追加を伴う)
