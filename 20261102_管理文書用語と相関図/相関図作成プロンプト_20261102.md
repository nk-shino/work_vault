# 指示: 管理文書用のシステム相関図を、アイコン+座標指定のPythonモックで作成する

## 役割と目的
管理文書(手順書·報告書等の様式)に掲載する「システム·サーバ·機器の関係図」を、Python(Pillow)による座標指定モックとして作成する。完成条件は次のとおり。

1. 重なりチェッカーで「0 overlaps」を達成する(線×線の交差は許容できるが、迂回可否を1件ずつ検討して記録する)
2. 変更領域の拡大クロップで目視確認する
3. 採否判断はユーザーへ返す。実ファイルへの実装は承認後に別工程で行う

## 前提と禁止事項
- 実装対象のxlsx·docxには触れない。モックで合意してから実装する(openpyxlのsaveは環境により破損の恐れがあるため使わない)
- 絵文字は使わない。コンソールへ日本語を出すときは `PYTHONIOENCODING=utf-8` を付ける
- 略語·出典符の定義を無断生成しない。原資料で確認できた定義のみ記載し、未確認は「要確認(出典)」として明示する
- 「会議で決定」「承認済み」等の権威づけは、記録の確認なしに事実として書かない

## 開始時に入力を確認する(ユーザーへ)
1. 要素一覧: 名称·分類(サーバ/端末/設備/保存/人/外部)·1行の役割·確定情報(IP·所在等)·推定の有無
2. 接続一覧: 起点→終点·内容·確定/推定·出典
3. 用途: 誰が·どの場面で·紙か画面か·白黒印刷の有無
4. 様式: 頁サイズ·ヘッダー/フッターの定型·頁ラベル
5. 既存図と踏襲すべき記法の有無

## 作成手順

### 1. 情報整理と頁構成
- 要素·接続を表に整理し、確定/推定を出典付きで区別する
- 目安: ノード12超または接続14超なら分割を検討する。C4モデルの考え方に従い「全体の関わり(コンテキスト図)→各内部(コンテナ図)→対応リスト」の構成を基本とする
- 図とリストは番号(N番号·E番号)で相互参照し、詳細·出典·要確認はリストへ集約する(図は位置づけと流れを担う)

### 2. 記法の確定(視覚文法)
- 分類は「塗り+罫線の色」「枠の太さ」「【分類】接頭辞」の3重で示す(白黒印刷で区別可能にする)。推定機器はグレー破線枠
- 線: 確定=黒実線·推定=グレー破線。矢頭は向きが確定しているものだけ付け、一方向で表記する
- 全ての線にラベル(E番号+内容)を付ける
- 各図頁の下部に凡例(線·枠の意味)·分類見本·略語の3行を置く。フッターの様式文字とも重ならない位置(例: 下端から30pt以上上)とする
- グループ帯(ネットワークセグメント等)は破線の外枠+見出しタグ。帯境界を跨る要素は太枠で示し、チェッカーの免除リストに設計意図として登録する

### 3. アイコン
- 素材: Material Symbols Rounded。軸は FILL=1·GRAD=0·opsz=20·wght=400 に固定(塗りあり·小サイズ用。細線スタイルは白黒印刷で途切れる)
- 色: 単色 #404040·背景透過·透過PNG 256×256px。分類色のアイコンは作らない(分類はノードの色と接頭辞が担う。黄は白黒印刷で消失する)
- 取得: `github.com/google/material-design-icons` の variablefont 配下から ttf と `.codepoints` を取得し、Pillowでコードポイントのグリフを描画して保存する
- 対応表(icon_map.mdの様式)を作る: 種別·アイコン名·ファイル名·推奨サイズ·配置ルール·選定理由(1行)·予備候補(実在確認済みのもの)
- 配置: ノード左端の内側(左右6pt·上8pt)·13pt。テキストはアイコンの右5ptから左寄せ

### 4. モック実装(Pillow)
参考実装 c4_mock.py を雛形にし、ノード·エッジ·リストのデータを差し替える。規約は次のとおり。

- 座標はpt基準。`S=3.0`倍してpxへ描画。A4横は842×595pt、縦置きリストは595×842pt
- フォント: Meiryo(`meiryo.ttc`·太字`meiryoB.ttc`)
- CV API: `CV(w_pt,h_pt)` / `rect(x,y,w,h,fill,outline,width_pt,radius)` / `line(pts,fill,width_pt,dash)` / `arrow(x,y,dx,dy,size_pt)` / `text(x,y,s,size_pt,anchor,halo)` / `tlen(s,size_pt,bold)`(実測幅をptで返す) / `icon(key,size_pt)`
- グローバル: `PAGE`(現在頁)·`OX,OY`(図面原点)·`CHECKS`(登録リスト)
- `draw_node`: 分類スタイル·番号チップ(枠上端中央·白地)·アイコン·【分類】名(太字)+1行役割を描き、icon/ntext/chip/node を登録する
- `edge`: 線分ごとにseg登録·矢頭はarr登録(着先ノードを find_node_owner で特定)·ラベルは elabel(中央基準·halo付き白地)

### 5. 重なりチェッカー(この方式の本体)
- 全要素を `reg(page,kind,owner,x0,y0,x1,y1)` で登録する。kind: node(ノード矩形)·ntext(文字)·label(線ラベル)·chip(番号チップ)·icon·seg(線分)·arr(矢頭)·cbord(帯枠·4辺を厚みtの帯として登録)
- 判定: `_rects_overlap`(0.5pt許容)で重なり検出。seg×segのみ線分の真の交差(proper_cross)として「交差(許容)」表示し、重なりには数えない
- node関連: node×nodeは包含なら許容·文字/チップ/アイコンはノード内に収まっていれば許容·枠に掛かったらNG
- node×seg: 節点を貫通する線はNG(端点が近ければ許容)。node×arr: 対象外ノードへの矢頭はNG
- 同一owner同士·EXEMPT_EIDS(設計意図の免除リスト)は無視する
- 実行ごとに「0 overlaps, n crossing(許容)」を出力する

### 6. 検証ループ(収束まで繰り返す)
- 収束条件: チェッカーの重なり0件+残る交差が線×線のみで迂回検討の記録があること+変更領域の拡大クロップ目視確認
- 失敗パターン(再発禁止):
  - 描画anchorと登録矩形の基準の不一致。ラベルは中央基準(mm)で描き、登録矩形も中央基準で計算する。左寄せ描画+中央基準登録は検査位置と実グリフがずれる盲区間になる
  - 登録漏れ。タイトル·副題·凡例·フッター·帯見出しもntextとして必ず登録する。未登録要素は検査対象外になり、後から指摘が出る
  - 長文の頁幅超過。tlenで実測し、終端が安全しきい値(例: 頁幅−40pt)を超える場合は折返し(wrap)または2行分割する
  - 接触の解消は、頁の上下マージン(帯の高さ·凡例位置·タイトル行)を先に調整してから個別座標を動かす
- 目視: PILで関心領域を切り出して拡大保存し、目視確認する(全頁の全景+修正箇所の拡大)

### 7. 盲評価と受け渡し
- 前提資料(図の意図·未確定事項·評価観点)を1枚にまとめ、役割の異なる評価者(例: 現場作業者·初学者)を独立セッションで評価させる。評価者間の意見は見せない
- 指摘は実在検証(座標·幅の実測)をしてから反映する。誤検出は理由を記録して除外する
- 対立する意見は多数決にしない。記録に残す
- 成果物: PNGモック群·記法仕様(icon_map.md·notation_spec.md)·チェッカー出力の記録·評価記録·実装時の未決事項リスト(頁番号の付与·台帳の所在·白黒グレースケール確認等)·適用提案メモ
- 作業はトピックフォルダ(`YYYYMMDD_<topic>/`)で行い、実行ログ(指示1件=エントリ1件)を残してコミットする

## 実績の参考値(参考実装での検証結果)
- 図面3頁(横A4·ノード7〜10/頁·帯1/頁)+リスト2頁(縦A4·機器18行·接続18行)で チェッカー重なり0件·交差4件(全て線×線·迂回不可の根拠を記録)
- 略語行·フッター·タイトル·副題を登録対象に含めて初めて「重なり0件」を確証できた(未登録だった時期には実在の重なりを検出できていなかった)
