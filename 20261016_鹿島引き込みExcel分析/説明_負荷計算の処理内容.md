# 負荷計算の処理内容説明(第三者向け)

- 作成日: 2026-10-16
- 対象読者: SMT実装の生産計画に関係するが、各マクロの中身を直接見たことがない方
- 根拠: TOOL.xlam・BOSS計画.xlsm・差分確認マクロver2.3a.xlsm のVBA復号結果とブック内数式、および ジョブ作成時データテーブル一覧(オーダテーブル作業テーブル・製造BOM).xlsx の実データ。行番号は復号ファイル(tool_vba.txt / vba_code_all.txt / Formulas_Section1.m)の行。すべて読み取り専用解析で、元ファイルは変更していない。

## 1. 全体像 — 3系統の計算で「収まる」を判断している

生産計画で「このジョブは装置に入るか、その日は終わるか」を判断する処理は、1か所ではなく3系統に分かれている。

1. スロット容量判定 — 部品がフィーダーとして物理的に載るか。ジョブ作成時(段取り予定表のTOOL.xlam)とBOSS取込時(BOSS計画.xlsm)で同じ判定を実行する。
2. 時間負荷計算 — 生産数量とサイクルタイムから稼働時間を算出し、日次の枠に収まるかを見る。BOSS計画.xlsm が担う。
3. Asprovaの割付け — 製造BOMと製造効率に基づき、資源カレンダーの空きへ作業を割り付ける。入らないオーダーは順延・割当変更で調整される。

データの流れは次のとおり。

DGS(実装条件作成ツール)で基板ごとのサイクルタイムを作成 → CSV出力 → TOOL.xlam が MySQL `QCD.CycleTime_Points` へ登録(tool_vba.txt:713-790) → BOSS計画.xlsm と段取り予定表が「最新10指図の実績平均」を取得(Formulas_Section1.m:4-7) → 負荷計算(1.と2.) → Asprova へ製造BOMを渡して割付け(3.)。

Asprovaがジョブ作成時に受け取るデータは3つのテーブルである(ジョブ作成時データテーブル一覧.xlsx の実データで確認)。

| テーブル | 行数 | 内容 |
|---|---|---|
| オーダーテーブル(指図) | 90 | 指図番号・品目・数量・納期・着手/完了実績 |
| 作業テーブル | 96 | 実装工程の作業ごとに資源・開始/終了・数量・段取と製造の実績時間 |
| 製造BOM | 24,763 | 工程ごとの品目/部品と、1個当たりの時間・段取・製造効率 |

DGS画面では、ラインL3NPM-1〜7(ノズル構成3/3〜16/16)ごとに基板5枚分のサイクルタイム・総実装点・ターン・Sec/Shoot・CPHが表示され、赤セルの値(7.393〜45.436秒)がライン全体で最も遅い機種、すなわちネックのサイクルタイムを示す。CSV出力オプション(サイクルタイム/部品リスト/フィーダーリスト/ノズルリスト)で出したファイルが、前述のMySQL登録の源になる。

## 2. 処理1: スロット容量判定(部品が載るか)

実装箇所: TOOL.xlam の部品確認ボタン `BuhinKakunin_ADO`(tool_vba.txt:3759)、BOSS計画.xlsm の `Cal_Capa`(vba_code_all.txt:573)。両者は同じロジックである。

処理の手順は次のとおり。

1. 選択した品目ごとに、部品リスト.accdb(`\\nksv523...\Job作成\部品リスト.accdb`)の egproBOM×PartList から部品名とフィーダーサイズを取得する。
2. フィーダーサイズを合計し、必要スロット数とする。部品のノズル欄に1000超の番号がある部品は3ノズルヘッド機用として集計を分ける(tool_vba.txt:3840)。
3. 装置の上限と比較する。上限は 3ノズルヘッド用90 + その他300 = 合計390スロット。
4. 空きスロット数を画面表示する。「【ALL】 x/390(空き: …)/ 3Noz: x/90 / Other: x/300」(tool_vba.txt:3939-3942)。
5. テーブル禁止推奨数の判定だけ安全率0.8が入る。非共有スロット数を 150×0.8=120、144、168、192、216 と順に比較し、超えるごとに禁止推奨テーブルが1つ増える(優先度 T8>T6>T4>T2>T10、tool_vba.txt:3921-3927)。

ここにサイクルタイムは登場しない。部品点数とフィーダーサイズだけの物理判定である。BOSS計画.xlsm 側では、この判定を日付×グループ(フリー/L1試作/L2試作/L3試作)ごとに実行し、結果を「計算」シートのフリー容量列へ書き込む(vba_code_all.txt:401-413)。

## 3. 処理2: 時間負荷計算(その日の中に収まるか)

実装箇所: BOSS計画.xlsm の `chkTime`(vba_code_all.txt:486-567)。同じ数式が `getBOSS_btn` 内にも重複実装されている(vba_code_all.txt:835-861)。

数式は次のとおり。

```
工数(h) = ( 生産数量 × サイクルタイム秒 + 段取600秒 ) ÷ 3600 ÷ 0.7
```

- サイクルタイムは実績平均である。パワークエリが MySQL から品目×Pn(表裏)ごとに最新10指図分を取得し、28秒未満は28秒に補正した上で平均する(Formulas_Section1.m:4-7)。DGSの最速値そのものを使っているのではない。
- サイクルタイムDBに品目が無い場合の代替値が用意してある。量産は56秒/台、試作は75秒/台(vba_code_all.txt:502-504)。組取り数が分かる品目は 数量÷組取り数 で台数を出す。どちらも無い品目は数量×28秒+600秒で仮計算し、リストに「★」印で残す(vba_code_all.txt:544)。
- ÷0.7 は計算上の工数を約1.43倍に膨らませる方向の余裕である。安全率を乗じて縮める実装はコード内に存在しない。
- 計算結果は「計算」シートに日付×グループで集約され、各グループの停止時間と合わせて日次の枠と照らされる。

## 4. 処理3: Asprovaのガントが容量を超えない理由

- 製造BOM(テーブル要素)に品目ごとの製造時間 sp(秒/個)と製造効率が設定してある。製造効率は実データでは工程別に分かれており、実装 0.7(9,645行)、目視 0.6(5,468行)、外観検査 0.5(2,269行)、二課 1.0(2,255行)である。旧資料の「SMT 0.7 / 外観検査 0.5」はこの内訳の一部である。
- 作業時間は「数量 × sp ÷ 製造効率 + 段取」で計算される。効率0.7の場合、実時間の約1.43倍の時間として計画に載る。処理2の÷0.7と同じ発想である。
- 段取にも効率が適用される。製造BOMの段取列には「10m」と「14.28571m」が混在し、14.28571m = 10m ÷ 0.7 である。作業テーブルの実績でも段取計画は「10M」と「14M17S」の2種類しか出ておらず、この対応を裏付ける。
- 実データでの裏付け: 作業テーブル96行のうち実績のある行で「(総時間−段取)÷数量」と製造BOMの sp÷0.7 を比較すると、84%(41/49行)が±12%以内で一致する。BOMの sp は実績平均CT÷面数から作られており、計画値としては整合している。一致しない残りは実績側のばらつき(トラブル・段取り替え等)である。
- 割付けは資源カレンダーの空き範囲内で行われ、入らないオーダーは順延または代替資源への割当変更で調整される。「超えない」は判定後の自動調整の結果であり、事前の合否計算の結果ではない。
- 製造BOMの元になるのは差分確認マクロのBOM作成シートで、E列にサイクルタイム秒(N列で「CT÷面数」の秒/個に換算)、13行目の注記に「28秒以下は、28で入れる」がある。28秒下限の規則は処理2のパワークエリと共通である。BOMシートへのCT転記経路(手作業かリンクか)は今回の解析では確認できていない。

### 4.1 製造BOMの読み方(実データの列対応)

ジョブ作成時データテーブル一覧.xlsx の製造BOMシート(24,763行)は、Asprovaが作業時間を計算するのに必要な値を工程ごとの行で持つ。

| 列 | 意味 | 実データの例 |
|---|---|---|
| EM_Item | 品目(基板) | URS-43833 |
| EM_ProcessOrderInt4 | 工程順序番号 | 2010=実装-1, 2020=実装-2, 2090=目視/外観検査, 2220=二課 |
| EM_ProcCode | 工程コード | 実装-1 / 実装-2 / 目視 / 外観検査-1 / 二課 |
| EM_ResOrItem | 使用資源または入力品目 | SMT-1L〜3L / SMT-AOI1,2 / SMT-VI1〜5 / SMT-Nika-1〜4L |
| EM_InstructionType + EM_Instruction | 指図の種類 | U×M=使用指図(19,670行) / I×In0=入力指図(5,012行) |
| EM_Task1 | 段取時間 | 3m(5,745行) / 14.28571m(4,663行) / 10m(415行) |
| EM_Task2 | 1個当たりの製造時間 | 16.5954sp のような「数値+単位」 |
| UseBomInst_ProductionFactor | 製造効率 | 0.7 / 0.6 / 0.5 / 1.0 |

EM_Task2 の単位は Asprova の時間表記である。sp=秒/個(17,197行)、mp=分/個(212行)、d=日(2,255行、二課の滞留期間)。外観検査には「9sp+15」のように 秒/個+固定秒 の表記もあり(338行)。二課の「3d」は1個あたりの作業時間ではなく日単位のリードタイムとして扱う値である。

### 4.2 オーダーテーブルと作業テーブルの対応

- 作業テーブルは1工程=1行で、指図コード(000212249572-2010 のような 品目コード-工程番号)で管理される。同一指図が実装-1(2010)と実装-2(2020)で2行になる。
- 作業テーブルの時間列の対応は実データから次のとおり確認した。X列=製造時間(実績)、AA列=段取時間(計画: 10M または 14M17S)、AE列=総時間(実績)であり、X+AA≈AE が49行中44行で成立する。残り5行は実績側のずれである。
- オーダーテーブルのAO列は「納期−完了実績」(I−AK)で、49/53行が一致。負の値=納期超過を示す。AN列(負の時間)の定義は推定を避け未確認としている。

## 6. 確認が必要な点

- 安全率0.7の方向。会議メモ(生産量を調査。.md)は「サイクルタイム=DGS最大値×安全係数」と記録しているが、コード実装は「実績平均CTを÷0.7」である。×方向の記述は実装と一致しない。0.7の設計意図は関係者(佐藤さん・実装技術課)への確認が必要である。
- DGS最速値(実装技術課が管理)と実績平均CT(生産1課の実績)の差をマスター検証でどう扱うか。これがBSM-1700負荷計算用マスター確認の要点になる。
- 段取り予定.xlsx本体(SharePoint)と差分チェックシステム(172.25.253.60)は今回の解析対象外であり、ジョブ作成シートの容量確認処理はTOOL.xlam側の実装から推定した。
- オーダーテーブルAN列(負の時間)の定義。着手遅延系の指標と推定されるが、列名・根拠が無いため断定していない。
- 二課の「3d」(EM_Task2)が日単位の滞留/リードタイムであることの運用上の確認。
- 「14.28571m」と「10m」の使い分け(どちらを正とするか)。実績では両方が観測される。
